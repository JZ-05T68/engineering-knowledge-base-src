## 8. 选定问题：证据与复现路径

**缺陷**：`_EvidenceRepository.get_or_create_basket`（`src/evidence_basket_service.py:336-351`）先 `SELECT ... WHERE name=?`（自动提交模式，不持锁）、无行则 `INSERT`。schema 对 `evidence_baskets.name` **没有 UNIQUE 约束**（`src/migrations.py:427-435` 仅 `CHECK`）。`Database._connection`（`src/database.py:102-116` 同款模式：`_EvidenceRepository._connection` 见 `:309-322`）在 Python sqlite3 传统隔离级别下，SELECT 不开启事务——检查与插入之间存在窗口。

**现实触发**：`EvidenceBasketService.default_basket()`（`:76-79`）被证据篮几乎所有操作调用；两个浏览器标签页/两个会话线程在全新数据库上首次同时访问证据篮功能即可能并发进入该窗口。

**当前行为**：两个并发调用各自 SELECT 得到"不存在"，各自 INSERT 并提交 → `evidence_baskets` 出现两行同名"默认证据篮"；此后 `ORDER BY id LIMIT 1` 恒定返回 id 较小者，经另一句柄加入的证据条目**永久不可见（静默数据丢失）**。

**预期行为**：无论并发时序如何，同名证据篮永远只有一个；所有并发调用方得到同一个篮。

**必须保持的不变量**：单线程行为完全不变（先查后建、幂等）；schema 保持 v4（不新增 UNIQUE 约束、不做迁移）；不改 `EvidenceDatabase` Protocol 与任何接口；失败路径继续由 `_connection` 统一 rollback。

## 9. 回归测试（先于修复）

新增 `tests/test_evidence_basket_service.py::test_default_basket_concurrent_first_access_keeps_single_basket`（+68 行，含辅助代理类 `_SelectSyncConnection`）：

- `tmp_path` 建真实 schema v4 数据库与 `EvidenceBasketService`；
- monkeypatch `_EvidenceRepository._connection`，用代理连接在"按 name 查篮"的 SELECT 返回后停靠 `threading.Barrier(2)`——**保证两个线程都先拿到"不存在"的结果，然后才允许任一继续插入**，消除时序依赖；
- 两个线程并发调用 `service.default_basket()`；断言：无线程异常、返回的篮 id 集合大小为 1、数据库中 `COUNT(*) WHERE name='默认证据篮' == 1`；
- Barrier 带 5 秒超时：修复后持锁线程会独自等到超时（`BrokenBarrierError`，窄捕获后放行），另一线程在锁释放后读到已提交行——同一测试对修改前确定性失败、对修改后确定性通过。

## 11. 修复设计与理由

**修改**（`src/evidence_basket_service.py`，+4 行）：在 `get_or_create_basket` 进入连接后、SELECT 之前执行 `connection.execute("BEGIN IMMEDIATE")`，并附 3 行注释说明原因。

**理由**：

- `BEGIN IMMEDIATE` 立即获取写意向锁，把"检查—插入"整体串行化；第二个并发调用在该语句处等待（连接已设 `PRAGMA busy_timeout = 30000`），待第一个提交后再 SELECT，读到已存在行直接复用；
- 项目既有惯例：`src/migrations.py:424` 与 `batch_service` 事务均使用 `BEGIN IMMEDIATE`；
- 影响面最小：该方法本就可能紧接 INSERT（持锁时间微秒级），单用户本地应用无争用风险；单线程路径行为完全不变；
- 明确**不采用**的替代方案：给 `name` 加 UNIQUE 约束 = 修改 schema（任务禁止且需迁移）；捕获 `IntegrityError` 重查 = 同样需先改 schema。
