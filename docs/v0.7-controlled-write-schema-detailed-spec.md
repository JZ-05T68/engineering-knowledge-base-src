## 2. DEEPSEEK_GATE_G1 — 物理版本号（唯一仍开放的门禁项）

**事实**：`ADR-006` Decision 9 曾把 "schema v13" 预留给 agent 多步执行链三表
（`agent_runs/agent_steps/tool_calls`，Phase 3 multi-step 触发，至今未落地）；
`ADR-011` 又用 "v13" 指代受控写经验数据模型。两者内容不同、编号相同。

**本规格推荐**：`TARGET_SCHEMA_VERSION = 13`，内容 = CONTROLLED_WRITE_SCHEMA_REVISION
（本文件）；ADR-006 的 agent 三表草案在其真正触发时重新编号，并在 ADR-006 加一行
勘误注记（不改动其决定）。

**理由**：①经验模型是唯一已被 ADR-011 冻结内容、且已被两份下游文档（失败矩阵、实施
计划）按"下一个迁移"引用的修订；②agent 三表无任何触发条件，为一个无触发草案占用
下一个编号会使"编号=内容"的对应在事实上断裂；③勘误注记是文档最小改动。

**风险**：若门禁裁决相反（agent 三表占用 13），本规格的全部内容不受影响——所有
DDL/约束/迁移设计以 TARGET_SCHEMA_VERSION 为参数，仅需改函数名与版本常量。

**状态：OPEN_FOR_DEEPSEEK_GATE。其余全部决策均为 IMPLEMENTATION-FROZEN（§54）。**

### 3.6 schema 元数据机制

- `schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL)`；
  当前版本 = `MAX(version)`；
- `migrate_database`：非空且需升级 → 先 `backup_database`（SQLite backup API +
  integrity 验证，失败即删备份文件并抛 `MigrationError`）；连接设
  `PRAGMA foreign_keys = OFF` / `journal_mode = WAL` / `busy_timeout=30000`；逐版本
  `if current_version < N: _apply_version_N(connection)`（v11/v12 显式
  `current_version = N`）；尾部 `PRAGMA foreign_keys = ON` + `integrity_check` +
  `foreign_key_check`，任一失败抛 `MigrationError`；
- 每个版本函数：模块级注入钩子变量（`_VXX_INJECTION_POINT`）+ `_inject_vXX_failure(point)`
  + 前置数据指纹 + `BEGIN IMMEDIATE` + 单事务 DDL/DML + 版本记录 + 后置指纹比对 +
  `connection.commit()` / 异常 `connection.rollback()`。

## 6. N-3 裁决 — outcome 长度

**调查记录**：

| 证据点 | 事实 |
| --- | --- |
| 服务层校验 | `src/database.py` create/update 记忆条目：`if len(outcome) > 4000`（"结果不能超过 4000 个字符"）；`context_conditions` 同为 4000 |
| schema | v12 ALTER 添加，无 CHECK |
| UI | 记忆页创建表单无 outcome/context_conditions 输入；无任何 UI 层长度限制 |
| 测试 | 无任何测试钉住 outcome 长度（grep 复核） |
| 历史迁移 | v12 添加列时无长度约束、无回填 |
| 比赛/演示使用 | 无使用（字段当前无活跃写入方） |
| 同族字段惯例 | root_cause/lesson 均为 4000（DB CHECK + 服务校验双层）；ExperienceModelService `_FIELD_MAX = 4000` |
| 预研措辞 | §12/§27 "outcome ≤2000" —— **无任何仓库事实支撑的孤立数字** |

**裁决：OUTCOME_MAX_4000。**

**理由**：①兼容与最小行为扰动——4000 是实现自 v12 以来的唯一真实边界，若裁 2000
会在 schema CHECK 与两年服务行为之间制造无谓差异；②与全部同族经验文本字段
（root_cause/lesson/context_conditions/候选字段 `_FIELD_MAX`）一致；③预研的 2000
无测试、无 UI、无历史依据。**DB CHECK 应当执行它**（重建时补
`CHECK (length(outcome) <= 4000)`）——沿 ADR-010 验证分层（"DB CHECK/UNIQUE 是第二道
防线"）与 root_cause/lesson 完全同构；既有行全部合规（服务校验自列存在起一直生效），
零迁移风险。`context_conditions` 同批补 CHECK（同一缺口、同一理由、同一零风险）。

**受影响校验/测试**：无既有代码需改（服务校验本就是 4000）；新增迁移测试应断言
新 CHECK 存在且 v12 旧行升级后仍合规。**不改代码。**

### 7.3 齐性不变量

受控创建的经验：**每个 block_key 恰有一行 provenance**（10 行）；允许来源链接的
8 个块可各关联 0..N 条 `knowledge_memory_sources`；title/outcome 恒 0 条来源。
人类既有路径创建的条目：provenance 行可缺席（缺席 = 保守"未标注"，§11.3）。

## 8. Provenance 存储形态 — 选型与冻结

**选型比较**（按任务 §9 的候选集）：

| 准则 | A. 每块一列（约 10 列） | B. JSON 对象列 | C. 规范化行（选定） | D. 其他（列名即 key 等） |
| --- | --- | --- | --- | --- |
| SQLite 约束强度 | 每列 CHECK 可行 | CHECK 只能做 json_valid 级；键/值闭合无法在 DB 表达 | FK + 双闭合 CHECK + UNIQUE 全部 DB 级 | 弱 |
| 迁移复杂度 | 重建表多 10 列 | 1 列 | 1 张空表 | — |
| 可查询性 | 尚可（列爆炸） | 差（需 json_each） | **优**（WHERE origin='agent_inferred' 直查） | — |
| UI 渲染 | 直读列 | 解析 JSON | 一次 JOIN | — |
| 规范哈希 | 10 列拼装 | 序列化歧义（键序/空格） | **按 block_key 排序的行序天然规范** | — |
| 未来加块 | **表重建** | 无结构变更 | 枚举值扩展（block CHECK 随下次重建演进；行结构不变） | — |
| 损坏检测 | CHECK | DB 层不可检 | FK/CHECK/UNIQUE + §41 逻辑查询 | — |
| 过度规范化风险 | 无 | 无 | **低**（每条目 ≤10 行，1:1 粒度，无多对多膨胀——块↔源的多对多由 §10 表承担） | — |
| 仓库风格 | 背离（无同类先例） | 背离（`target_refs` JSON 仅为审计附带列，非主数据） | **契合**（闭合 CHECK + 规范化表是全仓主风格） | — |

**冻结：方案 C —— 新表 `knowledge_memory_block_provenance`。**

```sql
CREATE TABLE knowledge_memory_block_provenance (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entry_id INTEGER NOT NULL
        REFERENCES knowledge_memory_entries(id) ON DELETE CASCADE,

        'title', 'problem', 'context', 'action', 'result',
        'root_cause', 'lesson', 'applicability', 'limitations', 'outcome'
    )),

        'user_asserted', 'direct_observation', 'agent_organized', 'agent_inferred'
```

（DDL 为规格示意；实现时按仓库迁移惯例写为带 `_inject` 钩子的事务内语句。索引命名
沿 `idx_knowledge_*` 风格调整。）

- origin 存储值用小写下划线（与 `KnowledgeEpistemicBasis` 的
  'personal_experience'/'direct_observation' 值风格一致）；
- **EXISTING_SOURCE_SUPPORTED 不入库**——派生态：某 block_key 在
  `knowledge_memory_sources` 存在活跃（目标未删）关联即显示"有来源支持"；
  目标全删则回落到持久 origin。派生规则见 §10/§13；
- `created_at`：provenance 行的创建时刻（= 命令提交时刻），便于审计；
- 隐私：本表只存枚举与 ID，零正文。

## 9. `root_cause_user_confirmed` 精确语义（冻结）

| 问题 | 裁决 |
| --- | --- |
| 既有行默认 | `0`（不推断；沿 v10 "no origin inference is performed on legacy data" 纪律） |
| 人类创建（creation_origin='human'）默认 | `0`；根因块 origin 行 = `user_asserted` 已表达"用户亲述"——确认门概念对人类路径冗余，恒 0 即可，不制造双权威 |
| agent_assisted 默认 | `0`；更强的 AI 根因默认 `agent_inferred` origin 行 |
| 何时可为 1 | 仅 agent_assisted 条目：用户对根因块执行显式"确认根因"动作，且该动作**绑定进批准载荷**（哈希覆盖）后才可为 1；1 与 `root_cause` 块 origin 行升格为 `user_asserted` **同笔提交**（列与 origin 行是同一事实的两种落库表达，服务层保证二者一致；DB 跨表一致性由同事务保证） |
| 要求 root_cause 非空 | 是——DB 级跨列 CHECK `(root_cause_user_confirmed = 0 OR length(root_cause) > 0)`（§5.2）；其余确认策略（如"确认时是否必须同时存在来源关联"）留应用层，不过度用 CHECK |
| v0.7 创建后可迁移吗 | **否**。确认发生在批准之前、随 create 落库；`update_knowledge_memory_entry` 不得修改本列（冻结：连接感知扩展时不加入该列的赋值面）；变更需走未来 ADR |
| 整稿批准自动置 1？ | **NO**（确认上游预期）。批准只授权 mutation，不改变认识论标记（ADR-011 §2） |
| 参与规范哈希？ | **YES**（确认上游预期） |

## 10. `knowledge_memory_sources` — 完整设计

### 10.1 目标类型选型（按实际 v0.7 工作流，逐类型裁决）

工作流事实：草稿引用 = `ExperienceCandidate.citations` = 经上下文包校验的
stable_id 集 = `ContextItemType` 投影的实体（page / knowledge_object /
knowledge_memory / evidence）。**document 从不出现在上下文项/引用中。**

| 目标类型 | 裁决 | 理由 |
| --- | --- | --- |
| `page` | **接受** | 引用主力；指纹现成（v1 配方：extracted/ocr 文本） |
| `knowledge_object` | **接受** | 引用主力；无指纹配方——用 `current_revision` 计数器做变更检测（§13，零新哈希） |
| `evidence` | **接受** | 证据项是天然经验支撑；指纹现成（v1 配方：行字段）；可硬删→删除策略必须闭环（§11） |
| `document` | **拒绝（v0.7）** | 工作流不产生 document 级引用（引用是 page 级）；ADR-011 列举它为"允许"而非"必须"；未来需要时枚举扩展迁移即可 |
| `knowledge_memory` | **拒绝（v0.7）** | 自引用同类表（周期/语义复杂）；记忆是用户创作内容而非外部支撑（ADR-009 语义）；ADR-011 §3.2 未列举它；他人经验引用留待未来显式门禁 |
| `note` | **拒绝** | 不在 ContextItemType 引用面内（note 经由 KO 来源间接出现）；指纹配方存在但工作流不可达 |

### 10.2 表规格（冻结；DDL 为规格示意）

```sql
CREATE TABLE knowledge_memory_sources (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    entry_id INTEGER NOT NULL
        REFERENCES knowledge_memory_entries(id) ON DELETE CASCADE,
    block_key TEXT NOT NULL CHECK (block_key IN (
        'problem', 'context', 'action', 'result',
        'root_cause', 'lesson', 'applicability', 'limitations'
    )),
    page_id INTEGER NULL REFERENCES pages(id) ON DELETE SET NULL,
    knowledge_object_id INTEGER NULL
        REFERENCES knowledge_objects(id) ON DELETE SET NULL,
    evidence_id INTEGER NULL REFERENCES evidence_items(id) ON DELETE SET NULL,
    -- 快照列（§10.3）：目标删除后仍诚实可显示
    target_stable_id TEXT NOT NULL CHECK (
        length(target_stable_id) BETWEEN 1 AND 128
    ),
    target_title TEXT NOT NULL DEFAULT '' CHECK (length(target_title) <= 500),
    fingerprint TEXT NULL CHECK (
        fingerprint IS NULL OR length(fingerprint) = 64
    ),
    fingerprint_version INTEGER NULL CHECK (
        fingerprint_version IS NULL OR fingerprint_version >= 1
    ),
    target_revision INTEGER NULL CHECK (
        target_revision IS NULL OR target_revision >= 1
    ),
    created_at TEXT NOT NULL,
    UNIQUE (entry_id, block_key, target_stable_id)
);
CREATE INDEX idx_kms_entry ON knowledge_memory_sources(entry_id);
CREATE INDEX idx_kms_page ON knowledge_memory_sources(page_id);
CREATE INDEX idx_kms_ko ON knowledge_memory_sources(knowledge_object_id);
CREATE INDEX idx_kms_evidence ON knowledge_memory_sources(evidence_id);
```

**关键设计点（必须逐条落实）**：

1. **"至多一个目标" DB CHECK**：`CHECK (
     (page_id IS NOT NULL) + (knowledge_object_id IS NOT NULL)
     + (evidence_id IS NOT NULL) <= 1 )`。
   **不得**写成 `= 1`——ON DELETE SET NULL 会把行更新为全 NULL，`= 1` 的 CHECK 会在
   目标删除时**炸掉删除操作**。"恰好一个"由提交服务在 INSERT 前强制（域校验层），
   DB 层兜底"至多一个"。这是本设计最易错的点，实现与测试都必须钉住。
2. **块粒度**：`block_key` CHECK 只含 8 个可被来源支撑的块（title/outcome 排除，
   §7.2）；与 §8 provenance 的 block_key 枚举是"子集"关系（两处 CHECK 各自闭合）。
3. **UNIQUE(entry_id, block_key, target_stable_id)**：同一来源对同一块至多一条；
   同一来源支撑多块 = 多行；同块多来源 = 多行。用 stable_id 而非 typed 列做唯一键，
   因为三列 typed 唯一约束在 NULL 上失效（SQLite UNIQUE 视 NULL 为互异）。
4. **entry 级联**：条目硬删（既有人类路径）时关联行 CASCADE 消失；条目墓碑
   （undo）时**零变化**（墓碑不触碰来源行）。
5. 三个 typed FK 的 `ON DELETE SET NULL` 语义与快照列的组合见 §11。

### 10.3 快照列规格（逐字段冻结）

| 列 | 类型/NULL | 最大逻辑长度 | 参与批准哈希 | 创建后可变 | 迁移行为 | 冻结理由 |
| --- | --- | --- | --- | --- | --- | --- |
| `target_stable_id` | TEXT NOT NULL | 128（实际 ~64） | **是** | 不可变 | 空表 | 目标删除后仍可解析出类型+ID+库身份（`parse_source_id`），是"曾引用何物"的唯一持久凭证 |
| `target_title` | TEXT NOT NULL DEFAULT '' | 500 | **是** | 不可变 | 空表 | 用户批准时所见显示标题；missing 态诚实展示"曾引用：<标题>（已失效）" |
| `fingerprint` | TEXT NULL | 64 hex | **是** | 不可变 | 空表 | 支撑声明的比对基线（page/evidence）；KO 为 NULL（§13） |
| `fingerprint_version` | INTEGER NULL | — | **是** | 不可变 | 空表 | 配方版本；错配=不可比（§13 fail-closed） |
| `target_revision` | INTEGER NULL | — | **是** | 不可变 | 空表 | KO 目标的变更检测基线（§13）；其余类型 NULL |
| `created_at` | TEXT NOT NULL | — | 否（审计时间） | 不可变 | 空表 | 关联建立时刻 |

**`target_stable_id` 与 live FK 是否冗余？——不冗余，两者都要**：
live FK = 目标存活期的引用完整性（`foreign_key_check` 可发现目标被删→SET NULL）；
stable_id 快照 = 目标删除后的身份/类型/展示凭证。删除 stable_id 快照会导致
"SET NULL 后无法知道曾经指向哪个类型的目标"；删除 live FK 则退化为 TD-04 式裸多态。
二者各司其职。

**不含**：来源正文、绝对路径、integrity_checked_at、provider/运行时元数据、
来源版本号（fingerprint_version + target_revision 已覆盖）。

## 11. 来源删除策略（冻结：SET NULL + 快照保留）

| 准则 | SET NULL + 快照（选定） | CASCADE 删行 |
| --- | --- | --- |
| ADR-011 §3.2 合规 | **合规**（"保留曾引用何 stable-id 的最小快照并显示 missing"是 ADR 明文要求） | **违规**（行消失=快照消失，无从显示 missing） |
| 派生 EXISTING_SOURCE_SUPPORTED | 目标 FK 变 NULL → 该关联从"有效支撑"降级为"missing"派生态，块回落持久 origin——诚实 | 支撑声明无声消失（看似从未存在）——不诚实 |
| 逻辑孤儿 | 无（FK=NULL，`foreign_key_check` 干净） | 无（但代价是历史丢失） |
| undo/restore | 关联行不受墓碑影响；restore 后 missing 态如实保留 | 同左 |
| 审计/历史 | 快照列 + 命令日志保留"批准过什么" | "批准过什么"丢失 |
| UI | "来源已失效：<target_title>（<stable_id>）" | 无从渲染 |

**"目标被删后 UI 如何知道曾有批准来源？"——由快照列回答**：行还在
（FK 全 NULL + `target_stable_id`/`target_title` 在）→ 派生判定 = missing。
**"FK 变 NULL 后如何安全保留类型/快照？"——由 `target_stable_id` 回答**：
类型编码在 stable_id 内（`<kb_uuid>:<type>:<id>`），无需额外 type 列。

## 12. 来源指纹策略（冻结：复用现行机制，零新哈希）

- **算法/版本**：`src/source_fingerprint.py` v1（`FINGERPRINT_VERSION = 1`），
  前缀化规范渲染 + SHA-256，只读、不回写；
- **逐目标类型**：

| 目标 | 提交时比对物 | 快照列填充 | 无法比对时 |
| --- | --- | --- | --- |
| page | 重算 `compute_source_fingerprint(conn,'page',id)` vs 快照 fingerprint | fingerprint=现算值；version=1 | 行缺失或无文本层（返回 None）→ **fail-closed**：草稿期不得出快照，提交期遇 None → `SourceReferenceInvalid` |
| evidence | 同上（'evidence'） | 同上 | 同上 |
| knowledge_object | **不用指纹**（v1 配方不含 KO，**不发明新配方**）；改比对 `current_revision`：`SELECT current_revision FROM knowledge_objects WHERE id=?` vs 快照 `target_revision` | fingerprint=NULL；fingerprint_version=NULL；target_revision=当时值 | 行缺失 → SourceReferenceInvalid；revision 不等 → SourceReferenceInvalid（陈旧） |
| （document/note/memory） | 不在目标枚举内 | — | — |

- **fingerprint_version 错配**：未来配方升级（v2）时，快照 v1 与运行时 v2 不可比 →
  fail-closed `SourceReferenceInvalid`（如实"无法校验"，不猜测相等）；
- **对批准哈希的影响**：fingerprint/fingerprint_version/target_revision 全部参与
  批准哈希（§10.3）——用户批准的是"对该内容快照的支撑声明"；
- 用户断言/直接观察块所附的**可选上下文引用**（非支撑声明）：**仅存在性校验**
  （上游已冻结）。schema 层面两类引用同表同构，差异只在**提交校验行为**
  （支撑关联做指纹/revision 比对，上下文引用不做）——由命令载荷中的
  support/context 语义标记区分（载荷结构归任务 B），schema 无需区分列。

## 13. 派生 EXISTING_SOURCE_SUPPORTED 的判定规则（冻结）

```
block B 的支撑态 =
  - 若 ∃ 关联行 r ∈ knowledge_memory_sources(r.block_key = B)
        且 r 的 typed FK 至少一个非 NULL   → EXISTING_SOURCE_SUPPORTED
  - 若 ∃ 关联行但全部 typed FK 为 NULL      → MISSING（"曾引用：target_title（已失效）"）
  - 若无关联行                              → 落回 B 的持久 origin 标签
```

- 派生态**永不回写**任何表（每次渲染时计算，沿 ADR-009 "读时点观测"同构思想）；
- 支撑声明**永不把** `agent_inferred` 静默洗白：origin 行与支撑态**并列展示**
  （"AI 推断 · 有来源支持"），持久 origin 不因关联存在而改变（上游 ADR-011 §2 明文）。

## 14. 墓碑生命周期（冻结）

## 16. `experience_command_log` — 角色（冻结）

一表两职：持久幂等 + 成功变异审计。**SUCCESS-ONLY**：只存在"已提交成功"的行；
失败/回滚尝试零库内痕迹（仅净化应用日志）——失败矩阵 #10 与 ADR-011 §3.3 的
"不在数据库伪造已提交审计行"。append-only。行即"提交标记"（与经验写入同事务，
§25）。

## 18. 幂等键规格（冻结）

- **生成者**：UI 在命令首次构造时生成 `uuid.uuid4()` 字符串（36 字符小写连字符）；
- **格式**：服务层校验 UUID 语法；DB 层只做 `length BETWEEN 16 AND 64`（容纳未来
  同类不透明格式）与 UNIQUE；
- **大小写**：按生成值原样存储、区分大小写（UUID 恒小写；无规范化步骤=无不一致面）；
- **持久性**：重试（确认框/按钮重发/超时重试）复用同键；新用户手势 = 新键；
  空值禁止（服务层 + 长度 CHECK 双层）；
- **它不是**：授权（授权=会话批准）、载荷哈希（负载比较用 payload_sha256）、
  内容身份（同内容两次保存=两个键=两条经验——**已核实为正确语义**：内容哈希不能
  做幂等权威，否则"撤销后重新保存相同内容"或"两会话各存一份相同草稿"会被错误
  合并；且 undo/restore 无内容可言）；
- **键复用防护**：同键 + 不同 (operation, payload_sha256) 任一不同 →
  `IdempotencyConflict`，fail-closed。

## 19. result 列裁决（§27 选型）

**选 B：`result TEXT NOT NULL DEFAULT 'committed' CHECK (result = 'committed')`。**

- A（无列）与 B 语义等价，但 B 自文档化（schema 自述 SUCCESS-ONLY 不变量）、
  与 `ai_calls.status` 闭合枚举风格一致、为未来扩展留出无需语义重释的演进位
  （扩展时随迁移改 CHECK）；
- C（按操作细分结果值）被拒：SUCCESS-ONLY 下无第二态可分，纯臆测；
- **绝不存储伪失败态**（成功日志纪律，§16）。

## 20. payload_sha256 与 approved_draft_sha256（冻结）

- **create**：两列**必然相等**（提交前置条件即 `canonical_hash(payload) ==
  approved_draft_sha256`，§25 步骤 4）——保留两列是显式审计语义（"批准哈希原样
  留档"）+ ADR-011 字面 conformant + 跨列 CHECK 免费钉住相等性；若未来出现
  提交载荷≠批准载荷的新操作类型，随迁移放宽 CHECK；
- **undo / restore**：`payload_sha256` = 该命令自身规范载荷的哈希
  （规范序列化 = `{operation, target_stable_id}` 确定性序列化，具体序列化器归任务 B，
  与 create 的载荷序列化器同一实现框架）；`approved_draft_sha256 = NULL`
  （undo/restore 无草稿批准语义；授权=会话内用户点击 + create 日志资格）；
- payload_sha256 **永远存在**（三操作皆然）——它是幂等重放的比对键。

## 21. 目标标识（冻结：快照，不带 FK）

`target_stable_id TEXT NOT NULL`，**不**加 `REFERENCES knowledge_memory_entries`。

**理由（逐条）**：
1. **FK RESTRICT 会破坏既有能力**：经验条目被既有人类 `delete_entry` 硬删时，
   命令日志的 create 行会阻止删除（RESTRICT）或被连带清除（CASCADE=销毁审计史）——
   两者都不可接受；快照零耦合；
2. **重放健壮性**：目标被硬删后同键重放仍能返回文本化历史结果
   （"该记录曾保存于此 stable_id，现已被删除"级别的诚实呈现归 UI，日志行恒可答）；
3. **资格判定查询**按 stable_id 等值（§28）——无需 FK；
4. 备份/恢复透明（纯文本列随库迁移）；
5. 用户可见身份就是 stable_id（命令结果/UI 跳转一律 stable_id，不暴露内部自增 id
   ——沿 ADR-010"不暴露内部 DB id"）。

受控 v0.7 用软删，条目行通常存在；快照设计在硬删情形下仍语义自洽。

## 22. actor 列（冻结：保留，恒值）

保留 `actor TEXT NOT NULL DEFAULT 'local_user' CHECK (actor = 'local_user')`：
①ADR-011 概念字段字面 conformant，零成本；②单用户下由系统构造保证（服务硬编码，
UI/载荷不可注入）；③未来多用户/授权语义属于未来 schema 迁移，届时改 CHECK 即可，
本表结构无需变化。**不发明任何用户/身份基础设施**（AGENTS.md 产品边界）。

## 23. append-only 执行机制（冻结）

**选型：应用纪律 + 受限仓储 API + 测试/release_check 断言。不加 SQLite guard 触发器。**

- 先例 = `ai_calls`/`ai_outputs`：全 `src/` 无 UPDATE/DELETE 语句、无 guard 触发器、
  仅 insert 方法（§3.4 grep 复核）——仓库对 append-only 的既定执行方式就是
  "insert-only API + 无暴露变异方法"；
- guard 触发器（RAISE(ABORT) ON UPDATE/DELETE）被拒：①仓库无先例（新增机制类别
  = 新维护面）；②本表无 UPDATE/DELETE 代码路径，触发器防御的是不存在的调用者；
  ③迁移面扩大（触发器随表重建逻辑互动）；
- 具体冻结：`experience_command_log` 只获得一个 `insert_experience_command_log(...)`
  低层方法（连接感知）；**不提供**任何 update/delete 方法；focused 测试断言
  append-only 语义（写入→尝试 UPDATE/DELETE→行为=无方法可调 + release_check
  静态断言）；release_check 增补"命令日志表存在 + 无变异 API"探针（§48）。

## 24. 索引（冻结，3 个）

| 索引 | 支撑的查询 | 现在需要的理由 |
| --- | --- | --- |
| UNIQUE(idempotency_key) | 幂等解析（同键查找/冲突检测） | 每次命令执行必经；兼防重 |
| `idx_ecl_target(target_stable_id)` | undo/restore 资格（EXISTS create 行）、按目标历史 | 每次 undo/restore 必经（§28） |
| `idx_ecl_created(created_at)` | 审计时间序浏览、first_committed_at 展示 | `ai_calls` 同款先例 |

不建 operation/actor/creation_origin 索引（无当前查询；避免臆测索引）。

## 25. 事务所有权与三个事务的精确顺序（冻结）

**所有权**：`ExperienceWriteCommandService` 拥有**唯一**外层 `knowledge_transaction`
（BEGIN IMMEDIATE + 异常整体回滚，`src/database.py:1643`）。事务体内**只允许**连接感知
调用（§26）；**禁止**调用自开事务的方法（`create_knowledge_memory_entry`/`update_...
status` 的**无参形态**、一切 `_connection()` 直开方法）——嵌套 BEGIN IMMEDIATE 会
直接抛 "cannot start a transaction within a transaction"，此为结构性约束。

### 25.1 CREATE（顺序冻结；幂等解析在批准校验**之前**）

```
1.  BEGIN IMMEDIATE
2.  幂等解析：SELECT * FROM experience_command_log WHERE idempotency_key = ?
3.  ├─ 有行 且 operation='create' 且 payload_sha256 相同
    │    → 返回记录结果(target_stable_id, created_at) + duplicate_replay=true
    │      【不要求会话批准——日志行即既往授权的持久证明】；COMMIT（空事务）；结束
    ├─ 有行 且 (operation 或 payload_sha256 任一不同)
    │    → ROLLBACK；IdempotencyConflict（与批准状态无关）
    └─ 无行（新键）→ 继续
4.  批准校验：批准令牌在场（否则 ApprovalMissing）；
    重算 canonical_hash(payload) == approved_draft_sha256（否则 ApprovalMismatch）
5.  域校验：title/outcome 必填、各块长度、10 块齐性、origin 枚举、
    root_cause_user_confirmed 一致性（=1 ⇒ root_cause 非空 + origin 行 user_asserted）
6.  来源校验（逐引用）：parse stable_id → 目标行 SELECT；
    缺失 → SourceReferenceInvalid；支撑关联 → 指纹/revision 比对（§12），
    错配 → SourceReferenceInvalid；上下文引用 → 仅存在性
7.  连接感知 INSERT 经验行（status='active'，creation_origin，
    root_cause_user_confirmed，agent_request_ref，content=规范区块序列化，
    四影子列同步写入）——FTS insert 触发器自动生效（同事务）
8.  连接感知 INSERT ×10 provenance 行
9.  连接感知 INSERT ×N source 关联行（提交前逐行"至多一目标"由域校验已保证）
10. build_stable_id(新行 id) → 连接感知 INSERT 命令日志行（create）
11. COMMIT
```

失败于 4-10 任一步 → 整体回滚 → 经验/来源/provenance/FTS/日志零残留 →
用户见"保存失败，未写入任何数据"（失败矩阵 #10/#14/#15），同键重试 = 步骤 2 无行 =
正常首写（成功日志纪律）。

### 25.2 UNDO

```
1.  BEGIN IMMEDIATE
2.  幂等解析（op='undo'，payload=规范{operation,target_stable_id}哈希）
    ├─ 同键同载荷 → 重放（不要求批准）；COMMIT；结束
    └─ 冲突 → IdempotencyConflict
3.  目标解析：target_stable_id → parse → SELECT entry；不存在 → typed 目标失效错误
4.  资格：EXISTS(create 日志行, target_stable_id)（否则 typed 拒绝——非命令链条目）
5.  状态校验：status 必须 = 'active'（否则 typed 状态冲突）
6.  连接感知 UPDATE status: active → deleted（update_knowledge_memory_status 变体；
    FTS update 触发器自动重同步索引——内容不变，可见性由检索 status 过滤承担，§17）
7.  连接感知 INSERT 命令日志行（undo；approved NULL；creation_origin NULL）
8.  COMMIT
```

**不删内容、不删来源链接、不碰 provenance、不 hard purge。**

### 25.3 RESTORE

```
1.  BEGIN IMMEDIATE
2.  幂等解析（op='restore'；同键同载荷 → 重放）
3.  目标解析（须存在；硬删后 → typed 目标失效错误）
4.  资格：EXISTS(create 日志行)
5.  状态校验：status 必须 = 'deleted'（否则 typed 状态冲突）
6.  连接感知 UPDATE status: deleted → active（FTS 触发器自动；恢复可检索）
7.  连接感知 INSERT 命令日志行（restore）
8.  COMMIT
```

provenance/来源链接/内容**零改写**——墓碑期间它们原样保留。

## 26. 连接注入（N-4 — 精确模式冻结）

**选型 A：既有方法加可选 `connection` 参数，经既有 `_knowledge_scope(connection)`
helper 生效。**（拒绝 B 私有变体=逻辑双份；C 已存在即 `_knowledge_scope` 本身。）

- **方法**：`create_knowledge_memory_entry`、`update_knowledge_memory_status`
  两个签名各追加 `connection: sqlite3.Connection | None = None`（置于参数表末尾）；
- **机制**：方法体内 `with self._connection() as conn:` 改为
  `with self._knowledge_scope(connection) as conn:`（`src/database.py:1660` 既有
  helper；connection 非 None → nullcontext 直用，**不发 BEGIN**；None → 现行为逐字
  不变）；约 11 个知识域方法已是此模式（先例充分）；
- **FTS 语义**：create 变体内的影子列写入与 INSERT 语句**逐字保留**——
  连接感知不改变触发器行为（触发器在行级触发，与事务归属无关）；
- **既有调用方兼容**：默认 None → 全部既有调用点零改动；
- **不做**：公共事务框架、context manager 泄漏、对 `update_knowledge_memory_entry`
  （v0.7 命令不用它）加参数。

## 27. 迁移策略（单事务表重建，沿 v10-v12 纪律）

**函数**：`_apply_version_target(connection)`；钩子变量
`_V13_INJECTION_POINT`（物理名随 G-1）；前置指纹沿 `_v12_data_fingerprint` 扩展

## 28. undo 资格判定（冻结）

- **查询**：`SELECT 1 FROM experience_command_log
    WHERE operation='create' AND target_stable_id = ? LIMIT 1`；
  索引 `idx_ecl_target` 支撑（§24）；
- **无 create 行**（人类创建的任意 kind 条目、或历史缺失）→ typed 拒绝
  （"该条目不在可撤销范围内"）——**无** `controlled_write_created` 列（资格完全
  可从日志导出，加列即双份真相）；
- **历史损坏/缺失**：fail-closed（查不到 create 行 = 不可撤销）——诚实且安全，
  不做任何重建/推断；
- restore 资格同查询 + 当前 status='deleted'。

## 29. 既有行回填（冻结，逐字段）

| provenance 行 | **不回填**（0 行） | 4 值 origin 枚举无一可诚实描述"历史条目的区块来源"（标 user_asserted 会把来源粘贴内容冒充用户断言；标 agent_* 是虚假）。**缺席即保守未知**：读路径对无 provenance 行的条目渲染"未标注来源（历史条目）"并禁用来源支撑派生态。缺席=未知是**显式保守表示**（ADR-011 §3.1 要求），且不改动已冻结的 4 值枚举——无 UNKNOWN 值，无门禁冲击 |

## 30. FTS 迁移安全（冻结）

- **拷贝保 id**：INSERT...SELECT 保留 id → rowid 稳定 → 'rebuild' 后索引内容与
  升级前逐条目等价；
- **影子列复制不重算**：`_tokenize_for_fts` 是确定性纯函数，但复制避免对
  tokenizer 实现演化的任何依赖漂移；
- **触发器重建逐字 v11 SQL**；外部内容表按名 `content='knowledge_memory_entries'`
  重挂（RENAME 后名字匹配）；
- **DROP 表与 FTS 的互动**：v10 重建时 FTS 尚不存在（v11 才建），本次是仓库首次
  在 FTS 存活下重建内容表——规格钉死顺序：DROP（触发器随表消亡，FTS 失配但仍在）
  → RENAME → 重建触发器 → **必须** 'rebuild'（否则 FTS 索引与新表脱钩，
  MATCH 查询结果未定义）；
- **升级后检查**（迁移内 + 迁移测试双保险）：
  `SELECT COUNT(*) FROM knowledge_memory_search` ==
  `SELECT COUNT(*) FROM knowledge_memory_entries`；
  既有检索冒烟（升级前记录某查询命中 id 集，升级后同查询命中集相等）；
  `PRAGMA integrity_check` ok；status 过滤行为不变（active 命中、archived 按
  include_archived、deleted 永不命中）。

## 31. 墓碑与 FTS（§37 裁决：方案 A）

**冻结：方案 A —— FTS 内容保持索引，可见性由 status JOIN 过滤承担。**

- 现行 UPDATE 触发器**无视 status**：active→deleted 的 UPDATE 会重同步索引
  （delete+insert 同文本）——文本未变，索引内容等价；
- 检索层过滤已天然排除 deleted（§3.2）；无任何 MATCH 路径绕过该过滤（唯一
  消费者 `search_knowledge` 硬编码过滤列表）；
- **隐私评估**：墓碑行本身保留内容（ADR-011 §5 设计使然——可恢复），因此 FTS
  保留同一文本**不引入任何新暴露面**（同一 DB 文件、同一读取边界）；
- **性能**：墓碑量级=用户撤销次数（个位数~十位数），空转索引成本可忽略；
- **restore**：deleted→active 后检索立即可见（过滤翻转），零重建；
- 方案 B（物理摘除 FTS 文本）被拒：需按 status 分支的触发器逻辑（复杂、易错）、
  与"restore 原样恢复"冲突（文本被摘除后 restore 无法凭索引恢复），零隐私收益。

## 32. 迁移幂等性与崩溃恢复（冻结）

- **DDL 原子性**：SQLite 事务性 DDL——CREATE/DROP/RENAME 在 `BEGIN IMMEDIATE`
  内，任一步异常整体回滚；进程崩溃 → WAL 日志恢复 → 库停回 v12 原状 →
  下次启动 `migrate_database` 重跑（版本读取 `MAX(schema_migrations.version)`，
  版本记录与 DDL 同事务 ⇒ 不存在"半升级"版本态）；
- **迁移前备份**：runner 对需升级库先 `backup_database`（backup API + integrity
  验证），失败回滚后原库与备份俱在（现有测试 `test_failed_migration_rolls_back_
  and_keeps_backup` 模式沿用）；
- **重入安全**：版本已 = TARGET 的库 → runner no-op（不备份、不执行）；
  注入测试模式：parametrize 全部 v13 注入点 → 断言版本回 v12、原始快照逐字节相等、
  新表/新触发器不存在、integrity/fk_check 干净、清除注入后重跑成功
  （`tests/test_schema11_knowledge_fts.py:534` 先例逐条复刻）；
- **验证防线**：指纹 before/after + 拷贝计数 + FTS 计数 + integrity + fk_check
  （§30/§41）。

## 33. 备份/恢复（冻结）

- **参与性**：`_sqlite_snapshot` = SQLite backup API 全库复制 → 四新表自动入备份，
  零改动；
- **健康校验**：`_require_healthy_database` 校验 schema_version 相等——升级后备份
  记录 v13；恢复旧 v12 备份后启动应用走既有 migrate 链再次升级（现有行为，无新逻辑）；
- **测试矩阵**：v12 备份→升级→受控写（create/undo/provenance/sources/日志）→备份→
  恢复→逐表行数/内容相等→同键重放语义→墓碑在恢复后仍为墓碑→快照列逐字节相等；
- **"恢复到早于某次成功命令的备份点"语义（冻结）**：那是**历史数据库回卷**——
  命令日志随库回到不含该命令的状态，应用对该命令零知识；同键重试 = 首写（经验亦
  不存在，语义自洽）。**不做跨备份去重、不做命令重放进恢复**（会伪造从未发生过的
  历史）；失败矩阵 #17 的"重放原结果或如实条目已不存在"两分支由"恢复点早/晚于
  提交"自然覆盖。
