# EKB v0.6.0 — Agent Foundation (Release Notes)

- Status: v0.6.0 release candidate; published as the GitHub Release `v0.6.0` body at release time.
- Positioning: on top of the v0.5.3 audited AI integration, establishes the Agent Foundation and
  the hosted deployment foundation.
- Release window: 2026-08-29 ~ 2026-08-30 (maintainer target; the actual release date governs).

## Overview

v0.6.0 introduces a local single-step read-only Agent and a controlled HTTP service entry point,
laying the groundwork for the future personal-experience Agent. Within one request the Agent may
make one decision, call at most one read-only tool and produce one final answer; write
capabilities, multi-step loops and autonomous retries are excluded by construction. The public
HTTP contract is frozen, errors use a closed message catalog, and internal objects never leak.

**Public deployment scope change (2026-08-28 maintainer decision):** the original v0.6.0 plan
required actual public deployment before release. The maintainer has changed the release
criterion, deferring actual public exposure out of the v0.6.0 release gate (DEFERRED). This is a
release-scope decision, not a deployment acceptance result: WP6A remains PARTIAL / PAUSED, WP6B
remains NOT STARTED, and this release neither includes nor claims any public deployment.

## Highlights

- Single-step read-only Agent: Decision → 0/1 Tool → Final Answer, no loops, no autonomous retries;
- 7 READ_ONLY tools covering page search, knowledge search, object/memory reads, provenance and
  source-integrity inspection;
- Final Answer generated only from Tool evidence with fail-closed citation validation;
- Source integrity semantics: valid / changed / missing / unknown; stale sources never silently
  act as reliable facts;
- Hosted HTTP Agent API (/health, /ready, /v0.6/agent/run, /v0.6/sources) with frozen public DTOs;
- Hosted security boundary: rate and concurrency limits, request body cap, exact CORS origins,
  budget rejection, error sanitization;
- Hosted SQLite storage safety: exact schema-v12 validation, symlink/sidecar rejection;
- Linux container and non-root (UID/GID 10001) packaging;
- Without an API Key every offline core feature keeps working; the local endpoint is unchanged.

## Agent Foundation

```text
user request → AgentRequest
             → Decision (≤1 structured decision)
             → 0/1 READ_ONLY Tool (registry policy enforces read-only)
             → Final Answer Stage (rag_answer, not a Tool)
             → citation validation (fail-closed) → AgentResponse
```

- Agent-autonomous retries = 0; citation repair retries = 0; no planning, loops or agent loops.
- Decision, tool and final answer are each capped at 1; at most two logical model calls in total.
- The runtime trace lives in process memory only: no database rows, files, logs or responses.
- The 7 READ_ONLY tools: `page_search`, `knowledge_search`, `get_knowledge_object`,
  `get_knowledge_memory`, `inspect_provenance`, `inspect_source_integrity`, `get_evidence`.
- The registry admits READ_ONLY tools only; unknown, disallowed or non-read-only tools fail closed.
- `rag_answer` is the Final Answer Stage, not a Tool: the final answer is generated only from Tool
  evidence and a KnowledgeContextPackage; with no evidence it honestly reports that nothing
  supports the question and fabricates neither answers nor citations.
- Citation validation reuses the v0.5.3 runtime validation: unknown, forged, out-of-range and
  empty citations fail closed.

## Source Integrity

- `inspect_source_integrity` reads already-captured fingerprint states only; it never refreshes,
  recomputes or writes.
- `changed` means the source snapshot disagrees with the recorded fingerprint and `unknown` means
  confirmation was not possible; neither implies fabrication, and neither triggers any repair.
- Read paths perform no hidden writes; fingerprint recapture remains an explicit manual operation.

## Hosted Deployment Foundation (WP1–WP5)

- WP1 Runtime Profile: a distinct hosted runtime profile; mixing with or falling back to the Local
  runtime is prohibited.
- WP2 HTTP Agent API: `/health`, `/ready`, `POST /v0.6/agent/run`, `GET /v0.6/sources/{stable_id}`;
  frozen public DTOs (`AgentRunResponse`, `SourceResponse`, `HTTPFailure`); closed error message
  catalog; internal traces, ToolResults, token usage and raw model responses are never exposed.
- WP3 Security boundary: rate and concurrency limits, request body cap, exact CORS origins, budget
  rejection, empty trusted-proxy default; errors are sanitized and keys never enter logs,
  responses or test snapshots.
- WP4 Storage safety: independent hosted SQLite bootstrap, exact schema-v12 validation, symlink
  and sidecar rejection; the Local production database is never read or written.
- WP5 Deployment packaging: Linux container and non-root (UID/GID 10001) runtime packaging with
  passing integration tests; actual cloud deployment validation remains PAUSED.

## Public Deployment Status (DEFERRED)

- WP6A = PARTIAL / PAUSED; WP6B = NOT STARTED; Public Agent exposed = NO.
- Actual public exposure is deferred out of the v0.6.0 release gate (2026-08-28 maintainer
  scope decision).
- This release contains no public deployment, cloud credentials or public corpus upload; resuming
  deployment follows the existing pause records and the anchors in
  `docs/v0.6.0-release-closure-inventory.md` §8 and requires an explicit maintainer decision.
- The hosted HTTP service remains usable in local/controlled environments for development and
  verification; a 200 from `/ready` does not prove that the AI key is valid or that model calls
  succeed.

## Data and Schema Compatibility

- The application version advances to 0.6.0; the database stays at **schema v12** with no new
  migration.
- v0.5.x user data needs no conversion; upgrading only changes the displayed version and adds
  capabilities.
- Official restore still accepts only complete backups compatible with the current version and
  schema v12.

## Offline Behavior

- AI defaults to manual mode (`ai_mode="manual"`); without an API Key the application starts and
  every offline core feature (import, search, reading, notes, evidence, deletion/recovery,
  backup) remains fully available.
- The Agent changes no existing local workflow; unavailability of Agent services without AI
  configuration is expected behavior, not a regression.

## Security and Privacy Boundaries

- The Agent has no write capability; it cannot modify, delete or overwrite user materials or
  knowledge assets.
- The HTTP layer never exposes internal traces, ToolResults, Decision objects, token usage,
  provider responses, filesystem paths or internal database primary keys.
- API keys are read from server-side environment variables only; they never reach a browser,
  log, backup or test snapshot.
- No registration, login, accounts, multi-user roles or cloud sync; the official Local service
  binds to `127.0.0.1:8501` only.

## Upgrade Notes

- From v0.5.3: no schema change and no data migration; adopt this version directly.
- From earlier versions: complete the v0.5.x migration and backup path first, then upgrade.
- Local startup is unchanged: `启动工程知识库.bat` or the existing service management; the hosted
  entry point is a distinct runtime profile requiring explicit configuration and is disabled by
  default.
