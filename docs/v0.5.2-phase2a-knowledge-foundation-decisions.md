## 0. 绑定输入（外部审核者强制裁决，不变）

1. 不接受按 kind 直接决定 reviewed：内容类别、形成方式、用户确认、证据状态、
   生命周期必须是不同维度。
2. 来源 freshness 属于 v0.5.2：来源存在 ≠ 来源内容未变；来源变化不能静默保持
   “证据仍有效”；KO 不得弱于 Evidence Object 的来源可信边界；来源变化后必须
   可观察、可解释、可重新确认。
3. 知识替代与演进属于 v0.5.2：可保留旧知识、新知识可明确替代旧知识、不静默覆盖、
   可见修改前后历史、区分 active/superseded/archived。自动判断过时属 v0.6.x。
4. Memory 与 Revision/Event 不长期共表。
5. 离线检索闭环必须成立；Revision 默认不混入普通知识搜索；结果可回源；不依赖
   embedding/API Key/外部调用。
6. 结构化导出属于 v0.5.2；排除 API Key、凭据、embedding、私人运行日志。
7. v8 备份采用隔离升级方向；正式恢复器保持 schema 精确匹配与 fail-closed；
   不覆盖原备份；最终 schema 不写死为 v9/v10。

## 3. ADR-01：知识语义正交模型（R1 修订）

### Context

R1 前草案的 `origin ∈ {user_recorded, distilled_from_source, personal_experience,
user_judgment, ai_inferred}` 不互斥（personal experience 也是 user recorded；
judgment 也是 user recorded；source distillation 最终也由用户记录）。且
`kind=experience` 与 `origin=personal_experience`、`kind=decision` 与决策 origin 重叠。

### 方案比较

**方案 A：Authorship 与 Epistemic Basis 分开（采纳）**

- `authorship ∈ {user, ai}`：谁对最终内容负责。v0.5.2 服务层只允许 `user` 写入；
  `ai` 保留为未来兼容值（CHECK 枚举现在就包含，避免未来重建表）。
- `epistemic_basis ∈ {source_derived, personal_experience, personal_judgment,
  direct_observation, decision_record, problem_definition, unknown_legacy}`：
  内容形成/证成依据，七值互斥、无重叠。

**方案 B：单一互斥 Provenance Type**
移除宽泛的 user_recorded，直接用一个七值枚举同时表达“谁写的”和“凭什么写的”。
- 缺点：authorship 与 epistemic basis 是两个正交问题，单枚举无法表达“AI 推断但
  以来源为依据”（ai + source_derived）这类组合；且未来 AI 写入时仍需拆列。
  拒绝。

### Decision（R1 冻结）

1. 采用方案 A：`authorship` + `epistemic_basis` 两列替换原 `origin` 单列。
2. `kind` 保持六值内容类别（concept/fact/principle/experience/problem/decision），
   `problem` 定义为“问题定义”内容类别，工作流状态由 `lifecycle` 承担；`judgment`
   不作为 kind（由 `epistemic_basis=personal_judgment` 表达）。
3. `epistemic_basis` 与来源链接解耦：**是否有 Source Link 不推导 basis**；
   `source_derived` 是用户声明，不是“有链接”的自动结果。同时有来源与个人判断的
   内容，basis 仍是 `personal_judgment`，来源作为证据链接独立存在。
4. `ai_inferred` 语义由 `authorship='ai'` 承担；v0.5.2 服务层拒绝一切
   `authorship='ai'` 的写入；AI 输出不得自动成为用户确认事实（与 ADR-02 联动）。

### 12 场景映射矩阵（R1 冻结，每场景唯一结果）

| # | 场景 | authorship | epistemic_basis | 说明 |
|---|---|---|---|---|
| 1 | 从芯片手册提炼的事实 | user | source_derived | 依据外部资料 |
| 2 | 用户自己的调试经验 | user | personal_experience | 亲历实践 |
| 3 | 根据多个来源形成的判断 | user | personal_judgment | 判断是综合行为；来源可作为证据链接 |
| 4 | 记录的一次项目决策 | user | decision_record | 内容即决策记录 |
| 5 | 无来源的问题定义 | user | problem_definition | 内容即问题识别 |
| 6 | 直接观察到的现象 | user | direct_observation | 感官/事实观察 |
| 7 | 从证据对象总结的原则 | user | source_derived | 证据对象属于外部来源 |
| 8 | 用户原创概念 | user | personal_judgment | 思维构造 |
| 9 | 未来 AI 推断但未确认 | ai | （按 AI 依据，如 source_derived） | v0.5.2 禁止写入；确认必为 unconfirmed |
| 10 | AI 草稿被用户修改确认 | user | （沿用草稿 basis，如 source_derived） | 用户修改并确认即承担责任；revision 注明“源自 AI 草稿” |
| 11 | 旧 v9 迁移且无法判断 | user | unknown_legacy | 不推测，统一保守回填 |
| 12 | 同时含来源和个人判断 | user | personal_judgment | 来源为证据链接，不改变 basis |

### Consequences

- 两列替代一列，语义互斥；每个对象恰好一个 (authorship, epistemic_basis)。
- UI 展示两枚独立徽标：作者（用户/AI）与依据（七选一）。
- 提示词包输出两字段，诚实区分“用户判断”与“来源提炼”。

### Migration impact（Phase 2B）

- `knowledge_objects` 重建：删除 `origin`（R1 前草案未落地，实际 v9 无此列）；
  新增 `authorship`/`epistemic_basis`。
- v9 → v10 回填：所有旧对象 `authorship='user'`、`epistemic_basis='unknown_legacy'`
  （不按来源/kind 推测，避免虚构）。用户可事后编辑。

### Compatibility impact

- v9 无 origin 概念，纯新增两列，旧数据保守映射。

### Test obligations

- 两列 CHECK 约束拒绝非法枚举。
- 12 场景映射表作为参数化测试（服务层场景构造断言）。
- `authorship='ai'` 在 v0.5.2 服务层被拒（负向）。
- 有来源 + personal_judgment 不被自动改写为 source_derived。

### Human acceptance

- 真人理解“作者（谁负责）”与“依据（凭什么）”两枚徽标（H7 修订）。

### Deferred items

- `authorship='ai'` 写入路径 → v0.6.x。
- `judgment` 独立 content kind → v0.6.x 再议。

### Rejected shortcuts

- 单一 `origin` 重叠枚举（R1 前草案）——被本 ADR 替换。
- 用“是否有来源链接”推导 epistemic_basis——拒绝（场景 12 反例）。
- 对旧数据按 kind/来源推测 basis——拒绝（无法判断则 unknown_legacy）。

## 4. ADR-02：用户确认与外部证据分离（R1 修订）

### Decision

1. `confirmation_status ∈ {unconfirmed, confirmed}`（仅两值，落库）。
2. `confirmed_at`：最近一次确认时间（UTC ISO 8601）。
3. `current_revision`：对象当前修订号（每对象从 1 单调递增）。
4. `confirmed_revision`：确认绑定的修订号；unconfirmed 时为 NULL。
5. 派生显示状态（计算，不落库）：
   - `unconfirmed` → “未确认”；
   - confirmed 且 `confirmed_revision == current_revision` → “已确认（当前第 N 版）”；
   - confirmed 且 `confirmed_revision < current_revision` → “确认基于旧版（第 C 版，
     当前第 N 版），需重新确认”。
6. 正文修改：`current_revision += 1`，写 `content_updated` revision；**不自动撤销
   确认**（保留“用户确认过第 C 版”这一历史事实），显示状态转为“旧版确认”。
7. 来源变化：**不自动撤销用户确认**。确认绑定内容修订，来源状态独立显示（ADR-03）。
   来源变化只改变来源状态与“外部证据充分性”，不触碰 confirmation 字段。
8. 无来源个人知识：可以确认（confirmation 与来源无关）；来源状态显示 UNSOURCED。
9. 读路径不写库：确认/修订号/生命周期只在用户显式操作时变更。
10. 单用户系统：不设 `confirmed_by`（结构上必然是本地用户）。

### v9 → v10 legacy migration（R1 重点修订）

**为每个 v9 对象 O 生成两类 Revision：**

1. `legacy_event`（旧 `knowledge_change` 日志搬迁）：
   - 取 O 在 v9 的全部 `knowledge_change` 行，按 `created_at ASC, id ASC` 排序，
     编号 `1..n`；
   - 每行 → revision：`event_type='legacy_event'`、`object_*_snapshot` 取迁移时可
     确定值（对象已删的孤儿行：local/stable id 为 NULL，title 从日志标题
     “知识创建：X”解析）、`before_*`/`after_*` 全部 NULL（**不虚构历史**）、
     `detail` 存旧日志原文、`created_at` 取旧行时间；
   - 旧日志标题前缀→说明映射仅写入 `detail` 供阅读，**不伪装成正式事件类型**。
2. `legacy_baseline`（迁移时点完整内容基线）：
   - 编号 `n+1`，`event_type='legacy_baseline'`，`after_content=O.content`（迁移时
     当前内容）、`after_title=O.title`、`after_lifecycle`/`after_confirmation` 为
     推导值、`before_*` 全部 NULL、`created_at` = 迁移时间戳、
     `detail='迁移基线：v9→v10 迁移时点完整内容快照'`。
3. 编号与绑定：
   - `current_revision = n+1`（baseline 是最新修订）；
   - 旧 `status='reviewed'` → `confirmation_status='confirmed'`、
     `confirmed_at=旧 reviewed_at`、`confirmed_revision = n+1`（**确认绑定 baseline**，
     即迁移时用户所确认的完整内容）；
   - 旧 `status='draft'` → unconfirmed、confirmed_at=NULL、confirmed_revision=NULL；
   - 旧 `status='archived'` → lifecycle=archived、unconfirmed（v9 归档已清空
     reviewed_at，保守不宣称确认）。
4. 无旧日志的对象：baseline 编号 1，`current_revision=1`；reviewed 绑 1。
5. **历史精度边界（正式声明）**：v10 之前的历史不可逐字重建；`legacy_event` 无
   before/after，`legacy_baseline` 是迁移时点快照而非真实历史事件；只有 v10 之后
   写入的 Revision 具备完整 before/after。UI 在对象历史中必须显示该边界提示。

### Alternatives（R1 比较）

- “reviewed → confirmed_revision=1”的机械映射（R1 前草案）：使确认绑定编号 1，
  若存在旧日志，编号 1 是旧日志而非迁移时内容，确认对象不明确。拒绝。
- 只生成 baseline、不搬迁旧日志：丢失可读历史。拒绝。
- 把旧日志伪装成拥有 before/after 的正式 revision：虚构历史。拒绝。

### Consequences / Compatibility / Test obligations

- 迁移后每个对象至少 1 条 revision；旧日志行数不丢失（逐行核验）。
- 测试：非空 v9 库迁移后 `legacy_event` 行数 == 旧 knowledge_change 行数；
  baseline 内容 == 迁移时对象内容；reviewed 绑 baseline；孤儿日志不炸。
- 兼容：v9 的 `reviewed_at` 语义迁移为“确认迁移基线”。

### Human acceptance / Deferred / Rejected

- 真人理解“确认基于旧版”提示（H9）；对象历史页看到精度边界。
- Deferred：`confirmed_by`（多角色才需要）；批量重新确认 → v0.6.x。
- Rejected：自动撤销确认；用 kind 决定能否确认。

## 5. ADR-03：来源 fingerprint（R1 修订：完整真值表）

### Decision

**单条来源状态（每条 source link 计算其一，读时不落库）**

| 状态 | 条件 |
|---|---|
| `VALID` | 目标存在 且 `source_fingerprint` 非 NULL 且 当前 canonical 指纹 == 存储指纹 |
| `CHANGED` | 目标存在 且 `source_fingerprint` 非 NULL 且 当前 canonical 指纹 ≠ 存储指纹 |
| `MISSING` | 目标行/文件不存在 |
| `UNKNOWN` | `source_fingerprint IS NULL`（仅 legacy 回填失败） |

**对象级聚合状态（读时计算，返回 `(aggregate_state, valid_count, changed_count,
missing_count, unknown_count)` 五元组）**

六条确定性规则（完整覆盖所有组合，无模糊优先级）：

1. 来源总数 = 0 → `UNSOURCED`（四计数全 0）。
2. `valid>0` 且 `changed+missing+unknown == 0` → `VALID`。
3. `valid>0` 且 `changed+missing+unknown > 0` → `PARTIALLY_VALID`。
4. `valid==0` 且 `changed>0` → `CHANGED`（无论 missing/unknown 是否同时存在）。
5. `valid==0` 且 `changed==0` 且 `missing>0` → `MISSING`（无论 unknown）。
6. `valid==0` 且 `changed==0` 且 `missing==0` 且 `unknown>0` → `UNKNOWN`。

|---|---|---|---|---|---|
| 1 | 0 | 0 | 0 | 0 | UNSOURCED |
| 2 | >0 | 0 | 0 | 0 | VALID |
| 3 | >0 | >0 | 0 | 0 | PARTIALLY_VALID |
| 4 | >0 | 0 | >0 | 0 | PARTIALLY_VALID |
| 5 | >0 | 0 | 0 | >0 | PARTIALLY_VALID |
| 6 | >0 | >0 | >0 | 0 | PARTIALLY_VALID |
| 7 | >0 | >0 | 0 | >0 | PARTIALLY_VALID |
| 8 | >0 | 0 | >0 | >0 | PARTIALLY_VALID |

| 10 | 0 | >0 | >0 | >0 | CHANGED |

| 12 | 0 | 0 | 0 | >0 | UNKNOWN |

规则 5/6 覆盖无 valid 无 changed 的剩余组合。）

**UI 文案与建议（每聚合态）**

| aggregate | UI 文案 | 是否可作为外部证据充分 | 是否建议重新确认来源 |
|---|---|---|---|
| UNSOURCED | 无来源 | 否 | 提示可补充来源 |
| VALID | 来源有效（N/N） | 是（若含 evidence 来源，见 ADR-03 evidence 限定） | 否 |
| PARTIALLY_VALID | 来源部分有效（有效 X，变化 Y，缺失 Z，未知 W） | 否（部分） | 是（建议处理非有效项） |
| CHANGED | 来源已变化（X 条） | 否 | 是 |
| MISSING | 来源缺失（X 条） | 否 | 是（建议重新链接） |
| UNKNOWN | 来源状态未知（历史数据） | 否 | 是（建议重新捕获指纹） |

所有 evidence 来源均已确认，见 ADR-03 证据限定）。不落库、不自动改写任何状态。

**读路径只读**：所有来源状态计算仅使用只读查询与内存哈希；禁止在 read 路径写
`last_validated_at` 或任何列。

### 四类 canonical 输入（fingerprint_version=1，sha256，前缀含版本）

| 来源 | canonical 输入 | 明确排除 | 空/不可用行为 |
|---|---|---|---|
| document | `sha256("ekb-doc-fp-v1\n" + documents.sha256)` | 文件名、标题、页数、ID | 行存在但 sha256 空 → MISSING |
| page | `sha256("ekb-page-fp-v1\n" + page_source_text)`，`page_source_text = extracted_text.strip() or ocr_text.strip()`（**不含 markdown**） | page ID、页码、document_id、PNG、markdown、状态字段 | 无文本层 → 服务层拒绝建立 page 来源，提示改用 evidence(image_region) 或 note |
| note | `sha256("ekb-note-fp-v1\n" + note_type + "\n" + personal_note + "\n" + (user_excerpt or "") + "\n" + (region_image_sha256 or ""))` | note ID、importance、标签、项目 | 目标不存在 → MISSING；正文改 → CHANGED |
| evidence | `sha256("ekb-evidence-fp-v1\n" + evidence_type + "\n" + source_text_sha256 + "\n" + selection_sha256 + "\n" + evidence_text)` | basket_id、position、user_note、标签、项目、**confirmation_status（绝不含入指纹）** | 见 ADR-03 证据双重状态 |

### Migration impact

- `knowledge_object_sources` 纯增量加列：`source_fingerprint TEXT NULL`、
  `fingerprint_version INTEGER NOT NULL DEFAULT 1`、`captured_at TEXT NOT NULL
  DEFAULT 迁移时间`。
- 非空旧库回填：逐行按当前配方重算；目标缺失/不可算 → NULL（UNKNOWN）。
- 新库写入永远非 NULL。

### Test obligations

- 真值表 12 组合参数化测试。
- 四类指纹排除字段负向（改文件名/重要性/标签不改变指纹；改 markdown 不改变 page
  指纹）。
- evidence 确认状态变化不改变指纹。
- 读路径无写库副作用。

## 6. ADR-03 附：Evidence 双重状态（R1 新增）

Evidence 来源具有两个正交状态，**不得混为一个 fingerprint**：

1. **内容/锚点有效性**：由 Evidence fingerprint 验证（evidence_type +
   source_text_sha256 + selection_sha256 + evidence_text）。它回答“证据内容是否
   仍是链接时的内容”。
2. **Evidence 用户确认**：`evidence_items.confirmation_status ∈ {unconfirmed,
   confirmed}`。它回答“用户在证据工作流中是否确认过这条证据”。**绝不写入 source
   fingerprint**（已列入 canonical 排除项）。

规则冻结：

- **未确认但内容有效的 Evidence 可以作为 Knowledge Source**（允许建立链接）。
- 但它**不能使对象达到“外部证据充分”**：派生充分性要求 aggregate VALID 且所有
  evidence 来源 `confirmation_status='confirmed'`。未确认时展示为“来源有效（证据
  未确认）”，充分性为“否（证据未确认）”。
- Evidence 从 confirmed → unconfirmed：KO 来源状态仍 VALID（内容未变）；仅
  “证据已确认/未确认”限定词与充分性变化；KO 用户确认（confirmation_status）完全
  不受影响。
- Evidence 内容 CHANGED 且未确认同时发生：单条来源 = CHANGED；限定词 = 证据未确认；
  聚合按真值表（CHANGED 或 PARTIALLY_VALID）；两者都展示。
- KO 用户确认独立：绑定 KO 内容修订（ADR-02），与 evidence 的确认/内容状态均无关。
- Prompt Package 诚实标注：每个 evidence 来源输出内容状态 + evidence 确认状态；
  对象级输出“外部证据充分性” + “用户确认状态/修订号”。

## 7. ADR-04：生命周期与 supersedes（R1 修订：fail-closed 删除）

### Decision

1. `lifecycle ∈ {active, superseded, archived}`。
2. `superseded_by_ko_id INTEGER NULL REFERENCES knowledge_objects(id)
   **ON DELETE RESTRICT**`（R1：由 SET NULL 改为 RESTRICT，采纳外部倾向）。
3. **数据库不变量（CHECK，行级）**：
   ```sql
   CHECK (
     (lifecycle IN ('active','archived') AND superseded_by_ko_id IS NULL)
     OR (lifecycle = 'superseded' AND superseded_by_ko_id IS NOT NULL)
   )
   ```
4. 合法状态转换（服务层强制）：
   - `active → superseded`：`supersede(old, new)` 置指针；
   - `superseded → active`：`reactivate(old)` 清指针；
   - `active → archived`：`archive(old)`（指针必须为 NULL，天然满足）；
   - `archived → active`：`unarchive(old)`；
   - `superseded` 重新指定后继：`repoint(old, new2)`（保持 superseded，换指针）；
   - `superseded → archived` 不直接允许：必须先 reactivate 再 archive（两步，
     服务层拒绝直接跳转）。
5. 循环拒绝（服务层）：`supersede(old,new)` 拒绝 `new == old`；沿
   `new.superseded_by_ko_id` 链遍历，若可达 `old` 则拒绝（防 A→B→C→A）；
   后继必须是 `lifecycle='active'`。
6. **删除 fail-closed**：
   - 删除任一 KO 前，服务层统计 `inbound_supersession_count`（有多少 superseded
     对象指向它）；
   - `>0` → **禁止删除**，中文报错列出被指向对象，要求用户先：重新指定后继 /
     解除替代并重新激活旧对象 / 归档旧对象 / 其它显式安全处置；
   - DB 层 RESTRICT 作为第二道防线（服务层漏判时拒绝并翻译为中文错误）；
   - 删除预览（KO 删除与文档删除预览）显示 `inbound_supersession_count`。
   - 绝不静默断链（拒绝 SET NULL + 快照方案：身份丢失、链断裂、静默改变结构）。
7. 删除 ≠ 归档；归档保留全部数据且可逆；删除移除对象与来源/关系（revision 永久
   保留，见 ADR-05）。
8. 替代与 relations 表分离：替代不写入 relations（关系表不驱动生命周期）。
9. 正文更新 ≠ 替代：修正走更新（新 revision）；结论实质变化走新建 + supersede；
   禁止覆盖正文表达替代。

### Alternatives（R1 比较）

- **A. ON DELETE RESTRICT（采纳）**：显式、fail-closed、删除预览可介入。
- B. Tombstone：额外表与身份快照，UI 复杂，v0.5.2 成本高。
- C. SET NULL + 独立快照字段：替代链身份丢失、静默断链，被外部倾向否决。

### Migration impact

- v10 重建 `knowledge_objects` 时 FK 用 RESTRICT；v9 无 superseded 数据，回填
  `lifecycle` 仅 active/archived、指针 NULL。

### Test obligations

- CHECK 不变量：active/archived 带指针、superseded 无指针的非法写入被拒。
- supersede/repoint/reactivate/archive/unarchive 全转换。
- 循环（自指、A→B→C→A）拒绝；后继非 active 拒绝。
- 删除有入向替代的对象被拒（服务层中文错误 + DB RESTRICT 双防线）。
- 删除预览计数正确。

## 8. ADR-05：Personal Memory 与 Revision 拆分（R1 修订：稳定身份）

### Personal Memory（同 R1 前，微调）

- `knowledge_memory_entries` 重建为纯用户 Memory：kind ∈ {problem_solving,
  experience, decision}；新增 `status ∈ {active, archived}`；可独立存在、可关联

- 新表 `knowledge_object_revisions`，append-only、不可变。
- **稳定对象身份（R1）**：每行保存不可变身份快照
  `object_local_id_snapshot` / `object_stable_id_snapshot` /
  `object_title_snapshot` / `object_kind_snapshot` + `revision_number` +
  `created_at`（事件发生时间）+ `payload_version`（before/after 格式版本）。
- **无 FK（R1）**：`knowledge_object_id` 为普通数据列（不声明 REFERENCES），
  对象删除时该行**完全不被修改**（SET NULL 也不行——那也是一次修改）。对象存在时

- 事件类型：`legacy_baseline` / `legacy_event` / `created` / `content_updated` /
  `confirmation_changed` / `lifecycle_changed` / `supersession_changed` /
  `source_linked` / `source_unlinked`。
- 不可变保证：service 与 database API 层均不暴露 update/delete；仅 INSERT。
  **不需要 DB trigger**（单用户本地应用，服务层是唯一写入路径；负向测试固化）。
- 对象删除后：revision 行原样保留；导出用 `object_stable_id_snapshot` 交叉引用。
- 搜索：revision 不进入普通知识搜索（ADR-06）。

### schema 演进比较（R1 不变）

- 共表严格隔离：拒绝（脆弱、污染）。
- 独立 revision 表：采纳。
- 通用 events 表：拒绝（过度设计）。

### Migration impact

- v9 `knowledge_change` 行 → `legacy_event`（编号 1..n）+ `legacy_baseline`
  （编号 n+1），规则见 ADR-02；孤儿日志（对象已删）允许 local/stable id 为 NULL、
  title 从日志标题解析；行数逐条核验，不删除任何旧行。

### Test obligations

- 迁移不丢行；baseline/event 编号与绑定正确。
- revision 不可 update/delete（负向，service+DB 双层）。
- 删除对象后 revision 行字节级不变（FK 列不被置 NULL——因无 FK）。
- 每个正式事件 before/after 正确。
- revision 不建 FTS。

## 9. ADR-06：离线知识检索（R1 修订：migration 分期）

### 方案比较（R1）

- **方案 A**：Phase 2B 的 v10 完整创建并测试 FTS 表/触发器；Phase 3 只写 Search
  Service 与 UI。
  - 缺点：FTS 在 2B 已建立但直到 Phase 3 才有任何服务使用，属于“未被服务使用”
    的半程交付；且 2B 测试面被 FTS 撑大。
- **方案 B（采纳）**：v10 只处理知识对象、Memory、Revision、生命周期、来源字段与
  `knowledge_base_meta`；Phase 3 用 **v11 迁移**正式新增两个 FTS 表、触发器与
  rebuild，并与 `KnowledgeSearchService`/UI 同期实现、同期测试。
  - 优点：migration 与其消费者同阶段交付；v10 已应用后绝不回头编辑；无半成品 FTS。

### Decision（R1 冻结）

1. **FTS 由 v11 迁移创建**（Phase 3），v10 不含任何 FTS 对象。
2. 索引层：`knowledge_object_search`（content='knowledge_objects'，索引
   title+content）与 `knowledge_memory_search`（content='knowledge_memory_entries'，
   索引 title+content+root_cause+lesson），触发器随 insert/update/delete 同步；
   Revision 不建索引。
3. 服务层：`KnowledgeSearchService`（只读、离线、无 AI）：jieba 查询归一（复用
   现有 SearchService 的 query-term 模式）→ 查两个 FTS（bm25）→ 类型分组 →
   结果带类型与回源数据。
4. UI：`pages/4_检索资料.py` 新增“个人知识”scope（独立 URL 状态命名空间），
   默认“页面资料”scope 原行为不变。
5. 冻结项：
   - 最小可搜索对象：KO(title/content) + Memory(用户三类，
     title/content/root_cause/lesson)；
   - 结果类型：`knowledge_object` / `knowledge_memory`；
   - 默认排序：类型内 bm25，同分 updated_at DESC, id DESC；
   - archived/superseded 默认排除，筛选“含已归档/已替代”纳入并带徽标；
   - Memory 参与（默认 active）；
   - 新 FTS 表：是（v11）；
   - embedding：否。
6. 固定边界：无 embedding、无外部 AI、无网络、Revision 永不进入普通搜索、
   无 API Key 照常。

### Migration impact（R1 修订）

- v10：无 FTS。
- v11（Phase 3）：纯增量创建两个 FTS 表 + 触发器 + 迁移末 rebuild；不重建任何
  既有表；幂等测试；v11 应用后不再回改。

### Test obligations

- v11 迁移幂等；FTS 同步即时一致；旧页面搜索零回归（全量）；默认排除/筛选纳入；
  Revision 不出现；离线可用。

## 10. ADR-07：结构化导出（R1 修订：稳定 ID）

### 方案比较（R1）

- **A. 持久 Knowledge Base UUID（采纳）**：单行 `knowledge_base_meta.kb_uuid`
  （uuid4，本地生成，随数据库备份/恢复迁移，不依赖账号/云端）。导出稳定 ID =
  `"<kb_uuid>:<object_type>:<local_id>"`。
  - 同一 KB 多次导出：同一对象稳定 ID 不变；换机/备份恢复：kb_uuid 随库迁移，
    身份不变；不同 KB：UUID 不同，不会因整数 ID 相同误判。
  - schema 成本最小：一张单行表，无需给每个对象加 UUID 列。
- B. 对象级 UUID：每对象一列，跨对象全要加列（KO/Memory/Relation/Source/
  Revision），migration 与写入成本高；v0.5.2 不需要对象级独立于库的存活。
- C. Export Package UUID + 本地 ID：只能保证包内引用，跨导出身份不稳定；不满足
  “多次导出同一对象稳定身份”。拒绝。

### Decision（R1 冻结）

1. 采用方案 A：`knowledge_base_meta(id=1, kb_uuid, created_at)` 在 v10 创建；
   `kb_uuid = uuid4()` 在库创建/首次迁移时本地生成；备份恢复与隔离升级后沿用
   库内 UUID；不同库不同 UUID。
2. 稳定 ID 格式：`<kb_uuid>:<object_type>:<local_id>`，
   `object_type ∈ {knowledge_object, knowledge_memory, knowledge_relation,
   knowledge_source, knowledge_revision}`。
3. 导出 JSON 中每个对象同时输出 `id`（本地整数，包内可读）与 `stable_id`
   （权威引用）；所有交叉引用（来源→KO、关系→KO、记忆→KO、revision→KO）使用
   `stable_id`；Markdown front matter 使用同一 `stable_id`。
4. 导出包结构（不变）：`manifest.json` + `knowledge.json` + `memories.json` +
   `relations.json` + `sources.json` + `revisions.json` + `markdown/index.md` +
   `markdown/memories.md` + `markdown/ko-<id>-<slug>.md`。
5. `export_format_version="1.0"`；manifest 含 application_version、schema_version、
   kb_uuid、文件 sha256/大小/条目数、`enums` 字典、`id_namespace="kb-uuid"`。
6. 时间 ISO 8601 UTC 含偏移；枚举输出代码值；缺失来源
   `"state_at_export":"missing"` 保留引用；revision 用 `object_stable_id_snapshot`
   交叉引用（孤儿 legacy 事件 stable id 为 NULL + 说明）。
7. 排除项：API Key、凭据、embedding、私人运行日志、搜索历史、raw PDF/页面 PNG、
   `.env`。
8. 增量导出：不支持（全量）；重新导入：v0.5.2 不支持（格式无损留未来；
   ID 冲突重映射为未来导入工具职责，写入文档）。
9. 三用途：人类可读（markdown/）、无损机器（JSON+manifest）、灾备换机（既有
   BackupService 完整备份，不变）。

### Migration impact

- v10 创建 `knowledge_base_meta` 单行表并生成 UUID；revision 表的
  `object_stable_id_snapshot` 在写入时使用该 UUID 拼接。

### Test obligations

- kb_uuid 唯一、单行、本地生成；备份恢复后 kb_uuid 不变。
- 同一 KB 两次导出：同一对象 stable_id 相同；不同 KB（不同 UUID）不碰撞。
- JSON 交叉引用全部使用 stable_id；Markdown front matter 与 JSON 一致。

## 11. ADR-08：v8 备份隔离升级（R1 修订：目标 schema 运行时化）

| 6 | 生成新版兼容备份 | 迁移后库+文件 | 新备份目录（正式 BackupService 格式，manifest 含当前 app/schema 版本） | 创建失败 | 删除半成品；原备份未动 |
| 7 | 验证新备份 | 新备份目录 | 新备份校验报告（正式 `validate_backup`） | 校验失败 | 删除新备份；保留诊断；原备份未动 |
| 8 | 交接正式恢复 | 校验通过的新备份 | 正式恢复预览/计划 | 正式恢复器自身失败 | 正式恢复 pre-restore 备份保护 production；新备份保留 |

约束（同前）：原备份全程只读不覆盖；隔离根不在原备份内、不在 production data 内；
每步 `upgrade-report.json` + 日志；复用 `backup_service.py` 只读校验原语，不复用
正式 `restore_backup` 入口；步骤 8 前确认正式服务停止；任何失败回到“原备份未动 +
诊断可查”。

## 12. ADR 交叉一致性矩阵（R1）

| 检查项 | 涉及 ADR | 一致性结论 |
|---|---|---|
| ADR-01 ↔ ADR-02 | authorship/epistemic_basis 与 confirmation | 一致：basis 不承载确认；confirmation 字段只在 ADR-02 定义 |
| ADR-01 ↔ Memory kind | knowledge kind 六值 vs memory kind 三值 | 一致：两套枚举独立，`decision`/`experience` 分属不同表语义 |
| ADR-02 ↔ ADR-05 | confirmation ↔ revision | 一致：`content_updated`/`confirmation_changed` 事件；legacy baseline 绑定确认 |
| ADR-03 ↔ Prompt Package | 来源状态与提示词诚实标注 | 一致：提示词输出单条状态 + 聚合五元组 + evidence 限定 |
| ADR-04 ↔ 删除流程 | supersedes ↔ 删除预览 | 一致：RESTRICT + `inbound_supersession_count` 预览 |
| ADR-05 ↔ ADR-07 | revision 身份 ↔ 导出 | 一致：`object_stable_id_snapshot` = `kb_uuid:knowledge_object:<id>` |
| ADR-06 ↔ migration 分期 | FTS ↔ v11 | 一致：FTS 只在 v11（Phase 3），v10 无 FTS |
| ADR-07 ↔ 稳定 ID | 导出 ↔ kb_uuid | 一致：全部交叉引用用 stable_id，front matter 同标识 |
| ADR-08 ↔ 目标 schema | 升级 ↔ 迁移链 | 一致：目标 = 运行时 `SCHEMA_VERSION`，不写死任何版本号 |
| 枚举单一定义 | 全 ADR | 一致：以 §1 注册表为唯一来源，各 ADR 不另写枚举 |
