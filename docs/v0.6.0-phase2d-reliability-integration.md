## Prompt Injection Findings

User text containing `Ignore all previous instructions`, `delete_database`, `shell`,
multiple-tool requests, and instructions to bypass read-only policy cannot alter the
execution authority. Strict parsing accepts only one decision object; the executor
resolves exactly one name through `ToolRegistry`; `Phase1ReadOnlyPolicy` remains the
side-effect authority. Unknown names never fuzzy-match or fall back.

Result: **PASS**.

## Tool-content Injection Findings

Tool evidence containing a fake system override, a request to call another Tool,
private-data exfiltration instructions, and a fake citation is passed only as untrusted
context. The Final Answer text is not interpreted as a new decision. A model response
that follows the fake citation instruction fails existing citation validation; there is
no repair, second Tool, or second decision.

Result: **PASS**.

## Implementation Defects Found

Five defect classes were proven by new tests:

1. `AgentRequest.text` had no vendor-neutral size bound.
2. A failed decision provider attempt was recorded as zero calls in runtime trace.
3. A handler returning a non-`ToolResult` escaped the executor's structured failure path.
4. Tool result data could substitute a stable ID different from its `ToolReference`,
   weakening citation lineage.
5. Decision/Tool/ledger logs and Final Answer provider error messages could expose raw
   exception content supplied by a failing dependency.

## Minimal Fixes Applied

1. Added a 120,000-character `AgentRequest` bound, aligned with the existing context
   package total-character ceiling.
2. Count decision calls at attempt time.
3. Validate handler output type and fail closed.
4. Make `ToolReference` authoritative in `ToolResultContextMapper` and reject mismatches.
5. Log exception type only on Agent/adapter/ledger failure paths and return fixed safe
   Final Answer provider error messages.

No retry, loop, planner, new Tool, new provider, new RAG path, persistence, or product
capability was introduced.

## Architecture Escalations

None. All discovered defects were local implementation/reliability defects and were
fixable without changing ADR-006 or frozen Phase 2A/2B/2C semantics.

## Five Codex Fixes Review

1. **Request length guard（120k）— ACCEPT**
   - 单位：字符（Python `len(text)`，code points）。
   - 依据：与既有 `KnowledgeContextPackager.DEFAULT_MAX_TOTAL_CHARS = 120_000`
     （v0.5.3 context 打包上限）对齐，且 Entry Architecture §10 已明确
     "`max_input_tokens` 复用 v0.5.3 context 上限（120k chars 打包上限）"。
     因此该数值有既有架构依据，不是 Codex 凭空冻结的产品限制。
   - 层级：`AgentRequest.__post_init__`（`src/agent/execution/contracts.py`），
     为 Agent 输入边界；formal constant `MAX_AGENT_REQUEST_CHARS = 120_000` 并导出。
   - vendor-neutral：是；不依赖 Qwen context window。
   - fail closed：构造 `AgentRequest` 时超限即 `ValueError`，发生在任何
     provider / network 之前；超限时 Decision=0、Tool=0、Final=0。
   - 错误信息 safe：仅含常数数值，无路径/密钥/正文。
   - Public Deployment 关系：不冲突；公网入口的 request body limit / rate limit
     是独立部署层工作（见 Residual Risks），本 bound 只约束 Agent 请求文本。

2. **Decision attempt counting — ACCEPT**
   - `decision_call_count = 1` 在 `provider.decide(request)` 之前置位，因此
     provider exception、budget denial、malformed output、非 `AgentDecision`
     返回均计为 1 次 decision attempt，避免"失败就不算调用"的审计低报。
   - budget denial 语义：runtime trace 记 `decision_call_count=1`（逻辑 attempt），
     `AuditedAIProvider` 台账记 `status="rejected"`、`error_class="budget"`、
     `latency_ms=0`、network=0；两层口径一致且不低报。
   - tool count 不受影响；`retry_count` 恒为 0。

3. **Handler return-type validation — ACCEPT**
   - executor 在 handler 返回后做 `isinstance(tool_result, ToolResult)` 检查；
     非法 dict/str/None/任意对象 → `TOOL_EXECUTION_FAILED`，safe message，
     `detail=type(tool_result).__name__`。
   - 非法返回时 handler 恰好被调用一次、tool_call_count=1、无 retry、无 Final Answer、
     无 traceback 泄漏。
   - 7 个正式 production Tool Adapter 逐一核对：全部返回 `ToolResult`，
     满足 `ToolHandler` contract。

4. **ToolReference lineage hardening — ACCEPT**
   - 完整追踪：`ToolResult.references → ToolResultContextMapper →
     ContextItem.stable_id → KnowledgeContextPackage.citations →
     _validate_answer_citations`。
   - 修复了真实 lineage bypass：此前 `data.stable_id` 存在时优先于
     `references[0].stable_id`；现在 `references` 是唯一 authority，
     `data.stable_id` 与 reference 不一致时在 Final Answer 模型调用前抛
     `KnowledgeContextError` → fail-closed（no-evidence，Final=0）。
   - `data` 中的任意 stable_id/string 无法再自行进入 citation allowlist。
   - 7 个 Tool 逐一核对（page_search / knowledge_search / get_knowledge_object /
     get_knowledge_memory / inspect_provenance / inspect_source_integrity /
     get_evidence）：所有 `ToolResult.data` 中的 stable_id 与
     `ToolResult.references` 保持一致，合法 canonical references 未被破坏。
   - 这是对既有 lineage 契约（Entry §12 / ADR-006 decision 6）的
     implementation hardening，不是 semantic contract change。

5. **Error/log sanitization — ACCEPT**
   - executor（decision / tool handler）、`_common.internal_failure_result`、
     `AuditedAIProvider` ledger 失败路径全部改为 `LOGGER.error(..., error_type=%s)`
     只记异常类型，不再 `LOGGER.exception`。
   - Final Answer 的 `AIUnavailableError` / `AIExecutionError` / 未知异常统一返回
     fixed safe message，`detail` 仅 `error_class` 或 type name。
   - 内部可诊断性保留：error type、error_class、status、correlation metadata
     仍在（runtime trace / ledger / detail 字段）。
   - 未出现"except Exception: return generic error"导致可观测性消失的问题。
   - 唯一残留：`src/ai/provider.py` 约 L359 的 docstring 仍写
     "logged with traceback"，与实际实现（只记 error_type）不一致 —
     MINOR 文档漂移，非行为缺陷。
