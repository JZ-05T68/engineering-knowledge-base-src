# EKB v0.5.3 Phase 5 — AI Call Ledger Schema Audit (v12)

- 生成日期：2026-08-25
- 审计对象：`ai_calls` 台账（SCHEMA_VERSION 12，`src/migrations.py:_apply_version_twelve`）
- 审计结论：**v12 足够，保持 SCHEMA_VERSION=12，不新增 schema v13**
- 裁决：不新增 migration；不改写历史记录；不合并 source_feature 与 call kind

---

## 1. ai_calls 当前实际字段、CHECK、索引、外键

`src/migrations.py:1634-1657`，列如下：

| 列 | 约束 |
|---|---|
| id | INTEGER PRIMARY KEY AUTOINCREMENT |
| call_uuid | TEXT NOT NULL UNIQUE |
| capability | TEXT NOT NULL CHECK (IN 'completion','embedding','rerank') |
| model | TEXT NOT NULL |
| prompt_sha256 | TEXT NOT NULL CHECK (length=64) |
| input_chars | INTEGER NOT NULL DEFAULT 0 CHECK (>=0) |
| status | TEXT NOT NULL CHECK (IN 'success','error','rejected') |
| error_class | TEXT（可空） |
| retry_count | INTEGER NOT NULL DEFAULT 0 CHECK (>=0) |
| latency_ms | INTEGER（可空） |
| prompt_tokens / completion_tokens / total_tokens | INTEGER（可空，可靠时才写入） |
| finish_reason | TEXT（可空） |
| source_feature | TEXT NOT NULL |
| target_refs | TEXT NOT NULL DEFAULT '[]'（JSON 数组） |
| created_at | TEXT NOT NULL（ISO UTC） |

- 索引：仅 `ai_calls` 无独立索引（主键 id 天然排序）；`ai_outputs` 有 `idx_ai_outputs_created_at`。
- 无外键；`target_refs` 是弱引用（stable_id 文本），引用对象删除不级联、不回写。

## 2. call kind 或等价字段的合法值

`capability` ∈ `completion` / `embedding` / `rerank`。生成型调用一律为 `completion`；
embedding 类调用为 `embedding`；rerank 预留但当前无调用方。

## 3. embedding、RAG Answer、Experience Model 各以什么数据落入台账

| 调用 | capability | source_feature | target_refs |
|---|---|---|---|
| 检索/索引 embedding（page indexer、hybrid search） | `embedding` | `application`（wrapper 构造值） | `()` 或调用方提供 |
| RAG Answer（真实 Provider） | `completion` | `rag_answer`（按次覆盖） | 本次 ContextPackage 使用项 stable_id |
| Experience Model（真实 Provider） | `completion` | `experience_model`（按次覆盖） | 本次 ContextPackage 使用项 stable_id |

证据：
- 按次覆盖实现：`src/ai/provider.py`（`AuditedAIProvider.complete/embed` 的
  `source_feature`/`target_refs` 关键字参数）。
- RAG：`src/ai/rag_answer_service.py`（调用时传 `source_feature="rag_answer"`）。
- Experience：`src/ai/experience_model_service.py:77,102-104`。

## 4. source_feature 是否足够区分

- `retrieval_embedding`：`capability='embedding'`（与所有生成调用天然隔离）。
- `rag_answer`：`capability='completion' AND source_feature='rag_answer'`。
- `experience_model`：`capability='completion' AND source_feature='experience_model'`。
- 其他既有功能：`application`（构造默认）+ `capability` 维度。

结论：**足够**。生成型调用查询可稳定写为
`capability='completion' AND source_feature IN ('rag_answer','experience_model')`。

## 5. target_refs 是否保存本次实际使用 stable_id、顺序与去重规则

- 是。RAG Answer 与 Experience Model 均以 `tuple(item.stable_id for item in package.items)`
  传入（包内条目按打包顺序去重后的稳定顺序）。
- 打包器已去重且保持输入顺序；`target_refs` 以 JSON 数组原样序列化
  （`src/database.py:insert_ai_call`，`_json_string_tuple` 契约）。
- 查询服务必须按同一契约解析，解析失败不回写、显式标记。

## 6. 成功、失败、超时、解析失败、citation 校验失败如何记录

| 场景 | status | error_class | 说明 |
|---|---|---|---|
| 成功 | success | NULL | retry_count / tokens / finish_reason 按返回写入 |
| 传输/429/5xx/超时 | error | transport / http_429 / http_5xx | 有限重试后仍失败 |
| 响应解析失败 | error | parse | Qwen 适配层映射 |
| 未配置/不可用 | error | unavailable | `AIUnavailableError` |
| 预算拒绝 | rejected | （预算门禁） | 不发起网络调用 |
| citation 校验失败 | **不入 ai_calls 的 status 维度** | — | 发生在服务层、provider 返回之后；该调用本身已以 `success` 记录在 `ai_calls`（模型确实成功返回了文本），而业务层 fail-closed 拒绝展示。调用级事实与业务级裁决分层，语义诚实。 |
| Experience JSON/引用校验失败 | 同上 | — | 模型调用成功记录为 success；候选被服务层拒绝，不产出半成品。 |

## 7. MockCompletionProvider 是否写入真实台账

- **不写入**。Mock 路径在 `RagAnswerService` / `ExperienceModelService` 中直接调用
  `MockCompletionProvider.complete`，不经过 `AuditedAIProvider`，因此不产生 `ai_calls` 行。
- Mock 绝不伪装成真实付费调用；测试将固化"Mock 调用后 ai_calls 行数为 0"。

## 8. 台账是否保存敏感内容

不保存：
- prompt 全文（仅 `prompt_sha256` 与 `input_chars`）；
- 完整上下文正文（仅 `target_refs` 稳定引用）；
- 模型完整回答（`ai_calls` 无任何回答列；`ai_outputs` 只存 `output_sha256`）；
- API Key（无任何凭据列）；
- 私人原文。

## 9. Provider、model、时间、耗时、token、费用、错误摘要字段

| 字段 | 是否存在 | 可靠性 |
|---|---|---|
| provider | **无此列** | 运行时唯一接入供应商为 Qwen（产品契约）；UI 以固定标签展示，不从行数据猜测 |
| model | 有（NOT NULL） | 可靠 |
| 时间 created_at | 有 | 可靠（ISO UTC） |
| finished_at | 无 | UI 不展示结束时间（只有 created_at + latency_ms） |
| latency_ms | 有（可空） | 成功/error 时可靠；rejected 为 NULL |
| prompt/completion/total_tokens | 有（可空） | 仅 Provider 返回时可靠；Mock 无、失败可为 NULL |
| 费用 | **无此列** | UI 不展示费用；不根据模型名或 token 猜测 |
| 错误摘要 | 无独立列 | 由 `error_class`（短枚举）生成；查询服务脱敏+截断 |

## 10. 当前 schema 能否准确查询"所有生成型调用"

能：
```sql
SELECT * FROM ai_calls
WHERE capability = 'completion'
  AND source_feature IN ('rag_answer', 'experience_model')
ORDER BY id DESC;
```
无需任何新列、新 CHECK 或新 kind。

## 11. generated_answer 是否是必要业务语义

否。`generated_answer` 可由既有字段派生：
`capability='completion' AND source_feature IN ('rag_answer','experience_model')`。
- RAG Answer 与 Experience Model 同属生成调用、通过 `source_feature` 区分（符合 Phase 4 冻结契约）。
- 新增 `generated_answer` kind 会与 `source_feature` 语义重叠，反而破坏"单一事实来源"。

## 12. 不升级 v13 的明确理由

1. v12 的 `capability + source_feature + status + target_refs` 已能诚实、稳定地区分
   embedding / rag_answer / experience_model / 成功 / 失败 / 拒绝。
2. 生成型调用可被一条稳定 SQL 精确查询（见第 10 条）。
3. Mock 不落台账，真实调用与离线演示天然区分，不需要新 kind。
4. 唯一"缺失"的 provider/费用列不影响审计语义：provider 由产品单供应商契约承载；
   费用从未承诺、也不可靠，禁止猜测。
5. 新增 v13 只是重命名或冗余列，违反"不得为了命名更漂亮而新增 migration"。

测试证据见本阶段新增 `tests/test_ai_ledger_schema_audit.py` 与既有
`tests/test_ai_ledger.py`、`tests/test_ai_rag_answer.py`、`tests/test_experience_model.py`。

## 13. 若升级 v13 需要的失败案例（本审计不成立）

需要但**不存在**的失败案例：
- "无法区分 rag_answer 与 experience_model" —— 不成立（source_feature 已区分）；
- "生成调用被错误分类为 embedding" —— 不成立（capability 已区分）；
- "Mock 伪装成真实调用" —— 不成立（Mock 不写台账）；
- "无法稳定查询生成型调用" —— 不成立（第 10 条 SQL 已证明）。

因此 **v13 不必要**。

---

## 审计裁决

**保持 SCHEMA_VERSION=12。不新增 migration。**
本阶段只新增：只读领域模型、只读查询服务、只读 UI 与对应测试。
