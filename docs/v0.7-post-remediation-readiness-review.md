## 3. Verified TD-04 State

**结论：TD04_PREREQUISITE_CONFIRMED。**

逐项核对 `git diff 8abf557..3b34a72` 与当前源码：

**NOTE DELETE（`src/note_service.py:632-663`）**
- 存在性校验移入事务内（`SELECT id FROM notes` 在 `BEGIN IMMEDIATE` 之后），
  原"事务外 get_note 再删除"的 TOCTOU 已消除；
- `DELETE FROM knowledge_object_sources WHERE source_type='note' AND source_id=?`
  在删除 note 行**之前**同事务执行；WHERE 精确到 source_type + source_id；
- `rowcount != 1` 守卫保留，`NoteNotFoundError` / `NoteWriteError` 用户语义不变；
- 失败经 `_connection()` 上下文管理器整体回滚（commit-on-success / rollback-on-exception
  语义已在 `src/database.py:129-143` 复核）。

**EVIDENCE REMOVE（`src/evidence_basket_service.py:762-790`）**
- `BEGIN IMMEDIATE` 加入；`source_type='evidence' AND source_id=?` 精确清理先于条目删除；
- 位置压缩（position compact）与 basket 时间戳更新留在同一 `_connection()` 事务内；
- 条目不存在时 `return False` 走空事务提交，无副作用。

**EVIDENCE CLEAR（`src/evidence_basket_service.py:803-816`）**
- 清理使用 `WHERE source_id IN (SELECT id FROM evidence_items WHERE basket_id=?)`
  子查询，**在删除 items 之前**执行（ID 在仍存在时选取）；
- 仅触及当前 basket 的 evidence 链接；跨 basket 隔离保持。

**隔离性**：三处清理均为精确 WHERE；无关 source type、无关 note/evidence、KO 本体、
其他 basket 全部不受影响；文档删除既有先例（`src/document_deletion_service.py:364-405`）
未被改动。focused tests 已落地（`tests/test_note_service.py`、
`tests/test_evidence_basket_service.py` 新增含孤儿计数的用例）。

**边界诚实声明**：`knowledge_object_sources` 本身仍是无 FK 多态表（TD-04 修的是三条
删除生命周期路径，不是 schema）。这不影响 v0.7 前提成立——ADR-011 §3.2 明确 v13 来源
链接用 typed FK，不复用该多态形态；孤儿缺陷类别不会传播进经验链接模型。

**回答**：v0.7 可以在无已知来源生命周期孤儿缺陷的基础上安全扩展 provenance/source
关系。

## 5. Verified TD-06 State

**结论：TD06_PATTERN_CONFIRMED。**

逐项核对 `git diff 687a10b..d6c4022` 与当前源码：

- **预算语义类型化**：`AIBudgetExceededError(AIUnavailableError)` 新增；Local
  `_LazyTokenBudgetGuard` 与 Hosted `HostedDatabaseAiBudgetGuard` 的配额超限均抛该类型；
  预算**未配置**仍为普通 `AIUnavailableError`（两种语义分离）；docstring 明示机器决策
  只认类型不认文案；
- **Provider 不可用语义独立**：`AIUnavailableError` 保留"未配置/能力不可用"；
  `AIExecutionError` 保留"已尝试但失败"（含 `error_class`）；
- **RAG 空上下文类型化**：`RagAnswerErrorCode`（closed `StrEnum`：`EMPTY_CONTEXT` /
  `CITATION_INVALID`）；`RagAnswerError.__init__(code, message)` 强制显式 code；
- **引用非法类型化**：三条引用校验失败路径全部携带 `CITATION_INVALID`；
- **子串分类清零**：`src/agent/response/final_answer.py` 仅按 type/code 映射
  （EMPTY_CONTEXT → 无证据回答；CITATION_INVALID → CITATION_INVALID；其余 RagAnswerError
  → INTERNAL_FAILURE；`AIBudgetExceededError` **先于** `AIUnavailableError` 捕获 →
  BUDGET_EXCEEDED；其余 unavailable → PROVIDER_UNAVAILABLE；AIExecutionError →
  FINAL_ANSWER_FAILED；未知 → INTERNAL_FAILURE fail-closed）。全 `src/` grep 确认
  Agent/AI 边界无残留 `"预算" in str(exc)` 型分类（剩余 `in str(exc)` 均为 SQLite
  vendor 协议串：fts5 探测、FOREIGN KEY / unique 约束映射，属既有约定且非本域）；
- **文案可独立变化**：消息文本与分类解耦；UI 层（rag_answer_ui / experience_ui）只渲染
  异常消息，不做机器分类；
- **未知条件 fail-closed**：未知 RagAnswerError 与未知异常均落 INTERNAL_FAILURE，
  只暴露安全消息与异常类名。

**对未来受控写错误族的适用性**：该模式（少量域基类 + 闭合 code 枚举 + 单点穷尽映射 +
未知 fail-closed）正是 v0.7 写路径错误语义的正确先例。**最小未来错误模式**（不现在
实现）：每个域一个 `XxxError` 基类 + 一个闭合 `XxxErrorCode` StrEnum，覆盖
validation / approval(missing|mismatch) / idempotency(conflict) / source_reference /
storage / write_not_allowed 六族；`AlreadyCommitted` 沿失败矩阵语义为 typed 成功重放
而非异常。**不需要也不应该**为每条文案建几十个异常类——TD-06 自己也遵循了这一点。

## 8. Schema v13 Necessity

**结论：V13_REQUIRED。**

独立核验 v12 现状后逐项评估"v12 能否支撑"，不允许"因为 ADR 说需要所以需要"：

| v0.7 正确性不变量 | v12 现状 | 判定 |
| --- | --- | --- |
| 持久幂等 / commit-unknown 闭环 | 无任何持久命令结果表；进程重启后同键重试无法找回首次结果 | **缺失，必须新增** |
| 写审计（成功 mutation 必有审计行） | `ai_calls` 只覆盖 AI 调用，不覆盖 DB mutation | **缺失，必须新增** |
| 声明级 provenance 载体 | 记忆表无任何 origin/provenance 列；`KnowledgeEpistemicBasis` 只作用于 KO 字段，不落记忆行 | **缺失，必须新增** |
| 墓碑状态 | status CHECK 仅 `('active','archived')` | **缺失，必须扩展** |
| 多来源引用（typed FK） | 记忆链接 = 三个可空 FK 单列（ko/document/page 各至多一条）；多态来源表无目标 FK | **缺失，必须新增** |
| 读后写 / 检索 / 备份 | FTS 触发器 + status 过滤 + 全库备份已就绪 | 已满足，无需 schema 变更 |

前五项全部是受控写的**正确性不变量**而非可选 UI 元数据，v12 无一具备。故
**V13_REQUIRED**，最小概念增量恰为 ADR-011 §3 的三件套：

1. **`knowledge_memory_entries` 扩展**（表重建沿 v10-v12 纪律）：status CHECK 扩
   `'deleted'`；`creation_origin` CHECK('human','agent_assisted')；
   `root_cause_user_confirmed` CHECK(0,1)；`agent_request_ref` TEXT NULL（只存 ID）；
   区块级 provenance 载体（闭合枚举，载体形态列冻结决定，见 §11）；复用既有
   outcome/context_conditions/content 列，不得再造同义列。
2. **`knowledge_memory_sources`**（新表）：entry FK + typed 目标 FK 列 +
   stable_id/指纹快照列；同一 entry+typed target 唯一；禁止无 FK 裸多态。
3. **`experience_command_log`**（新表）：append-only、幂等键 UNIQUE、operation/result

经验数据模型（ADR-011）；ADR-006 的 agent_runs/agent_steps/tool_calls 草案在其真正触发

## 10. Tombstone Lifecycle

**结论：推荐方案 A —— `status = active | archived | deleted`（不新增 deleted_at 列，
不建独立墓碑表）。**

| 准则 | A（status 扩展） | B（status+deleted_at） | C（独立墓碑表） |
| --- | --- | --- | --- |
| 查询简单性 | 单列过滤，与 `search_knowledge` 现有 `me.status IN (...)` 参数化过滤零改动集成 | 每处过滤多一列条件 | 每处过滤多一表 JOIN/反 JOIN |
| 意外复现风险 | 两处读路径守卫即可封死（N-2） | 同样需要该两处守卫（列存在不自动挡读取） | 需要反连接语义，最易漏 |
| FTS 排除 | 天然（status 过滤在 FTS JOIN 查询内） | 需额外条件 | 需额外条件 |
| restore | 单列迁移 | 单列迁移+清列 | 跨表迁移 |
| 审计 | 命令日志承载（undo/restore 行） | 同左，且 deleted_at 与日志时间戳构成双份真相（漂移风险） | 同左 |
| 迁移 | 随 v13 重建免费扩展 CHECK | 多一列+部分索引 | 多一表 |
| 现有代码兼容 | StrEnum 加值 + label；改动最小 | 全链路多一列处理 | 读写路径大改 |
| 备份/维护 | 无差异 | 无差异 | 略增 |

**语义规格（架构层）**：
- `active`：正常可见（FTS 检索默认、列表、按 id 读取、Agent 工具）；
- `archived`：现行语义不变（include_archived / 显式过滤可见）；
- `deleted`：墓碑——`search_knowledge` 永不返回（status 过滤列表不含它，现有代码零
  改动）；记忆页默认列表**必须**排除（`src/knowledge_memory_ui.py` 现默认 status=None
  全量，需加排除，N-2）；`get_knowledge_memory` Tool Adapter **必须**排除（现按 id 直读
  不看 status，N-2）；内容/provenance/命令审计全部保留；不 hard purge；
- restore 目标状态：**active**（v0.7 undo 只作用于受控命令链创建的、以 active 起始的
  条目，不存在 archived→deleted 路径；ADR-011 §5 已定 deleted→active）；
- undo/restore 的时间戳语义由 `experience_command_log` 行承载（append-only 审计即
  时间线），条目行不重复存 deleted_at，避免双份真相漂移。

**Tool/搜索过滤落点汇总（实现规格必须钉住）**：
1. `search_knowledge`：已天然安全（`memory_statuses` 只含 active[+archived]）；
2. `list_knowledge_memory_entries` / `KnowledgeMemoryService.list`：记忆页默认过滤
   需排除 deleted（或 service 层默认排除、显式参数可见）；
3. `get_knowledge_memory_entry` / `KnowledgeMemoryAdapter`：按 stable_id 直读路径需
   status 守卫（墓碑返回 NOT_FOUND 或带墓碑标记，由实现规格定夺，推荐前者语义更严）；
4. `KnowledgeMemoryStatus.label` 增加墓碑中文标签。

与 ADR-011 §5 一致，**非** ADR011_REVISION_CANDIDATE（是确认+落点钉住）。

## 11. Provenance Granularity

**结论：FIELD_BLOCK_LEVEL。**

| 粒度 | 评估 |
| --- | --- |
| ENTRY_LEVEL | **拒绝**。一条经验必然混合用户结局（USER_ASSERTED）与 AI 组织叙事（AGENT_ORGANIZED）、可能还有 AI 推断根因（AGENT_INFERRED）。条目级标签要么整体拔高 AI 文本（违反核心不变量）要么整体贬低用户断言，无法表达"AI 推断永不静默成为用户确认事实"。 |
| FIELD_BLOCK_LEVEL | **采纳**。草稿本来就有固定的封闭区块集合（title/problem/context/investigation/root_cause/resolution/verification/lesson + outcome），每区块一个 origin 标签 + 零到多个来源引用，与用户在屏幕上逐块审阅的粒度严格一致。根因区块叠加显式确认门（`root_cause_user_confirmed`）。 |
| STATEMENT_LEVEL | **拒绝**。需把自由文本解析为语句断言（边界模糊）、逐语句锚定 schema/徽章/UI，schema 与交互复杂度不成比例；v0.7 草稿的产出单位就是区块而非语句。不因"最细"而自动选择。 |

**每区块 origin 的持久模型（推荐，列冻结评审终定）**：
- 持久化 closed 枚举 4 值：`USER_ASSERTED` / `DIRECT_OBSERVATION` /
  `AGENT_ORGANIZED` / `AGENT_INFERRED`；
- `EXISTING_SOURCE_SUPPORTED` **不作为第五个持久 origin**，而是派生态：区块存在
  ≥1 条**显式支撑（support）区块↔来源关联**（用户在草稿中建立并随载荷批准）即显示
  "有来源支持"；来源后续删除则该支撑态如实转为缺失支撑（missing support）、回落到
  持久 origin。**上下文（context）类关联仅作相关参考显示，永不参与支撑派生**——
  该区分必须在持久层保留（N-6 更正，RESOLVED_BY_SPEC_CORRECTION，见 schema 详规
  §0/§10/§13 的 `relation_kind`），不能只存在于命令载荷中。不持久化第五标签的理由
  不变：双份真相会漂移（违反"不得产生看似仍有效的逻辑孤儿"，N-2 同族）。这与
  ADR-011 §2 的表述兼容（该表是"必须至少区分"的语义区分，派生表达仍区分且更不易
  漂移）；如门禁评审坚持 5 值持久化，须同步冻结失效语义。
- `DIRECT_OBSERVATION` 仅在用户显式声明为亲历/实测时使用，不得由来源链接或模型推导
  （沿 `KnowledgeEpistemicBasis` 既有纪律）；
- 根因确认门保持 ADR-011 §2 语义：更强的 Agent 根因默认 `AGENT_INFERRED`，仅用户
  字段级显式动作升格 `USER_ASSERTED`，批准整体草稿不改变认识论标记。

**示例（编码器案例）**：
- 区块"用户结局"（outcome 列）= `USER_ASSERTED`："更换编码器反馈线后设备恢复。"；
- 区块"排查过程" = `AGENT_ORGANIZED`（重组用户口述，未增强事实强度）；
- 区块"根因" = `AGENT_INFERRED`："编码器反馈极性接反"，带
  `root_cause_user_confirmed=0`，未来检索展示必须带"AI 推断"标注；用户点确认后才
  升格；
- 区块"问题现象"若关联到某导入文档的 page 引用且用户批准该关联 =
  EXISTING_SOURCE_SUPPORTED（派生显示"有来源支持"）。

## 12. Audit vs Idempotency Storage

**结论：ONE_STRUCTURE**（`experience_command_log` 一表两职，确认 ADR-011 §3.3 /
ADR-010 事务边界节）。

按准则逐项评估（对照现行约定：`ai_calls` 是 append-only、UNIQUE uuid、闭合 CHECK、
hash-only 的先例，`src/migrations.py` v12 段）：

| 准则 | 一表两职 | 两表分离 |
| --- | --- | --- |
| 幂等查找 | 键 UNIQUE 直查 | 同 |
| 重放 | 行内 target/result 直取 | 需跨表关联 |
| 隐私 | 均只有哈希/长度 | 同 |
| 安全审计 | 谁/何时/何操作/何对象/何哈希齐备 | 同 |
| 操作历史（含 undo/restore） | operation 枚举覆盖 | 同 |
| undo/restore | 目标行直接可查 | 同 |
| 调试 | request_id 贯通应用日志 | 同 |
| schema 清晰度 | 一张表一组闭合 CHECK | 两张表字段高度重叠（key/hash/result/target/时间） |
| 索引 | UNIQUE(key) + (target)/(created_at) | 两份 |
| append-only | 天然 | 两表都要维护 append-only |
| 备份 | 随库 | 随库 |
| 事务原子性 | 单事务一行 | **必须维持两表同步不变量**（每条审计配一条命令行），恰是本仓一贯避免的双权威 |

两表分离的唯一论据是"职责单一"，但代价是引入一条必须永不错位的同步不变量——修复
TD-04 的教训恰是：能被结构（FK/单表）保证的不变量不要靠约定保证。**ONE_STRUCTURE。**

概念职责（不写 SQL）：每行 = 一次已提交命令的完整证明：命令身份
（idempotency_key UNIQUE + request_id）、操作（create/undo/restore）、双哈希
（payload_sha256；create 另加 approved_draft_sha256）、目标（target_stable_id）、
主体与来源（actor、creation_origin）、结果（result 闭合枚举）、提交时间（created_at）。
append-only，不 UPDATE 不 DELETE，永不清理。

## 13. Canonical Payload / Approval Model

**结论：APPROVAL_MODEL_CONFIRMED**（会话内一次性 `{approved_draft_sha256, approved_at}`
维持），并冻结规范化载荷的参与者清单。

**必须参与哈希的参与者（穷尽）**：

| 参与者 | 处理规则 |
| --- | --- |
| 全部内容区块文本（含 title、outcome、各叙事区块） | 用户屏幕所见的确切文本；规范化 = 各字段 trim（与提交时同一规则） |
| 区块序列 | 固定封闭区块枚举序（规范化序列即显示序） |
| 每区块 origin 标签 | 参与哈希（用户批的是"这段话是 AI 推断"这一事实） |
| 根因用户确认标记 | `root_cause_user_confirmed` 参与哈希 |
| 来源引用列表 | 完整有序：target_type + stable_id + 显示标题 + 指纹快照（§17）+ **每条引用的关系语义（support/context，N-6 更正后持久化于 relation_kind）**；顺序 = 草稿展示顺序（所见即所批） |
| creation_origin（human/agent_assisted） | 参与哈希（批准 UI 应显示"AI 辅助整理"元状态） |
| null vs empty | 规范化为统一形态（推荐全字符串、缺席 = ''，与存储 NOT NULL DEFAULT '' 对齐） |

**不得参与哈希**：idempotency_key、request_id、actor、任何时间戳、kind（恒
experience）、任何未显示给用户的字段。**核心不变量**：不存在"批准后可变却不使批准
失效的隐藏可变语义字段"——凡影响落库语义者皆在哈希内，凡在哈希内者皆被显示。

**序列化器**：单一确定性规范化序列化器（固定字段顺序 + UTF-8 + 明确分隔规则），
批准时与提交时调用同一函数；配套"规范化稳定性"单元测试（同载荷两次计算必等、字段
顺序扰动必等、trim 前后差异按规则处理）。具体实现形态是实现细节。

**`approved_at` 的语义定位**：**仅审计/UI 语义**（显示"何时确认"），不承担安全职责。
安全边界由"会话内一次性 + 哈希绑定 + 消费即清"构成；不需要基于时间的过期语义（会话
即有效期），不需要持久化批准实体或批准令牌表。**确认原模型，无修订。**

> **N-7 更正注记（2026-08-30，事实一致性）**：本节冻结的两字段令牌形态经 Task B
> 安全复审修订——批准令牌增加 `approved_idempotency_key` 绑定，服务层对新键 CREATE
> 强制三条件校验（令牌在场 + 载荷哈希相等 + 键相等），使"一次显式批准至多一次逻辑

> golden 向量与 schema 零变更）。

## 14. Approval vs Idempotency Ordering

**结论：CONFIRMED**（授权 = 用户批准；去重/恢复 = 持久命令日志；两者绝不互相冒充）。

关键分离原则：
1. **批准授权首写**：命令日志中无同键行时，必须存在有效批准（令牌在场 + 规范化哈希
   一致）才允许进入事务。未提交命令的幂等键**永远不能**授权写入——键只是"这是同一次
   手势"的标识，权威永远来自批准。
2. **日志证明既往授权**：命令日志行只可能因一次"已通过批准校验并成功提交"的命令而
   存在（成功日志设计，见下）。因此"同键 + 同载荷 + 有日志行"的重放不需要、也找不到
   批准令牌——日志行本身就是那次已发生授权的持久证明。重放返回记录结果，零写入。
3. **成功日志（success-only log）**：失败/回滚的尝试**不落库**（ADR-011 明文"失败且
   已回滚的尝试只进入净化后的应用日志，不在数据库伪造已提交审计行"；失败矩阵 #10
   同）。因此不存在"失败命令行"语义，幂等判定天然二态：有行=已提交成功，无行=未提交。

**决策树算法（架构层，逐情况）**：

```
执行命令(op, idempotency_key, payload, approval?):
  BEGIN IMMEDIATE
  1. 以 idempotency_key 查 experience_command_log
  2. 无行（新键）:
       a. approval 缺失            → 回滚，ApprovalMissing（首次写必须有人类授权）
       b. 重算 canonical_hash(payload) ≠ approved_draft_sha256
                                  → 回滚，ApprovalMismatch（TOCTOU 封死）
       c. 域校验 + 来源引用校验失败 → 回滚，对应 typed validation 错误
       d. 写经验行 → 写来源链接 → (FTS 触发器自动) → INSERT 命令日志行(含结果)
       e. COMMIT；返回首写结果（新 stable_id）
  3. 有行 且 operation 相同 且 payload_sha256 相同:
       无条件返回记录结果 + duplicate_replay=true；不写任何数据；
       【不要求 approval】——授权已由该日志行证明
  4. 有行 且 payload_sha256 不同:
       回滚，IdempotencyConflict（fail-closed，键复用是 bug 信号；
       与 approval 状态无关）
  5. 有行 且 operation 不同（同键跨操作，如 create 后同键 undo）:
       回滚，IdempotencyConflict（键按手势一次一操作；UI 为 undo/restore
       生成新键）
  COMMIT / ROLLBACK
```

**逐情况覆盖验证**：

| 任务给定的情形 | 落点 | 结果 |
| --- | --- | --- |
| 1. 新键、无先前命令 | 情况 2 | 校验批准后首写 |
| 2. 同键+同载荷+先前已提交成功 | 情况 3 | 重放原结果 |
| 3. 同键+不同载荷 | 情况 4 | IdempotencyConflict |
| 4. 同键+先前失败/未提交尝试 | 日志无行（成功日志设计）→ 情况 2 | 视同首写（应用日志留痕，无库内伪行） |
| 5. commit 成功但响应丢失 | 情况 3 | 同键重试重放原结果，绝无第二条 |
| 6. 批准在成功提交后过期/清除 | 情况 3 不查批准 | 重放照常 |
| 7. 任何成功存在之前批准缺席 | 情况 2a | ApprovalMissing，零写入 |

## 15. Commit-unknown Recovery

**结论：CONFIRMED**（ADR-010 事务边界节 / ADR-011 §4 / 失败矩阵 #11 的机制经本轮
事务可行性复核后成立；决策树见 §14）。

精确时序与恢复点（对照 `knowledge_transaction`，`src/database.py:1642-1658`）：

```
BEGIN IMMEDIATE                       ← 写锁取得，后续全部原子
  写经验行 / 来源链接 / provenance
  FTS 影子列由 INSERT/UPDATE 触发器同事务同步（src/migrations.py:1538-1583）
  INSERT experience_command_log（结果行 = 提交标记）
COMMIT                                ← commit-unknown 窗口开启
（上下文管理器返回、服务产出响应）      ← 窗口关闭
```

- 窗口内任何崩溃/断连：事务整体回滚，日志行不存在，重试=首写（情况 2）——
  **不会**产生"已提交但无日志"的状态；
- COMMIT 返回后、响应到达前丢失：日志行已随数据原子落库，同键重试=重放（情况 3）；
  进程重启、跨天重试均成立（日志在 DB 内，随备份/恢复迁移）；
- 恢复语义对 create/undo/restore 三操作一致（各自幂等键）。

## 16. Source Staleness Policy

**结论：按 provenance 类型区分的最小安全策略（D 的收窄形态）**。

| 引用性质 | 提交时校验 | 依据 |
| --- | --- | --- |
| 用户断言/直接观察区块所附的来源（可选上下文） | **仅存在性** | 用户断言的事实性来自用户本人；底层来源事后变化不构成对该断言的否定 |
| 区块 ↔ 来源的显式"支持"关联（EXISTING_SOURCE_SUPPORTED 派生态的基础） | **存在性 + 指纹一致**：提交时对目标重算 DB 行指纹，与批准载荷中的指纹快照比对；不一致 → `SourceReferenceInvalid`（陈旧） | "支持"声明的语义是"这个来源，如我所见，支撑此区块"；草稿与提交之间来源漂移 = 支持声明失效，必须重新审阅 |
| 目标已删除 | `SourceReferenceInvalid`（失效），指出具体引用 | 失败矩阵 #7 |

- 使用**现行** `src/source_fingerprint.py` 机制（对 DB 行规范化渲染做 SHA-256），不引入
  新指纹体系；
- **不实现 ADR-009**（公共完整性 DTO 是另一维度、另一批次）；**不使用**其 integrity_state
  词表做写校验；**永不**把 changed 表述为篡改/造假（沿 ADR-009 §3 语义红线）；
- 提交成功后来源才被删除：typed FK 删除动作 + missing 快照显示按 ADR-011 §3.2 冻结
  （列冻结评审定 SET NULL/snapshot 组合），不得产生看似仍有效的逻辑孤儿。

## 17. Source Snapshot Requirements

**结论：批准载荷中每个来源引用捕获四要素，提交后落 `knowledge_memory_sources` 快照列。**

## 18. Transaction Feasibility

**结论：TRANSACTION_MODEL_CONFIRMED**（单 `BEGIN IMMEDIATE` 五件套架构成立），附两项
实现规格钉住项。

**仓库事实（全部复核）**：
- `knowledge_transaction`（BEGIN IMMEDIATE + 异常整体回滚）现成
  （`src/database.py:1642-1658`）；
- 单事务多语句先例充分：文档删除 12 项残留校验一事务（`document_deletion_service.py:
  357-487`）；TD-04 三个删除路径同模式；
- 连接注入模式现成：`_knowledge_scope(connection)` + 约 11 个知识域方法接受

- FTS 用**触发器**（非显式更新），INSERT 同事务写影子列并进 FTS 索引；触发器失败=
  整笔回滚；

- 失败回滚由 `_connection()`/`knowledge_transaction` 上下文管理器保证（commit-on-success /
  rollback-on-exception），失败矩阵 #10/#14/#15 的"无残留"成立；
- commit-unknown 精确点：上下文管理器内 `connection.commit()` 处（§15）。

`knowledge_transaction`，事务体内只调用连接感知的低层方法；**禁止**调用会自开事务的
service 方法（嵌套 BEGIN IMMEDIATE 会直接抛 "cannot start a transaction within a
transaction"，此为结构性约束而非风格建议）。

**钉住项 N-4**：`create_knowledge_memory_entry` 与 `update_knowledge_memory_status`
目前**不**接受连接注入（自开 `_connection()`）。v0.7 需窄幅扩展：为记忆创建/状态迁移
增加连接感知变体（或加可选参数），并精确复刻 tokenize 影子列写入。这是沿既有
`_knowledge_scope` 模式的有界变更，不是架构风险。

**幂等解析放事务内**：BEGIN IMMEDIATE 串行化 + `idempotency_key UNIQUE` 使并发双击
退化为"一提交 + 一重放"，无需独立预留（reservation）机制；`INSERT … ON CONFLICT`
协议沿失败矩阵 §4。

## 19. Audit Atomicity

**结论：AUDIT_MUST_BE_ATOMIC**（确认原设计；非 DeepSeek 重开项——任何偏离才是门禁
候选）。

- **安全**：尽力而为审计 = 存在"无审计的成功变异" = 不可追溯 mutation，直接违反
  ADR-006 Decision 8 精神与 ADR-010 安全不变量 5；
- **可用性**：本地单用户、SQLite 同事务插一行，可用性代价≈0；审计失败即存储异常，

- **调试/恢复**：命令日志即权威历史；同事务使其永远与数据一致，重放语义依赖它；
- **实现复杂度**：比双写+对账更低。

失败矩阵 #14 已按此语义定义，维持不变。

## 20. Undo / Restore Semantics

**结论（架构层，不实现）**：

**UNDO**：
- 仅用户显式动作（保存后 UI 入口 / 知识记忆页入口）；
- 软删除墓碑：`status: active → deleted`（§10）；
- 从 FTS 检索、默认列表、Agent 读路径消失（守卫落点见 §10）；
- 保留内容/provenance/命令历史；不 hard purge、不建回收站、不做事件溯源；
- 独立命令：自己的 idempotency_key、`operation='undo'`、审计行；
- **资格判定（本评审钉住的新不变量）**：undo 仅允许作用于"由受控命令链创建"的条目，
  判定依据 = `experience_command_log` 存在该 target 的 create 行。命令日志即授权登记册，
  无需在条目上加额外列。对非命令链创建的条目（人手建的任何 kind）undo 拒绝
  （typed validation 错误）——它们继续走既有 `set_status`/`delete_entry` 人类路径。

**RESTORE**：
- 仅用户显式动作；`deleted → active`（唯一恢复目标，见 §10）；返回 **active** 而非
  "先前状态"（v0.7 不存在 archived→deleted 迁移路径）；
- 独立命令：自己的 key、`operation='restore'`、审计行；
- 原始 provenance/来源链接/内容零改写地恢复可检索性；
- 资格判定同 undo（create 行存在 + 当前 status='deleted'）。

**非法迁移**：`deleted→deleted`（重复 undo）→ 幂等重放（同键）或 typed 状态冲突错误
（新键）；restore 非墓碑 → typed 状态冲突错误。均与失败矩阵 #16 一致。

## 21. Read-after-write

**结论：ZERO_NEW_TOOL_CONFIRMED**（不需要第八个 Agent Tool），附两项既有读路径守卫。

现有读取链逐环复核：

| 环节 | 现状 | 结论 |
