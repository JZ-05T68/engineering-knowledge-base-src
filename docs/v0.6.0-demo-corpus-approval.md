## Review checklist

- [ ] Purpose, audience and every included source are explicitly identified.
- [ ] Ownership/license permits the proposed public display and AI processing;
      publicly accessible material is not automatically authorized for reuse.
- [ ] Content review covers all visible and persisted text: document/page text,
      notes, evidence/context/user notes, objects, memory, revisions, source notes,
      project/tag names and any other retained fields.
- [ ] No personal identifiers, account information, private engineering/customer
      data, confidential project names or unauthorized third-party material.
- [ ] Credential scan covers API keys, tokens, passwords, connection strings,
      private keys and credential-bearing URLs; record counts/categories only.
- [ ] Path review covers source/image/Markdown paths, filenames, provenance,
      revision snapshots and free text. No Windows paths, local usernames, home
      directories, private network shares or personal URLs. Required path columns
      satisfy the frozen validator's demo locator rules.
- [ ] No Local import/deletion/backup/restore history or persisted processing errors.
- [ ] Historical `ai_calls` and `ai_outputs` are empty; do not upload real prompts,
      AI outputs or prior audit records as part of the initial seed.
- [ ] Exact schema-v12 table/column/FTS structure, UUID, integrity and foreign keys
      pass the current WP4 validator without migration or weakening checks.
- [ ] Artifact is a regular standalone DB, without links, WAL/SHM/journal sidecars
      or a dependence on Local files. Capture size and SHA before and after validation.
- [ ] Human reviewers have reviewed the exact artifact associated with the recorded
      SHA/UUID; no change was made after review.
- [ ] Maintainer explicitly approves this specific corpus for the stated public use,
      with timestamp and scope recorded below.

Structural validation is necessary but cannot decide ownership, privacy or consent.
A synthetic test passing, a clean credential scan, a hash, or an agent's judgment
cannot replace human content approval.

## Execution and sign-off procedure

1. Maintainer selects independent authorized source materials and identifies human
   reviewers. Record public-use and AI-processing permission before preparation.
2. Prepare a separate candidate artifact in an operator-controlled location, never
   by copying/sanitizing the production DB. Stop if any source authorization is unclear.
3. Review all content and metadata. Run credential/path checks without printing
   findings containing sensitive values. Correct issues only in the separate
   candidate; do not touch production data.
4. On the quiescent candidate, run the frozen
   `src.hosted.storage_validation.validate_seed_artifact(path, expected_sha256,
   expected_uuid)` with explicit independently recorded identifiers and Hosted
   configuration; no dotenv, external AI or production-path access. Record exact
   baseline, safe result, schema, UUID, size, digest and timestamp. Do not add an
   HTTP validator/upload endpoint or substitute a different sanitizer.
5. Human reviewer signs the content/rights/privacy checks. Maintainer then gives an
   explicit statement approving **this exact SHA/UUID** for the recorded public
   purpose. Until that happens, status remains **PENDING**.
6. Operator verifies uploaded bytes/UUID against this record before first seed,
   follows the WP6A first-seed sequence, and keeps the seed path server-controlled.
   Runtime database hashes may later change; the approved hash identifies the
   immutable seed, not a permanent runtime DB hash.
7. Any artifact/content change invalidates that artifact's previous approval and
   requires a new SHA and review. On withdrawal, block public access and arrange
   an explicit maintenance/data-removal decision; never automatically delete data.
