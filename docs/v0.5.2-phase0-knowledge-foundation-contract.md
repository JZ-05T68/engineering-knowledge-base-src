### 4.3 来源与生命周期总结

- **强来源**（SHA-256 + 快照/实时校验）：Document（文件哈希去重）、Evidence Item
  （原文/选区哈希 + 人工确认）、Note 锚点（文字选区/图片区域快照哈希）、Page Embedding
  （来源文本哈希 freshness）。
- **弱来源**（仅存在性校验）：Knowledge Object Source 链接只检查目标行是否存在，
  不比较内容快照——这是与笔记锚点的重要差异，必须在 v0.5.2 验收中明确为“来源可追溯”
  而非“来源快照一致”。
- **删除生命周期**：文档删除有预览→隔离区→对账的 fail-closed 链路；v0.5.2 已把
  知识对象来源链接纳入删除预览与显式清理（`src/document_deletion_service.py:139-142,365-402`）；
  知识对象删除只级联来源/关系，绝不触碰原始材料
  （`src/knowledge_object_service.py:227-235`）。
- **备份恢复**：完整备份含 SQLite 库 + data 文件资产；恢复校验要求
  `schema_version == SCHEMA_VERSION`（当前 9），因此 **v0.5.1 的 schema v8 备份会被
  v0.5.2 直接拒绝**（`src/backup_service.py:651-655`）——这是本阶段发现的最重要
  兼容缺口之一（见第 10 节）。

| 证据确认（人工） | `evidence_items.confirmation_status`（v7） | 知识对象 `reviewed` 借鉴同一“人工确认”思想 |
| fail-closed 来源校验 | `src/evidence_basket_service.py`（导出前 validated snapshot） | 知识对象提示词包已复用 GROUNDING_RULES |
| 完整备份与恢复 | `src/backup_service.py` | 见恢复兼容缺口 |
| 删除生命周期 | `src/document_deletion_service.py`、`src/deletion_recovery.py` | 已扩展清理知识来源链接 |
| AI provider 抽象 | `src/ai/provider.py` | v0.6.x Agent 必须继续只依赖契约层 |
| production/staging 隔离 | `src/config.py:119-154`、`scripts/service_manager.py` | 知识对象功能属 production，测试走 staging/tmp |

### 4.5 当前局限（为什么它仍是“工程知识管理系统”）

1. **知识仍主要依附文档/页面**：结构化笔记的 4 类锚点全部要求 `document_id` 或
   `page_id`（`src/migrations.py:552-560` 的 CHECK 约束），用户无法创建一个不依附
   外部文档的长期经验/判断/决策条目（v0.5.2 的 `knowledge_objects`/
   `knowledge_memory_entries` 才开始改变这一点，但尚未与检索/聚合打通）。
2. **全局检索只覆盖页面 FTS**：`SearchService` 只检索页面（`src/search_service.py:99`），
   知识对象仅页面内 LIKE，记忆条目无检索——新知识资产无法从主搜索入口找到。
3. **来源真实性与知识本体分离不彻底**：知识对象与记忆条目无来源快照，用户无法
   判断“这条知识形成时依据的原文当时是什么样”。
4. **无过时/替代生命周期**：只有 draft/reviewed/archived，无“已被新知识替代”的显式
   语义（`contradicts` 关系只表达矛盾，不表达时间上的替代）。
5. **版本演进不可见**：内容更新只写一行“已更新”日志，不保留前后内容（
   `src/knowledge_object_service.py:215-224`）。
6. **版本/文档一致性破损**：README/CHANGELOG/roadmap/release_check 与运行时 0.5.2
   不一致（见第 3 节）。

## 5. Personal Knowledge System 缺口

### 5.1 已确认事实（代码证据）

- F1：结构化笔记无法脱离文档/页面存在。`src/migrations.py:552-560` 的 CHECK 约束
  强制 document 类笔记必须 `document_id IS NOT NULL AND page_id IS NULL`，其余三类
  必须 `page_id IS NOT NULL`。
- F2：v0.5.2 已引入独立知识对象表 `knowledge_objects`（`src/migrations.py:885-918`），
  kind 六类含 experience/decision，status 三态含 archived——即“第一等知识对象”已
  在仓库中实现（但未获本 Phase 0 之前的契约背书）。
- F3：知识对象可关联来源（document/page/note/evidence），`reviewed` 状态强制至少
  一个有效来源；但来源校验只查行存在性，不比较内容快照
  （`src/knowledge_object_service.py:155-161`、`:386-399`；`src/models.py:994-1000`）。
- F4：知识对象创建/更新/来源变更/关系建立会自动追加 `knowledge_change` 记忆
  （`src/knowledge_object_service.py:177-182`、`:401-417`），但只有“动作+标题”，
  无内容前后快照。
- F5：知识记忆条目（problem_solving/experience/decision）可由用户无文档来源创建
  （`src/knowledge_memory_service.py:78-114` 允许 `document_id/page_id` 均为 NULL）。
- F6：`knowledge_change` 系统自动生成且禁止手动创建
  （`src/knowledge_memory_service.py:92-96`）。
- F7：知识对象与记忆条目**未接入全局检索**：检索页 `pages/4_检索资料.py` 只走
  `SearchService`（页面 FTS）；知识对象搜索是页内 `title/content LIKE`
  （`src/database.py:1826-1828`）；记忆条目无关键词检索。
- F8：跨文档聚合只含 note+evidence（`src/models.py:811-816` 的 `AggregationSourceKind`），
  知识对象与记忆条目不参与。
- F9：AI 推断在 v0.5.2 数据模型中不存在（知识对象只由用户手建；提示词构建器把草稿
  标注为“不应视为已确认事实”），这符合版本边界——但“AI 推断”作为未来内容类型尚无
  字段预留（`src/knowledge_prompt_builder.py:28-36`）。
- F10：备份恢复要求 schema 精确匹配 v9（`src/backup_service.py:651-655`），v0.5.1
  的 v8 备份无法直接恢复。
- F11：`docs/v0.5.x-roadmap.md` 未同步 Personal Knowledge System 长期路线。

### 5.2 基于代码的推论

- I1：v0.5.2 的实现方向（独立知识对象 + 来源链接 + 类型关系 + 变更留痕）与
  Personal Knowledge System 的“知识不依附文档”方向一致；缺失的是**与检索/聚合/
  证据工作流的打通**和**生命周期深度**。
- I2：知识对象当前更像“提炼后的资产库”，而不是“可演进的记忆系统”——因为它有
  状态机但没有版本链、没有过时替代语义、没有快照来源。
- I3：`knowledge_memory_entries` 承担了双重职责：用户经验/决策记录 + 系统变更日志。
  两类数据同表、同查询入口，未来数据量增长后需要关注查询与展示的区分成本。
- I4：释放“用户主动记录不依附文档的知识”的最小路径已经存在（知识对象 draft 无源 +
  记忆条目无源），但 UI 用“手输来源 ID”的方式关联来源，说明当前 UI 是功能验证级，
  不是完整产品级（`src/knowledge_object_ui.py:233-260`）。

### 5.3 产品假设（待审核者确认，非代码事实）

- P1：用户愿意主动维护“知识对象”这一抽象，而不是继续只写页面笔记。
- P2：六类知识对象（概念/事实/原理/经验/问题/决策）足以覆盖个人工程知识的主要形态。
- P3：来源链接只需要存在性校验（而非快照校验）即可满足 v0.5.2 的可追溯要求。
- P4：知识对象不进入全局检索、只在知识对象页内过滤，是 v0.5.2 可接受的闭环；否则
  “检索→回看→再利用”闭环不成立。
- P5：把“知识变更日志”与“用户记忆”放在同一入口展示，用户能够理解。

### 5.4 尚需真人验证的问题

- H1：真人是否理解“结构化笔记 vs 知识对象 vs 知识记忆”三者的边界，并在真实工作中
  做出正确选择。
- H2：真人能否在没有来源选择器（仅手输 ID）的情况下成功关联来源。
- H3：真人是否认为知识对象不进入全局搜索是可接受的（或必须接入）。
- H4：真人是否需要“过时/替代”语义来管理长期知识。
- H5：真人是否接受 `knowledge_change` 只有动作日志、没有内容前后对比。
- H6：v0.5.1 的 schema v8 备份在 v0.5.2 上恢复失败，是否会影响真人既有备份资产。

## 6. v0.5.2 产品契约

### 6.1 Problem Statement

当前系统解决的是“把 PDF 变成可检索、可核验、可引用的页面级资料”。用户依然无法
完成以下真实知识行为：

1. 用户从一次排障中得到一条“经验/判断/决策”后，**如果不依附某个 PDF 页面就无法
   把它保存为长期知识**——结构化笔记的数据库约束强制要求文档或页面锚点
   （`src/migrations.py:552-560`）。
2. 用户无法把散落在多个文档、多条笔记、多条证据里的判断**提炼为一个可复用、
   可关联来源的知识资产**，并在以后用关键词从主搜索入口找到它（现状：知识对象
   页内 LIKE 过滤，未进全局检索）。
3. 用户无法看到“这条知识是什么时候、依据什么来源形成的”，也无法在知识被更新、
   替代或过时后留下可回看的演进痕迹（现状：无内容快照、无替代语义）。
4. 用户把知识交给外部 AI 时，无法得到一个明确区分“草稿/已复核”与“来源事实/个人
   判断”的引用提示词包（现状：v0.5.2 的 KnowledgePromptBuilder 已初步具备，但需
   验收其与证据包的一致性）。

一句话：**EKB 缺的不是“更聪明的检索”或“聊天框”，而是让个人知识在离开原文档后
仍然能够被记录、被结构化、被关联来源、被检索回看、被更新留痕、被再次引用。**

### 6.2 目标用户

- 在 Windows 本机维护个人工程知识库的单用户（工程师/研究者/自学者）。
- 已有 PDF 资料库，并持续产生排障经验、设计判断与决策记录的人。
- 不使用云同步、不接受账号体系、希望数据完全本地可控的人。

### 6.3 核心场景

- S1 无源经验沉淀：用户排障结束后，不关联任何文档，直接记录“问题→最终原因→经验
  教训”或一条经验/决策。
- S2 有源知识提炼：用户从某 PDF 页面、某条笔记或某条证据中提炼一个概念/事实/原理，
  并把来源显式关联到知识对象。
- S3 知识回看与更新：用户通过关键词或过滤找到知识对象，更新内容、调整重要程度、
  复核或归档，系统自动留痕。
- S4 结构关联：用户建立“A 派生自 B”“A 支持 B”“A 与 B 矛盾”等类型化关系。
- S5 复用：用户基于一个或多个知识对象生成带引用规则、带草稿警告的提示词包，复制到
  外部 AI 工具使用；不发起本地 AI 调用。
- S6 数据安全：备份/恢复/删除均覆盖新知识数据；删除知识对象不碰任何原始材料。

### 6.4 最小用户闭环

采用并论证以下闭环：

**记录 → 结构化 → 关联来源 → 检索 → 回看 → 更新 → 再利用**

论证依据（仓库证据）：

- “记录”与“结构化”由 `knowledge_objects` 的六类 kind + 三态 status + importance
  支撑（`src/migrations.py:885-918`）；
- “关联来源”由 `knowledge_object_sources` 四类来源支撑（`:921-934`）；
- “回看/更新”由 `KnowledgeObjectService.update` + append-only `knowledge_change`
  支撑（`src/knowledge_object_service.py:184-225`、`:401-417`）；
- “再利用”由 `KnowledgePromptBuilder` 支撑（`src/knowledge_prompt_builder.py:48-84`）。

本闭环不照抄提示词候选：保留“更新”并加入“关联来源”，因为 v0.5.2 的价值不在
“写笔记”，而在“知识可追溯、可演进、可复用”；同时把“检索”从提示词候选的中间位置
提前到“回看”之前，因为现有检索缺口是 v0.5.2 最需要闭合的环节。

**该闭环成立的硬性前提（必须在后续 Phase 闭合）**：知识对象进入全局检索入口或
具备等价的全库关键词检索路径；否则“检索→回看”断裂，闭环不成立。

### 6.5 第一等知识对象结论

**建议引入独立于 PDF 页面的第一等知识对象 `KnowledgeObject`。**

理由：

1. 现有 `notes` 表被 CHECK 约束锁死在文档/页面锚点上（`src/migrations.py:552-560`），
   扩展它去支持“无源长期知识”需要破坏性重建表，风险高于新建表；
2. `evidence_items` 的本质是“来源材料的证据化选区”，强制要求文档/页面/选区哈希
   （`src/migrations.py:700-769`），不适合承载“个人判断/经验/决策”这类可无源内容；
3. 知识对象需要自己的生命周期（draft/reviewed/archived）、关系图与变更日志，混入
   notes 或 evidence 会破坏两者现有的检索/聚合/证据语义；
4. 仓库中已存在该方向的实际实现（schema v9），本契约为其补上产品论证，而不是
   另起炉灶。

与 Structured Note 的本质区别：

| 维度 | Structured Note | Knowledge Object |
|---|---|---|
| 存在前提 | 必须有文档或页面锚点 | 可无外部来源 |
| 内容性质 | 对页面/选区/区域的个人批注 | 被提炼、可独立成立的知识资产 |
| 来源保存 | 选区/区域快照 SHA-256 | 多态来源链接（存在性校验） |
| 生命周期 | 随锚点有效/失效 | draft/reviewed/archived + 关系 + 变更日志 |
| 检索 | 经页面 FTS | 独立过滤（需接入全局检索） |
| 复用 | 页面回看/聚合 | 引用提示词包 + 关系导航 |

与 Evidence Item 的本质区别：

| 维度 | Evidence Item | Knowledge Object |
|---|---|---|
| 目的 | 证明“原文里有这句话” | 沉淀“我由此形成的知识/判断” |
| 锚点 | 强制页面/选区/区域 | 来源可选 |
| 确认 | 人工确认证据有效 | 人工复核知识成立 |
| 复用 | 证据包 | 知识提示词包 |

来源保存方式：`knowledge_object_sources(source_type ∈ {document,page,note,evidence},
source_id, source_note)`，服务层写前校验目标存在、读时重算有效/缺失
（`src/knowledge_object_service.py:238-253,386-399`）。

事实/经验/判断/决策/推断的区分：由 `kind ∈ {concept,fact,principle,experience,
problem,decision}` 承担“事实/原理/经验/问题/决策”的语义区分；`status ∈ {draft,
reviewed,archived}` + `reviewed_at` 承担可信度区分；提示词包对草稿追加“不应视为
已确认事实”的警告（`src/knowledge_prompt_builder.py:28-36`）。**AI 推断内容在
v0.5.2 明确不进入知识对象**（无 AI 写入路径），其类型预留延后至 v0.6.x。

是否允许无外部来源的个人经验：**允许**。draft 状态可无源创建；`reviewed` 状态
强制至少一个有效来源（`src/knowledge_object_service.py:155-161`）。

编辑/替代/归档/过时：v0.5.2 最小实现为“编辑 + 归档 + 变更日志”；“过时/被替代”
的显式语义不在 v0.5.2（延后 v0.6.x），但 `contradicts` 关系已能表达矛盾。

进入检索和复用：页内过滤（已实现）+ 全局检索接入（Phase 计划必做项）；复用为
引用提示词包（已实现）。

为什么不能直接复用或扩展现有表：见上文 CHECK 约束与语义差异；扩展现有表需要
破坏性重建（v2/v3/v7 模式的表重建），对既有数据与备份恢复的风险高于纯增量新表。

最小字段与未来扩展字段区分：

- 最小字段（v9 已冻结）：`id, kind, title, content, importance, status,
  created_at, updated_at, reviewed_at`。
- 未来扩展（v0.6.x+ 再议）：`supersedes_ko_id`/`outdated_at`（替代语义）、
  `source_snapshot_sha256`（来源快照）、`tags_json/projects_json`（聚合轴）、
  `origin`（user/ai 推断标记）、`version` 链或内容历史表。

### 6.6 Goals（v0.5.2 可验收结果）

- G1：用户可以创建不依附任何文档/页面的知识对象与记忆条目（无源个人经验）。
- G2：用户可以为知识对象关联 document/page/note/evidence 四类来源；`reviewed`
  状态必须有至少一个有效来源。
- G3：用户可以用类型化有向关系连接知识对象。
- G4：知识对象的创建/更新/来源变更/关系变更自动留痕（`knowledge_change` 日志）。
- G5：用户可以从一个或多个知识对象生成引用提示词包，草稿对象带明确警告。
- G6：知识对象可通过关键词从知识对象页过滤找到；**并且**（若 Phase 计划中的检索
  接入项被批准）从全局检索页找到，命中后可回到知识对象及其来源。
- G7：旧数据（v0.5.1 schema v8）升级到 v9 不丢失任何文档/页面/笔记/证据数据
  （迁移测试已覆盖：`tests/test_schema9_knowledge_foundation.py:127-163`）。
- G8：备份/恢复覆盖新知识数据；删除文档时清理其知识来源链接；删除知识对象不碰
  原始材料。
- G9：无 API Key 时全部知识底座功能离线可用；AI 仍为手动模式默认。

### 6.7 Non-goals（明确排除）

- 通用 AI 聊天框；多模型聚合/模型广场/多聊天机器人并列。
- 完整 Personal Context Agent（v0.6.x）。
- Task Agent（v0.7.x）。
- 自动代替用户作出决定。
- 云同步；注册、登录、多用户权限（沿用仓库产品边界）。
- 自动抓取私人聊天或未授权资料。
- 无边界的知识图谱（只有六种类型化直接关系，无图查询引擎）。
- 一次性重写现有系统（PDF/搜索/笔记/证据/数据安全路径保持原样）。
- 以模型生成内容覆盖用户原始知识（v0.5.2 无 AI 写入知识对象的路径）。
- 破坏 v0.5.1 数据兼容性（v8→v9 必须纯增量、迁移前自动备份）。
- v0.5.2 不以“接入一个大模型”作为版本核心成果。

### 6.8 数据所有权

- 本地事实来源：`data/database/knowledge.db`（SQLite，唯一数据库事实来源）+
  `data/raw`、`data/pages`、`data/markdown`（文件资产）。知识对象/记忆/关系/来源
  全部只存在于本地 SQLite；提示词包为可复制文本，不产生服务端状态。
- 备份范围：完整备份含 SQLite 库 + data 文件资产（`src/backup_service.py` 既有机制），
  新知识表随数据库整体备份，不需要额外备份通道。
- 恢复范围：v0.5.2 只能恢复 schema v9 备份；v8 备份的兼容恢复路径必须作为
  Phase 2 硬项处理（现状见 `src/backup_service.py:651-655`）。
- 导出方向：v0.5.2 最小导出为引用提示词包（Markdown 文本）；知识对象的批量导出
  延后至 v0.6.x（不阻塞闭环，但记录为技术债）。
- AI 供应商替换后保持可用：知识对象/记忆/来源/关系为纯本地结构化数据，与 Qwen
  或任何供应商无关；替换供应商只影响可选 embedding/检索增强，不影响知识本体。
- 无 API Key 时必须继续工作：PDF 导入、搜索、阅读、笔记、证据、删除/恢复、备份、
  知识对象、知识记忆、知识提示词包全部离线可用（`src/runtime.py:108-133` 证明 AI
  缺省为 None 且无启动依赖）。
- 避免把个人知识锁死在 prompt/embedding/模型内部状态：知识本体只存 SQLite 表；
  prompt 包按需生成不落库；embedding 只作为页面级检索派生数据（`page_embeddings`
  带 freshness，可删除重建），**知识对象在 v0.5.2 不生成 embedding**。

### 6.9 可迁移性

- 数据库可迁移：单文件 SQLite + 既有迁移链；新知识表为纯增量。
- 导出可迁移：知识提示词包可复制；未来 v0.6.x 增加结构化导出。
- 模型可替换：`src/ai/provider.py` 契约层与知识底座零耦合。
- 应用可替换：知识数据不依赖任何非本地服务。

### 6.10 与 v0.6.x / v0.7.x 的边界

- v0.5.2 只建立 Knowledge Memory / Knowledge Structure / 第一等知识对象 / 经验
  累积的**数据与服务基础**；不实现 Agent。
- v0.6.x Personal Context Agent：在知识底座之上做个人上下文组装、语义回忆与
  “一个体验一致的 AI Agent”；AI 推断内容类型、替代/过时语义、结构化导出等可在此
  版本引入。
- v0.7.x Task Agent：任务执行闭环；v0.5.2 不建立任何任务/目标表。
- 长期不变量：Local-first；用户拥有数据；数据可迁移；模型可替换；核心知识资产
  不依附特定 AI 供应商；AI 不作为启动依赖；自动生成内容与来源事实/用户输入/推断
  保持可区分。

## 7. 数据模型方案比较

### 方案 A：直接扩展现有 Structured Note（`notes` 表）

- 优点：复用现有笔记 UI/服务/检索路径；概念少，用户心智负担低。
- 缺点：`notes` 被 CHECK 约束锁死为文档/页面锚点（`src/migrations.py:552-560`），
  支持无源知识必须重建表；note 语义是“批注”而非“可独立知识资产”，强行扩展会把
  锚点状态机、证据包与聚合视图全部卷入；没有关系表、没有独立生命周期。
- migration 风险：高（重建表 + 改 CHECK + 迁移历史数据）。
- 兼容风险：高（影响 v0.3.0 起的笔记语义与既有测试）。
- 搜索影响：受益有限（仍需改造 FTS/聚合）。
- 备份恢复影响：高（表结构变化牵连 v5-v7 约束）。
- 推荐与否：**不推荐**。

### 方案 B：引入独立第一等知识对象（`knowledge_objects` + 来源/关系/记忆表）

- 优点：语义干净（知识资产 vs 批注 vs 证据三权分立）；纯增量迁移，不动既有表；
  可独立演化生命周期/关系/版本；知识对象可无源；与 Personal Knowledge System
  长期方向一致。
- 缺点：新增概念与页面，用户需要学习；来源链接是多态引用，SQLite 无法声明 FK，
  需服务层校验（已在实现中）；需单独解决全局检索接入。
- migration 风险：低（纯增量 + 核心数据指纹校验）。
- 兼容风险：低（不触碰 v1-v8 表；`reviewed` 规则只作用于新表）。
- 搜索影响：需要新增检索接入（FTS 或统一查询层），这是必做投入。
- 备份恢复影响：低（数据库整体备份天然覆盖；唯一缺口是 v8→v9 备份的恢复校验
  规则，见方案 B 的配套修复项）。
- 推荐与否：**推荐**（与仓库现状一致；产品论证见 6.5）。

### 方案 C：扩展现有 Evidence Item 承担“知识”

- 优点：复用证据确认与提示词包。
- 缺点：evidence 的强制锚点（document/page/selection hash）与“个人经验可无源”
  直接冲突；证据语义是“原文可证明”，不是“个人判断”；扩展会破坏 v4/v7 冻结的
  证据语义与证据包输出。
- migration 风险：高。
- 兼容风险：高。
- 搜索影响：无改善。
- 备份恢复影响：高。
- 推荐与否：**不推荐**。

结论：Phase 0 只提出推荐（方案 B），**不得实施**；是否采纳由审核者决定。
同时必须把“方案 B 的配套修复项”（v8 备份恢复兼容、全局检索接入、来源选择器 UI）
纳入后续 Phase 计划。
