## 1. North Star（倒推设计的目标回路）

> 用户解决了一个真实工程问题 → 检索已有知识 → 得到有依据的回答 →
> 用户给出真实结局 → Agent 把它组织成可复用的工程经验草稿 →
> **用户审阅草稿 → 显式批准** → 受控写入 → 审计/溯源 → 写后立即可读 →
> 未来可被正常检索与引用。

架构必须从这条回路倒推：**用户是唯一写权威；模型只是起草者；批准绑定到"用户看到的那份内容"；写必须幂等、可撤销、可审计、写后即可被现有读取链复用。**

## 2. 核心设计问题：如何跨过 READ_ONLY → HUMAN-APPROVED WRITE

三个严肃备选：

| 方案 | 形态 | 评估 |
| --- | --- | --- |
| **A. 写 = 另一个 Agent Tool** | registry 增加写类 Tool，模型决策可调用 | **拒绝**。模型获得写触发权（即使包批准壳），提示注入面直通写路径；七工具冻结不变量被打破；executor 必须区分副作用类失败语义 |
| **B. 写 = Tool 执行之外的独立 WriteCommand 应用服务** | 用户显式动作 → 应用层命令 → 事务提交 | **采纳的骨架**。写权威在应用层（用户 UI 动作），模型零参与提交；registry/executor 零改动 |
| **C. 两阶段 propose→approve→commit 的多步 Agent 工作流** | Agent 循环内自己"等待批准再继续" | **拒绝循环形态，吸收两阶段语义**。批准天然是 run 之间的人类动作，不需要 Agent 循环；引入循环违背 ADR-006（多步需新 ADR 且未验证回滚/审计语义） |

**推荐 = B 为骨架 + C 的两阶段语义（无循环）：**

```
[阶段1 · 提案（无写）]  现行单步只读 Agent run（可选，用于检索依据）
                       + ExperienceModelService 风格的草稿模型调用（经审计）
                       → 草稿只进 UI 会话，零持久化
[阶段2 · 批准（人类）]  用户审阅/编辑草稿 → 显式确认 → 生成一次性批准
                       （绑定草稿规范哈希，会话内一次性）
[阶段3 · 提交（确定性）] WriteCommand 应用服务：
                       验证批准哈希 → 单事务（写入+链接+FTS触发器+审计+幂等行）
                       → 返回结果；重试按幂等键重放
```

写**不是** Tool、不是 Agent 行为；Agent 的产出永远只是提案。

## 3. 单步执行器保持不变（规格 §7 的明确决定）

**不变。** Decision ≤ 1、Tool ≤ 1、Final ≤ 1、逻辑模型调用 ≤ 2、autonomous retry = 0 全部保持。论证：

1. 提案阶段所需的检索与组织 = 现有单步能力 + 一次经审计的补全（F6 先例），不需要多工具组合；
2. 批准是人类门，天然发生在 run 之外；
3. 提交是确定性代码，无模型参与——没有任何环节需要"Agent 再决策一次"；
4. 引入 Agent 循环的唯一动机是"自主完成多步任务"，与本里程碑"人批准的受控写"目标相反。

## 4. 经验领域模型（概念层，不冻结列）

一条 Personal Engineering Experience 包含概念区块：

`title`；`problem/symptom`（问题/症状）；`context`（背景）；`investigation`（排查过程）；
`root_cause`（根因）；`resolution`（解决结局）；`verification`（验证）；`lessons`（教训/注意）；
`related_equipment`（相关设备/系统）；`user_facts`（用户陈述的事实）；`agent_organized_text`；
`source_references`；`provenance`；`created_at/updated_at`；`status`。

**强制区分**（每个内容区块/声明必须携带 origin/provenance；记录级
`creation_origin=human|agent_assisted` 只描述创建方式，不证明内容真假）：

| origin | 含义 | 信任处置 |
| --- | --- | --- |
| `USER_ASSERTED` | 用户亲口给出/亲手编辑确认的内容（含“最终确认是编码器 A/B 相接反”这类外部文档中没有的结局） | 只能称为“用户陈述”，不得伪称已有来源验证 |
| `DIRECT_OBSERVATION` | 用户明确声明为亲眼、现场或测量所得的直接观察；不得由来源链接或模型推导 | 可称为“用户直接观察”，仍保留用户声明性质 |
| `AGENT_ORGANIZED` | Agent 在不增强事实强度的前提下重组、压缩或结构化用户/来源内容 | 仅提案；不得被表述为确认事实 |
| `AGENT_INFERRED` | Agent 添加的因果、诊断或归纳（如把“换线后好了”推断为“根因是编码器反馈极性错误”） | 明示为推断；不得被表述为确认事实 |
| `EXISTING_SOURCE_SUPPORTED` | 有一个或多个明确、有效的现有来源引用支撑的声明 | 附引用、可回源；不得超出来源内容 |

**根因确认规则（防"静默升级"）**：Agent 草稿中的更强根因默认 `AGENT_INFERRED`；
只有用户执行显式的"确认根因"动作（UI 按钮，绑定该字段）才升级为
`USER_ASSERTED`，并以 `root_cause_user_confirmed` 或等价字段级 provenance 落库。
未确认的更强根因保持 `AGENT_INFERRED`，在未来引用/检索展示中必须带“AI 推断”标注。
批准完整草稿只授权 mutation，不自动改变上述认识论标记。

## 5. Experience vs 现有 Knowledge Memory（规格 §9 的证据化结论）

**结论：同一域对象的扩展，不是新实体。** 证据：

1. `kind=experience` 已存在（F1）——"经验"正是记忆表的设计用途之一；
2. 记忆表已含 root_cause/lesson 等经验语义字段（F1）；
3. 读路径全部现成：FTS（F3）、`knowledge_search`、`get_knowledge_memory` 工具（F7）——写进去即被 Agent 复用，零新读工具；
4. 认识论标签的先例（PERSONAL_EXPERIENCE，F5）证明"用户声明"语义在本仓已有表达方式；
5. 缺的只有 v0.7 特有语义：创建来源（人/AI 协助）、批准/审计/幂等挂钩、用户断言标注。这些是**列级扩展**（v13），不需要新表挤进 KO 或另起炉灶。

**不选新实体的理由**：新实体 = 第二套 FTS/检索/读取/引用链路 = 双份维护 + Agent 复用断裂。
**不过载现有模型的红线**：批准与幂等语义**绝不**塞进记忆表本身——它们属于命令日志
（见 §8/§11），这保证了扩展不会污染记忆的核心语义。

## 6. 草稿态（规格 §10）

**决定：草稿只存在于 UI 会话（Streamlit session_state），零持久化。**

| 准则 | 评估 |
| --- | --- |
| 隐私 | 最优——草稿（含用户结局陈述）不落盘、不入日志 |
| 崩溃恢复 | 草稿丢失，用户重填（结局陈述通常几百字，可接受）；已提交的经验有完整持久化 |
| 复杂度 | 最低（无草稿表、无清理任务、无过期策略） |
| 陈旧草稿 | 随会话消失，天然过期 |
| 审计 | 审计挂钩在提交命令上（批准哈希），草稿本身无需审计 |
| 与"自动化边界"一致性 | 未批准内容零持久化 = 字面满足"未经确认不得修改用户资料" |

明确拒绝：临时 DB 记录、持久草稿实体（无具体需求支撑，规格默认最简单安全设计）。
UI 必须注明"刷新页面将丢失未保存草稿"。

## 7. 批准模型（规格 §11）

- **批准对象**：用户在屏幕上看到的**完整草稿**（所有区块 + 来源引用），不含任何隐藏字段。
- **绑定机制**：批准 = `{approved_draft_sha256, approved_at}`，其中哈希是对草稿**规范化载荷**（区块序列 + 引用列表按固定规则序列化）的 SHA-256。
- **一次性**：批准令牌在会话内生成一次、由提交命令消费一次；提交后即清除。**不可重放**：新写必须重新生成草稿并重新批准。
- **草稿批准后变化？** 不允许——提交命令重算载荷哈希，与 `approved_draft_sha256` 不符即拒绝（`ApprovalMismatch`），UI 回到编辑态要求重新确认。这就是 TOCTOU 防护（§规格12：**写入的必须是用户看到的那份**）。
- **有效期**：会话生命周期（批准不可跨会话；无 TTL 常量——会话即有效期）。
- **双击/UI 重跑**：同一幂等键的重复提交由幂等层吸收（§9）；UI 按钮提交后立即置 loading 态。
- **不持久化批准实体**：批准是"会话内的一次人类意图表达"，持久化它反而制造可重放的授权凭据。

## 8. 写命令（规格 §13）

```
ExperienceWriteCommand（概念字段）:
  request_id: uuid4            # 服务端生成，贯穿审计
  idempotency_key: uuid4       # UI 在命令构造时生成，重试保持不变；非 AI 生成
  approved_draft_sha256        # 批准绑定
  payload                      # 规范化草稿（区块+引用），提交前重算哈希比对
  actor: "local_user"          # v0.7 恒定
  created_at
```

- **验证层次**：应用服务做全部域校验（必填、长度、引用存在性、批准哈希、幂等键）；
  DB CHECK/UNIQUE 是第二道防线（F1 长度 CHECK 已存在）。UI 校验只是体验优化，域层不信任 UI。
- **不暴露内部 DB id**：命令与结果使用 stable_id/`request_id`；结果返回新建经验的 stable_id 供 UI 跳转。

## 9. 幂等（规格 §14）

- **键**：`idempotency_key`（UI 生成 uuid4，非 AI、非内容哈希派生）。
- **存储**：持久化命令日志表（v13，§12）——必须可持久：提交成功后响应丢失 + 进程重启 + 用户重试，仍须重放原结果。
- **作用域**：全局唯一（单用户系统无需按用户分区）。
- **重放语义**：同键 + 同 `payload_hash` → 返回首次结果（原经验的 stable_id），HTTP/服务层标记 `duplicate_replay=true`，**绝不写第二条**。
- **冲突语义**：同键 + 不同 `payload_hash` → `IdempotencyConflict` 拒绝（键被复用是 bug，fail-closed）。
- **保留期**：永久（行极小；它同时是审计记录，见 §11）。
- **覆盖的重复面**：双击、浏览器重试、网络重试、超时后重试、UI 重跑、服务重试——全部收敛为"同键重放"。

## 10. Commit-Unknown（规格 §15，最难的失败）

**语义承诺：提交成功的命令永远可以通过幂等键找回原结果，绝不产生第二条记录。**

时序：`BEGIN IMMEDIATE → 写经验行 → 写链接 → （FTS 触发器同事务）→ 写审计行 → INSERT 命令日志（含结果引用）→ COMMIT`。

响应丢失后的重试：命令携带同一 `idempotency_key` → 日志表命中（同 payload_hash）→ 返回日志中记录的 `experience_stable_id` 与首次结果。**用户看到的是"已保存（重复请求已忽略）"，数据层只有一条。** 进程崩溃、重启、跨天重试均成立（日志在 DB 里）。

## 11. 事务边界与审计原子性（规格 §16/§24）

**一个事务（BEGIN IMMEDIATE）内必须完成**：

1. 创建经验行（含 v13 溯源列）；
2. 创建来源链接（v13 链接表，FK 级联）；
3. FTS 影子列更新（现有触发器自动，同事务，F3）；
4. **写审计记录**；
5. **插入幂等/命令日志行（含结果引用）**。

**审计与写同事务（非 best-effort）。** "写成功、审计失败"的分析：若审计是尽力而为，
存在无审计的成功变更 = 不可追溯的 mutation，直接违反自动化边界与 ADR-006 最小审计
原则的精神；同事务使二者原子——审计失败则整笔回滚，用户看到失败并重试（幂等保证
安全），不存在"无审计的成功写"。

**审计记录内容**（写什么/何时/何对象/何操作/何结果/何键，均满足；不存正文/CoT/密钥）：
`request_id, idempotency_key, operation(create|undo|restore), target_stable_id,
payload_sha256, approved_draft_sha256, actor, result(success|rolled_back), created_at,
creation_origin(agent_assisted|human)`。遵循 F12 最小审计数据原则：哈希与长度，无正文。
事务内回滚场景本身也值得记录吗？——回滚即无变化，由应用日志（LOGGER）承载，不入库
（避免"记录一次未发生的写"的自我污染）。

## 12. Schema v13 概念设计（规格 §30——是，需要，但最小）

**需要 v13 的原因**：幂等/命令日志必须持久（§10）；溯源列与用户断言标注无 v12 宿主；
软删除墓碑需要扩 status CHECK。

**概念迁移（不写 SQL，列冻结留给实现包评审）**：

1. **`knowledge_memory_entries` 扩展**（表重建沿 v10-v12 纪律：事务+前置备份+数据指纹+失败注入测试）：
   - `creation_origin` CHECK('human','agent_assisted')——创建方式，不是事实依据；
   - `root_cause_user_confirmed` CHECK(0,1)——根因确认标注（§4）；
   - 明确复用 v12 `outcome` 承载用户原始结局陈述（≤2000，origin=`USER_ASSERTED`），
     列冻结时不得无理由再造同义 `user_outcome` 列；
   - `agent_request_ref` TEXT NULL——关联的 agent run/request（可空，人写为 NULL）；
   - `status` CHECK 扩展第三值 `'deleted'`（墓碑，§15 undo）；
   - 以最小受约束结构承载声明级 `USER_ASSERTED` / `DIRECT_OBSERVATION` /
     `AGENT_ORGANIZED` / `AGENT_INFERRED` / `EXISTING_SOURCE_SUPPORTED`；
   - 既有内容字段不动（content 继续承载结构化区块文本）。
2. **`knowledge_memory_sources`**（新表，FK 支撑的多来源链接——规避 TD-04 那种无 FK 多态模型）：
   `entry_id → knowledge_memory_entries`；document/page/knowledge_object/evidence 使用真实
   typed FK 列或等价可验证约束；同一 entry+typed target 唯一；创建时目标必须存在；
   来源后来删除时保留最小 stable-id snapshot 并诚实显示 missing。具体 SET NULL/tombstone
   组合在列冻结评审确定，不得退化为无 FK 的裸 `(target_type,target_id)`。
3. **`experience_command_log`**（新表，幂等+审计一表两职）：
   `idempotency_key UNIQUE`、`request_id`、`operation` CHECK('create','undo','restore')、
   `payload_sha256`、`approved_draft_sha256`、`target_stable_id`、`actor`、`result`、
   `creation_origin`、`created_at`。append-only（不 UPDATE 不 DELETE）。

**明确不做**：草稿表、批准表、会话表、事件溯源、full-text 之外的索引结构。

## 13. DeepSeek-Pro 紧凑决策包（§52，无需重读仓库）

- **North star:** 用户解决真实问题后，Agent 把"用户结局 + 已有依据"组织成经验草稿；
  **用户显式批准后**受控写入现有知识记忆存储（kind=experience），幂等、可撤销、
  可审计、写后立即可被现有 FTS/检索/Agent 工具读取与引用。
- **Non-negotiable invariants:** ①文档/工具/模型内容对"写"的权威 = 0（只有 UI 用户动作
  能发起准备、只有显式批准能提交）；②写入内容 ≡ 批准内容（哈希绑定，TOCTOU 封死）；
  ③同幂等键永不产生第二条记录（含 commit-unknown 重放）；④写+链接+FTS+审计+幂等行
  同一事务；⑤审计不可绕过（同事务）；⑥只读 Agent 七工具与单步执行器零改动；
  ⑦Hosted 保持只读，写仅 LOCAL。
- **Chosen architecture:** 两阶段提案-批准-提交，**无循环**：提案=现行只读 run +
  经审计的草稿补全（ExperienceModelService 先例）；提交=应用层 WriteCommand
  （域校验→BEGIN IMMEDIATE→提交）。写不是 Tool。
- **Alternatives rejected:** 写作为 Tool（模型获写触发权，注入面直通写）；多步 Agent
  循环（ADR-006 明确未验证）；新经验实体（与 kind=experience 重复，读链路断裂）；
  草稿持久化（违反自动化边界）。
- **Schema decision:** v13 = 记忆表扩展（creation_origin / 字段级 provenance /
  root_cause_user_confirmed / 复用 v12 outcome / agent_request_ref / status+'deleted'）+ FK 支撑的
  knowledge_memory_sources + experience_command_log（幂等=审计一表两职）。无草稿表；需要
  v13 是因为 v12 尚无持久幂等/commit-unknown 结果、写审计、声明级 provenance 和墓碑。
- **Write boundary:** allowlist 仅 CREATE experience + UNDO/RESTORE 自己刚创建的
  条目；禁止编辑导入文档、改指纹、删源文件、批量变更、后台学习。
- **Approval model:** 会话内一次性 `{approved_draft_sha256, approved_at}`；不持久化、
  不可重放；提交前重算哈希，不符即 ApprovalMismatch。
- **Idempotency:** UI 生成 uuid4 键；持久日志表；同键同哈希=重放原结果；同键异哈希=
  IdempotencyConflict；永久保留。
- **Transaction:** 单 BEGIN IMMEDIATE（经验行+链接+FTS触发器+审计+幂等行）；
  审计失败=整笔回滚。
- **Undo:** 软删除墓碑（status='deleted'）+审计行；可 restore；硬清除延后。
- **13 final decisions:** ①WriteCommand（非 Tool）；②单步 executor 不变；③复用
  Knowledge Memory(kind=experience)；④草稿 session-only；⑤批准 hash-bound/one-shot；
  ⑥持久幂等命令日志；⑦单原子事务；⑧审计同事务；⑨tombstone+restore；⑩schema v13；
  ⑪Local-only/Hosted read-only；⑫v0.7 不做 Agent-assisted edit；⑬不持久聊天历史。
- **Pre-v0.7 prerequisites:** TD-04、TD-05 必须在 v0.7 主体实现前完成；TD-06 必须在
  v0.7 发布前完成，且在 Phase 7 前关闭。
- **Top 5 risks:** ①v13 迁移触记忆表重建（FTS 影子列/触发器重建，须沿 v10-v12
  指纹纪律）；②TD-04 孤儿链接先不修会污染经验链接模型（须先修，见 §14）；③
  TD-05 审计绕过面在新增 AI 调用点后放大（须先收紧组合根）；④UI 会话草稿在
  Streamlit 重跑中的状态一致性（批准哈希机制兜底）；⑤"AI 组织文本被当成确认事实"
  的语义漂移（origin 标注+根因显式确认门）。
- **Only unresolved implementation choices:** 架构层无阻塞分叉；Phase 1 列冻结仍需决定
  ①typed source FK 的具体列/删除后 missing 表示；②声明级 provenance 用规范化子表还是
  受约束结构；③agent_request_ref 关联 run id 还是 request_id。DeepSeek 只需判断这些选择
  是否可以在 ADR 不变量内留给实现评审。
- **Requested DeepSeek verdict:** `APPROVE` / `APPROVE_WITH_CHANGES` / `BLOCK`，只给简短理由；
  无需重读仓库。

## 15. 写策略 allowlist（规格 §20）

**v0.7 授权写范围（穷尽）**：
- CREATE：`knowledge_memory_entries` 一行（固定 `kind=experience`），经批准命令；
- UNDO / RESTORE：仅限"由本命令链创建的经验条目"的 status 迁移（active→deleted→active），经审计命令。

**明确禁止（非目标，架构上不可达）**：编辑/重写导入文档；修改/刷新指纹；删除源文件
（PDF/PNG/Markdown）；改写任意知识对象（KO 更新走既有人类 UI，不经 Agent 链）；
修改设置；批量变更；后台自动知识维护；删除他人（不存在他人）内容；Hosted 写。

## 16. Tool vs Command 边界（规格 §21）

**推荐方案 1：七工具不变，写走独立应用命令。**

| 维度 | 评估 |
| --- | --- |
| 安全 | 模型/提示注入对写零触发权；registry 无写条目=结构性只读（与 ADR-007 同构思想） |
| 清晰度 | "Tool=确定性本地读取"定义保持纯净（ADR-006 Decision 7 的延伸一致性） |
| Executor 改动 | 零 |
| 可审计性 | 命令日志即审计（§11），比工具调用审计更贴近"谁批准了什么" |
| v0.8 意味 | 未来若需要 Agent 辅助修订（草稿→重批准→提交），仍走命令路径；多步循环议题独立评审 |

**拒绝**：新增 WRITE Tool（新 policy 类等于给模型开洞）；双 registry（两套解析/校验
逻辑，收益为零）。

## 17. 重试策略分层（规格 §22）

| 层 | 策略 |
| --- | --- |
| AI 调用（草稿） | 与现状一致：transport ≤2 次额外尝试（仅网络/429/5xx）；语义不满永不重试 |
| 应用命令 | 只允许**幂等重放**（同键）；任何"不确定是否已提交"的重试必须携带同键——禁止盲目重试 |
| DB | 不新增重试；沿用 busy_timeout=30s + 失败上抛（单用户，写竞争罕见） |
| Transport（UI↔服务） | 本地进程内调用，无网络重试问题 |

## 18. 错误分类（规格 §23，按域分组，挂接 TD-06）

- **草稿域**：`DraftValidationError`（必填缺失/超限）、`ProviderFailure`、`BudgetFailure`（以 typed AI error/code 区分，不解析消息文本）；
- **批准域**：`ApprovalMissing`、`ApprovalMismatch`（哈希不符/TOCTOU）；
- **命令域**：`IdempotencyConflict`、`AlreadyCommitted`（=重放成功返回，非错误——按重放语义处理）、`SourceReferenceInvalid`、`StorageUnavailable`（DB 锁/错误）；
- **审计域**：审计失败不设独立错误——同事务回滚后以 `StorageUnavailable` 呈现（审计失败≡写失败）。

不新造异常基类树；沿用各域现有 `XxxError` 命名风格；TD-06 的类型化改造为这些类型
铺路（final_answer 子串匹配移除后，提案链路错误即可结构化流转到写 UI）。

## 19. 撤销 / 编辑（规格 §26/§27）

- **Undo（v0.7）**：软删除墓碑 `status='deleted'`（v13 扩 CHECK）+ 审计行；记忆页可
  restore。不选硬删除（失去可追溯与误恢复）；不建回收站（墓碑即回收站）；不做事件
  溯源。与现有删除架构的关系：经验是纯 DB 行（无文件资产），不适用文档删除的隔离区
  机械；`AGENTS.md` 禁自动删除——undo 只能由用户显式触发。
- **Edit（v0.7 = 否）**：v0.7 只做 create+undo。理由：编辑引入"修订 vs 重批准"语义
  （改了内容，原批准即失效），而记忆的人类编辑路径**已经存在**（`update_entry`，
  用户随时可在知识记忆页手改）；Agent 辅助修订（重新起草→重新批准→提交）属 v0.8。

## 20. 读后写（Read-after-write，规格 §28）

| 环节 | 时机 | 说明 |
| --- | --- | --- |
| FTS 索引 | **同事务同步**（触发器，F3） | 提交即可见；触发器失败=整笔回滚 |
| knowledge_search / get_knowledge_memory | 提交后立即 | 同库同事务可见性；Agent 工具零改动（F7） |
| 未来 grounded 引用 | 立即可用 | 记忆 stable_id 进上下文包后走既有引用校验 |
| Streamlit 刷新 | 提交后 rerun 即见 | 无需缓存失效（现无缓存层） |
| 失败形态 | 整笔失败，无半可见状态 | 单事务保证（F8） |

## 21. 语义重复（规格 §29）

- **请求级重复**：幂等层解决（§9）。
- **语义重复**：v0.7 **不做自动判定、绝不静默抑制**。草稿面板可附带一条
  "相似记忆"提示（对 title+outcome 跑一次现有 knowledge_search，纯提示，
  不拦截）——帮助用户自知重复，决定权在人。模糊去重自动拦截写入 = 违反
  "不静默覆盖用户资料"边界，明确排除。

## 22. 并发（规格 §33）

单用户本地产品，最低保护即足：①所有写走 BEGIN IMMEDIATE（串行化，F8）；
②`idempotency_key UNIQUE` 让并发双击退化为一次插入+一次重放；③双浏览器标签页
= 两个会话 = 两个独立命令（各自批准各自键）→ 两条经验——这是**用户发起的两次
真实意图**，接受并文档化；不做跨会话锁/多用户分布式协调。Hosted 并发不在范围
（写仅 LOCAL）。

## 23. UI 流与 v0.6.1 工作区（规格 §34/§35）

**交互流（复用 Agent Workspace，不重做前端）**：
回答区（grounded 完成态）→「沉淀为工程经验」→ 草稿面板（区块+origin 徽章+
必填"用户结局"输入）→ 审阅/编辑 →「确认保存」（= 批准，绑定哈希）→ Saving →
Saved（展示新经验 stable_id + 前往知识记忆页入口）→ 撤销入口 → 重复请求提示
（重放语义）→ 校验/存储失败态。

**状态机**：`idle → drafting → draft_ready ⇄ editing → approval_ready → saving →
saved → (undo_available → undone → restored)`；失败迁移：draft 失败回 idle（附原因）、
validation/storage 失败回 editing（草稿保留）、ApprovalMismatch 回 editing。
APPROVED **不持久化**（§7）——持久化状态只有已提交实体的 active/deleted。

**v0.6.1 工作区保全**：问答/引用/来源查看器/信任边界/无证据行为原样保留；
比赛件（A/B/C 预置卡、演示措辞、排练重置）**后续移入 Demo Mode 分区**——移动
属于赛后整合包（ADR-008/009 同批），不属于 v0.7；本设计不删工作区任何现役语义。

## 24. ADR-008/009 关系（规格 §36）

- ADR-008（引用映射）改善经验保存后的引用展示，但 v0.7 写路径**不依赖**它；
- ADR-009（公共完整性 DTO）与 v0.7 **零依赖**：经验写入的溯源真相在内部存储
  （origin/命令日志），公共 UI 契约是另一维度；不得为实现写而先实现 ADR-009。
- 三者关系：v0.7 是内部能力；008/009 是公网读侧增强；互不阻塞。

## 25. Hosted（规格 §37）

**写能力 LOCAL ONLY；Hosted 保持只读。** ADR-007 的"Hosted 不 import/不构造任何
写类 service"结构性保证原样成立——WriteCommand 服务只装配进 Local 组合根
（`src/runtime.py`），Hosted 组合根不可见。不为架构对称暴露公网写端点；公网写
需要独立安全 Gate（多用户、滥用、预算），远超本里程碑。

## 26. 安全模型（规格 §38/§39/§40）

**核心不变量（零例外）**：导入文档、工具证据、模型输出中的任何内容，对写操作
的**触发与批准权威均为零**。只有用户 UI 动作能发起草稿准备；只有用户显式批准能
提交；文档内的"请保存…"类文本只是普通数据。

**权威层级**：
```
导入来源/文档 = 信息（information only）
模型          = 提案（proposal only）
Agent         = 提案编排（proposal/orchestration only）
用户          = 唯一写权威（write authority）
应用服务      = 策略执行（allowlist/验证/哈希比对/幂等）
数据库        = 校验通过后的提交权威（CHECK/UNIQUE/FK + 事务原子性）
```

**威胁与防御**：

| 威胁 | 防御 |
| --- | --- |
| 文档内提示注入诱导保存 | 写触发权不在模型/内容（UI-only 发起 + 批准门）；Agent 工具仍全只读 |
| 恶意源文本污染草稿 | 草稿按 AGENT_ORGANIZED/AGENT_INFERRED 标注，用户审阅后才可批准写入；引用校验照常 fail-closed |
| 用户误批错误草稿 | 批准绑定完整草稿哈希（所见即所批）+ undo 墓碑可恢复 |
| 模型虚构根因 | 更强根因默认 AGENT_INFERRED；升格 USER_ASSERTED 需显式字段级确认动作（§4） |
| 批准重放 | 批准一次性、会话内、消费即清；不持久化授权凭据 |
| 双写 | 幂等键 + UNIQUE |
| 写越权实体 | 命令域 allowlist 穷尽（§15），服务校验命令类型 |
| 引用指向无关/不存在对象 | 提交事务内对链接目标做存在性校验（FK + 服务级域校验） |
| 路径/密钥泄漏 | 最小审计数据（哈希/长度）；命令日志无正文；沿用现有 scrub 模式测试 |
| 审计绕过 | 审计与写同事务（§11） |
| 裸 provider 绕过 | TD-05 先修 + 组合根不变量：**任何生产路径不得接收裸 provider**（§27） |

**组合根不变量（挂接 TD-05）**：草稿生成只经 `application_ai_provider()`（audited）；
`AuditedAIProvider.wrapped` 私有化/加能力门（整改包）；scripts 付费探针走显式标注的
未审计构造出口。v0.7 代码评审以"是否存在第二个 provider 构造点"为红线。

## 27. 校验与限制（规格 §41/§42）

- **域校验（服务层，不信任 UI）**：必填（title、outcome）；长度（沿 F1 上限+
  outcome ≤2000）；来源引用存在性（事务内实查）；批准哈希一致；幂等键形态；
  实体状态（目标可写）；用户意图（批准令牌存在）。
- **UI 校验**：仅体验（即时提示），不承担安全职责。
- **限制**：不存完整对话；存"选定的用户陈述（outcome）+ 结构化组织文本"。
  概念上限：title ≤200（既有）、content ≤20000（既有）、root_cause/lesson ≤4000
  （既有）、outcome ≤2000、来源引用 ≤10 条——防止把聊天记录整段灌库。
- **隐私**（规格 §44）：进模型 = 问题、grounded 回答要点、用户结局（经审计，hash-only
  账本）；留本地 = 一切内容（草稿只进会话内存）；进日志 = 类别与哈希，无正文；
  进审计 = 哈希/长度/引用；进备份 = 已提交的完整经验行（本地备份，属用户资产，
  符合 Local-first——与导入文档同等对待）。

## 28. 会话历史（规格 §43）

**不需要持久聊天历史。** 经验创建的输入 = 当前问题的回答（已在会话中）+ 用户结局
陈述（现填）。持久聊天库会引入隐私面、保留期问题与"UI 像聊天"驱动的伪需求；
不引入。

## 29. v0.7 IN / OUT（规格 §49）

**IN**：经验草稿（会话内，origin 标注）；显式批准（哈希绑定）；窄 create 写命令；
来源链接（FK 支撑）；幂等（持久日志）；审计（同事务）；undo/restore（墓碑）；
读后写（FTS/检索/Agent 工具即时复用）；相似记忆提示（纯 advisory）；schema v13
（最小概念集）；TD-04/05 先修、TD-06 发布门前完成。

**OUT**：多步自主 Agent 循环；后台学习/自动知识修改；多用户；联网浏览；批量变更；
自动语义去重拦截；持久聊天历史；公网 Hosted 写端点；复杂编辑历史（Agent 辅助修订
= v0.8）；完整事件溯源；草稿持久化；hard purge。

## 30. 验收场景（规格 §48 摘要，细版见实施计划）

A 正常沉淀（答→草→批→存→检索复用）；B 批准前编辑草稿（origin 徽章随编辑更新，
重算哈希）；C 取消（草稿弃置，零持久化残留）；D 双击/重复提交（幂等重放，一条记录）；
E 存储失败后安全重试（回 editing，重试同键）；F 提交前来源被删（事务内校验拒绝，
提示具体引用失效）；G 模型推断不被静默升格为确认事实（根因确认门）；H 撤销已保存
经验（墓碑+可恢复+审计行）；I 未来 Agent 检索并引用已保存经验（零新工具）。

## 31. 最终决定表（规格 §53 的 13 项）

| # | 决定 | 结论 |
| --- | --- | --- |
| 1 | Tool vs WriteCommand | **WriteCommand**（应用服务，写非 Tool，registry 冻结） |
| 2 | 单步执行器 | **不变**（提案复用现行单步 + 一次审计补全） |
| 3 | 经验模型 | **扩展现有 knowledge_memory（kind=experience）**，不建新实体 |
| 4 | 草稿持久化 | **会话内**，零持久化 |
| 5 | 批准表示 | 会话内一次性 `{approved_draft_sha256, approved_at}`，不持久化 |
| 6 | 幂等存储 | 持久 `experience_command_log`（UI uuid4 键，append-only） |
