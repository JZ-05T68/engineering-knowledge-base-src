# EKB v0.5.2 Phase 3 — Retrieval Contract（ADR-06 补充契约）

- 文档性质：ADR-06（Phase 2A-R1 冻结）的补充数据契约；不新开与 ADR-06 冲突的设计方向。
- 冻结日期：2026-08-24
- 适用范围：Phase 3（FTS v11 / Retrieval Closure）。Phase 3B 只实现 schema、migration、
  legacy shadow-column backfill、FTS 建表、trigger 与 rebuild；服务层与 UI 由 Phase 3C/3D 实现。
- 状态：已冻结。后续阶段按本契约实现，不再回到这些微决策。

---

## 1. Shadow columns 方案（冻结）

v11 对已有知识业务表使用**纯增量 `ALTER TABLE ... ADD COLUMN`**，禁止 drop / recreate
已有 `knowledge_objects` 或 `knowledge_memory_entries`。

`knowledge_objects` 新增：

- `search_title TEXT NOT NULL DEFAULT ''`
- `search_content TEXT NOT NULL DEFAULT ''`

`knowledge_memory_entries` 新增：

- `search_title TEXT NOT NULL DEFAULT ''`
- `search_content TEXT NOT NULL DEFAULT ''`
- `search_root_cause TEXT NOT NULL DEFAULT ''`
- `search_lesson TEXT NOT NULL DEFAULT ''`

这些字段保存经过现有 jieba / FTS canonical tokenization（与 `pages.search_*` 同一语义，
即 `src/database.py::_tokenize_for_fts`）后的影子文本。

**架构冻结**：服务层写 shadow columns；SQLite trigger 只负责把 shadow columns 同步进入
FTS。trigger 不在 SQLite 内执行 jieba。

**Phase 3B 边界**：只做 schema、migration、legacy 数据 shadow-column backfill、FTS 建表、
trigger 和 rebuild；不实现正常运行时服务层同步（留 Phase 3C）。

## 2. FTS 表和 trigger 命名（冻结）

FTS 表：

- `knowledge_object_search`
- `knowledge_memory_search`

`knowledge_objects` trigger：

- `knowledge_objects_fts_insert`
- `knowledge_objects_fts_delete`
- `knowledge_objects_fts_update`

`knowledge_memory_entries` trigger：

- `knowledge_memory_fts_insert`
- `knowledge_memory_fts_delete`
- `knowledge_memory_fts_update`

命名与现有 `pages_fts_*` 风格一致。

**FTS 列名实现说明（已验证的 SQLite 行为）**：FTS5 external-content（`content=...`）要求
FTS 表列名与 content 表列名一致，否则 `'rebuild'` 会报 `no such column`。因此 FTS 列名
直接采用 shadow column 名：

- `knowledge_object_search(search_title, search_content)`
  —— 契约中 "title 对应 search_title、content 对应 search_content" 的实现形态。
- `knowledge_memory_search(search_title, search_content, search_root_cause, search_lesson)`
  —— 同上。

这与现有 `page_search(search_extracted_text, search_ocr_text, search_markdown_content)`
完全同构。

## 3. Knowledge Retrieval 召回语义（冻结）

两个 scope 的召回语义**有意不同**，Phase 3 不得为了"统一实现"而修改页面检索：

| scope | 召回门 | 排序依据 |
|---|---|---|
| 页面资料 | LIKE（现有 `_search_match_clause`） | FTS5 bm25 参与 `_relevance_expression` |
| 个人知识 | FTS5 `MATCH` | 类型内 bm25 |

知识结果排序契约（Phase 3C 实现）：

1. 类型内 bm25；
2. bm25 相同时 `updated_at DESC`；
3. 再相同时 `id DESC`。

Phase 3B 只写入本契约，不实现 `KnowledgeSearchService`。

## 4. Query 行为（冻结）

v11 知识检索：

- 支持 token OR；
- 支持 quoted phrase；
- **不支持 prefix `*`**；不做隐式 prefix 扩展，不新增 prefix tokenizer 或其他搜索语法。

Phase 3C 用测试固化该行为（含负向：prefix 不被当作通配语法）。

## 5. 默认状态过滤（冻结）

Knowledge Object：

- `ACTIVE` 默认参与；
- `ARCHIVED` 默认排除；
- `SUPERSEDED` 默认排除。

Memory：

- `ACTIVE` 默认参与；
- `ARCHIVED` 默认排除。

"含已归档 / 含已替代"是显式筛选项（Phase 3C/3D 实现）。Phase 3B 不实现查询过滤。

## 6. URL scope 契约（冻结）

后续 `pages/4_检索资料.py` 使用独立 scope：

- 无 scope 的旧 URL = `page`（兼容）；
- `page` = 页面资料；
- `knowledge` = 个人知识。

旧 URL 行为必须保持兼容。Phase 3B 不修改 UI 与 `search_state.py`。

## 7. Knowledge Search Result（冻结）

个人知识检索结果使用**独立模型**，不复用现有 `SearchResult`。

必须为 Phase 4（导出）与 Phase 5（Prompt Builder / 全局 UI）保留：

- result type（`knowledge_object` / `knowledge_memory`）；
- object / memory id；
- `stable_id`；
- title；
- searchable content / snippet；
- status（KO 为 lifecycle，Memory 为 status）；
- `updated_at`；
- provenance / source 回链所需锚点。

具体 Python model 由 Phase 3C 实现；Phase 3B 不修改 `src/models.py` 提前实现该模型。

## 8. v11 migration data integrity（冻结）

v11 迁移必须增加知识表专项迁移保护，migration 前后至少核验：

- `knowledge_objects` 行数；
- `knowledge_objects` id 集合；
- `knowledge_objects` 原始业务字段内容哈希；
- `knowledge_memory_entries` 行数；
- `knowledge_memory_entries` id 集合；
- `knowledge_memory_entries` 原始业务字段内容哈希；
- `knowledge_object_sources` 行数；
- `knowledge_object_relations` 行数；
- `knowledge_object_revisions` 行数及既有 revision 内容。

允许发生变化的只有：

- 新增 shadow columns；
- shadow columns backfill；
- 新建 FTS virtual tables / shadow tables；
- 新建 FTS triggers；
- `schema_migrations` 新增 version 11；
- migration 所需结构元数据。

shadow columns 是 v11 新派生字段，**不得**纳入"原始数据必须不变"的哈希输入；
不得把 shadow column 回填误判成原始 Knowledge Foundation 数据被改写。
