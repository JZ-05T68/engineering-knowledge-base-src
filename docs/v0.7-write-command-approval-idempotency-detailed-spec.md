## 0. N-7 更正记录 — Approval one-shot scope / idempotency binding gap

**RESOLVED_BY_SPEC_CORRECTION（本提交，2026-08-30）。**

- **缺陷描述：** 原批准令牌仅含 `{approved_draft_sha256, approved_at}`，只证明
  "批准了**什么**载荷"（语义范围），未绑定"批准了**哪一次**逻辑变异"（逻辑命令身份）。
  而本规格同时冻结"异键同内容 = 两条独立有效写入"。于是同一令牌可被两个不同幂等键
  携带同一载荷各自通过服务校验：`UNIQUE(idempotency_key)` 在 K1≠K2 之间不冲突，
  一次显式批准可授权两次独立 CREATE 变异。
- **复现：** 是（对原 §12/§13 逐字对照 + 数学复现）。原 §13.2 "哈希绑定 ⇒ 只可能
  提交同一载荷一次" 的一次性证明**无效**——SHA-256 绑定只证明载荷恒等，不证明
  命令恒等；该论证隐含依赖"UI 每令牌只发一键"这一 UI 约定，而 ADR-010 把策略
  执行权授予应用服务，UI 约定不构成服务级不变量。
- **核心不变量（本更正冻结）：** **一次显式 CREATE 批准至多授权一次逻辑 CREATE
  变异**——即使调用方绕过 UI 直接构造任意不同幂等键的命令。
- **选型：** 方案 A —— 批准令牌增加 `approved_idempotency_key` 绑定（键在批准动作
  时生成，先于令牌创建）；服务对新键 CREATE 校验三条件：令牌在场 ∧ 载荷哈希相等 ∧
  `command.idempotency_key == token.approved_idempotency_key`。拒绝方案 B（持久化
  已消费批准台账——违反会话内批准架构、引入同步不变量）、方案 C（内容哈希全局
  去重——违背"内容哈希不是命令身份"冻结原则）、方案 D（首试即消费——无状态服务
  无法强制消费、在飞令牌副本可绕过、且破坏失败重试 UX）。
- **影响面：** 本文件 §1/§3.1/§12/§13/§14/§15/§22/§23/§24/§26/§30/§31/§35/§36/
  §44/§45/§48/§49/§50/§51/§52 全部一致性修订；失败矩阵增补 #24；就绪评审 §13
  最小事实注记。**schema 零变更**（命令日志行的 `idempotency_key` 即被批准的
  逻辑键，无需新列）；**黄金向量零变更**（幂等键不入规范载荷，V-01~V-04 字节不变）。
- **ADR 影响：** ADR-010 的批准边界小节明文给出两字段令牌形态
  （`approved_draft_sha256 + approved_at`）；本更正具体修订该形态（+键绑定）以
  服务级强制 ADR-010 自身已冻结的 one-shot 不变量——不改变写权威/持久化架构/
  durable schema/Local-Hosted 边界/Agent 可达性，**非门禁升级**；记为
  **ADR010_REVISION_CANDIDATE**（仅记录，不编辑 ADR、不接受 ADR）。
- **commit-unknown 文字矛盾：** 原 §30.4 案 1 称响应丢失后"令牌被消费"——与规则 B
  （消费发生在 UI 观察到成功结果时）矛盾。本更正一并修正：响应丢失后令牌与键
  **仍在会话**；同键重试走幂等重放；UI 收到重放成功后消费。已修复。

| 重复重放 | **TYPED_SUCCESS**（非异常）（§21） |
| 历史重放（其后被 restore） | 返回历史成功结果 + `duplicate_replay=true`，**不改当前状态**（§43） |
| 历史重放（其后被硬删） | 返回历史成功结果（幂等回答"是否提交过"，不回答"目标是否还在"）（§43） |

### 2.2 冻结边界（本规格不得重开）

- **写权威层级**：SOURCE/检索内容=信息；MODEL=提案；AGENT=提案/编排；USER=显式变异权威；
  APPLICATION SERVICE=策略执行；DATABASE=验证后的确定性提交。
- **写形态**：Write 不是 Agent Tool；registry 恰七只读 Tool；executor 单步；写=确定性
  应用层命令服务；Local-only 写；Hosted READ_ONLY；无自主写、无持久聊天、无持久草稿、
  无任意编辑；v0.7 仅 create+undo+restore；hard purge 与 Agent 辅助编辑延后。
- **持久层**：CONTROLLED_WRITE_SCHEMA_REVISION 的全部列/约束/事务顺序（schema 详规 A）
  视为已冻结输入；物理版本号是参数（G-1），本规格**版本号无关**。
- **N-6 已解决，不得回归**：relation_kind（support/context）持久化、参与批准哈希、
  按关系分派提交校验、按关系分立派生（MISSING_SUPPORT / MISSING_CONTEXT 永不合并）。
- **SUCCESS-ONLY**：命令日志只存已提交成功行；失败零库内痕迹。
- **幂等键不是授权；内容哈希不是命令身份。**

## 4. Experience Block Contract

### 4.1 区块集与规范序（不重开）

区块集 = schema 详规 A §7.1 冻结的恰 10 块；**规范语义序**（canonical order）冻结为：

```
title → problem → context → action → result → root_cause → lesson
      → applicability → limitations → outcome
```

该序与现行 `ExperienceCandidate`（`src/models.py:1604`）字段序一致（outcome 为 v0.7
新增的用户结局，置于末位），并与 schema 详规 A §7.1 排列逐字一致。**不新增**
investigation/resolution/verification/summary 等同义块。

### 4.2 逐区块契约表（唯一权威；不设第二张竞争校验表）

| block_key | 存储落点 | 必填 | 最大长度 | 空白策略 | 空表示 | origin 规则 | 来源关联 | 用户可编辑 | AI 可起草 |

## 5. Content Serialization

### 5.1 问题定义（任务 §7 高价值检查）

schema 详规 A §7.2 注 2 冻结：`content` 列按规范区块序列化承载 5 个内容块
（problem/context/action/result/limitations），概念形态为每块以独立行 `【<block_key>】`
开头。序列化器的实现与稳定性测试被显式委托给本规格（任务 B）。

**判定：纯标记文法（无长度信息）对任意合法用户文本不可逆。**
用户可以在某块正文内合法地输入一行恰好为 `【problem】` 或 `【result】` 的文本
（4000 字符内无任何字符限制），解码器按行扫描标记时将把它误认为块边界，导致
还原结果 ≠ 原文——违反 schema 详规 A 冻结的"按键可无损还原各块"。
**因此必须细化文法；不得静默保留歧义解析。**

### 5.2 冻结文法：长度前缀标记（确定性 + 位置解析）

```text
serialized_content   := "" | segment ( "\n" segment )*
segment              := header "\n" text
header               := "【" block_key "|" char_count "】"
block_key            := 'problem' | 'context' | 'action' | 'result' | 'limitations'
char_count           := text 的 Unicode 码点数（十进制，无前导零）
text                 := 该块的规范化文本（§7；0 < 码点数 ≤ 4000；不含结尾换行）
段序（固定）         := problem → context → action → result → limitations
空块                 := 整段省略（不出现在 serialized_content 中）
全空                 := serialized_content == ""（存储为 ''）
```

示例（两块非空）：

```
【problem|23】
设备上电后电机反转，方向与指令相反。
【result|12】
更换后电机方向恢复正常。
```

**解码算法（唯一权威；按位置消费，绝不做全文扫描）**：

```
parse_content_blocks(content) -> dict[block_key, str] | None:
  pos = 0; result = {}
  循环：
    1. 若 pos == len(content)：若已读到至少一段则返回 result，否则（空串）返回 {} 语义等价空
    2. 期望 pos 处为完整 header（精确匹配 "【" + k + "|" + digits + "】"，k ∈ 五键）
       —— 不匹配 ⇒ 返回 None（不合规）
    3. 期望 header 后恰一个 "\n"（若其后无字符则 text 为空串 → 不合规，空块不该序列化）
    4. 按 char_count 消费恰好 N 个码点作为 text；N == 0 ⇒ 不合规
    5. 若 pos < len(content)：期望当前 pos 为 "\n" 且其后为下一段 header（回到 2）
    6. k 已出现过 ⇒ 不合规（重复块）
  任何一步不满足 ⇒ 返回 None
```

**为什么对任意用户正文可逆**：解析从不扫描正文寻找标记——读完 header 后按
`char_count` 精确消费 N 个码点，正文内容（无论含多少 `【problem】` 形行、换行、
任意 Unicode）只被当作不透明字符消费；下一段 header 的位置由 N 唯一确定。
用户正文中出现标记形行只会成为该块 text 的一部分，解码时逐字还原。
`char_count` 使用 **Unicode 码点数**（Python `len(str)`；与 SQLite `length()` 对
TEXT 的码点语义一致），不使用 UTF-16 代理对计数。

### 5.3 往返不变量（实现必须测试）

`parse_content_blocks(serialize(blocks)) == {k: text for 非空块}`，对全部 10^∞ 类
输入成立，特别是：正文含 `【result】` 行、正文含 `【problem|0】` 行、正文含
多个换行/制表/零宽字符、正文恰 4000 码点、仅一个非空块、全空。

### 5.4 序列化总长边界（fail-closed，不改任何冻结数字）

- 头部开销上界：每段 header ≤ 16 码点（`【limitations|4000】`=15）+ 段间分隔 1 码点；
  五段全满时总开销 ≤ 80 码点。
- **冻结规则**：域校验（§29 步骤 3 之后、任何 DB 写入之前）计算
  `len(serialized_content)`；**> 20000 ⇒ `VALIDATION_FAILED`**（安全中文消息，
  提示缩短内容）。per-block 4000 与 content CHECK 20000 两个冻结数字**均不改变**；
  本规则只是把"两者同时成立"变成提交前的精确 fail-closed 校验。触发窗口极窄
  （要求 5 块总长 > 19920 且头部开销把总长推过 20000），且失败零副作用。
- **禁止**任何静默截断；**禁止**为容纳头部而修改 4000/20000（schema 详规 A §6 已裁决）。

### 5.5 人类路径编辑后的不合规内容（fail-safe 回退，非本写路径职责）

受控写创建的经验仍可被既有人类 `update_entry` 路径编辑 `content`（schema 详规 A §5.3
边界不变）。其结果可能不符合 §5.2 文法。冻结读侧行为：

- `parse_content_blocks` 返回 `None` ⇒ 该条目按"未分块"渲染：整段 content 作为单一
  文本展示，区块级映射不可用；既有的 10 行 provenance 行**原样保留**（它们记录的是
  提交时事实），但 UI 不得把 origin 标签映射到具体正文段落，改为条目级保守提示
  （与历史条目"未标注"语义同族）。**绝不猜测、绝不重写用户正文。**
- 读路径永远不回写、不修复、不重新序列化 content。

### 5.6 对 schema 详规 A 的有界澄清

§5.2 把概念标记 `【<block_key>】` 细化为长度前缀 `【<block_key>|<N>】`，并将
"序列化总长 ≤ 20000 fail-closed"显式化。分类：**IMPLEMENTATION_FROZEN 的有界实现澄清**
（schema 详规 A 注 2 已把序列化器显式委托给任务 B；不触写权威/安全/不可逆语义；
非 DeepSeek 门禁）。schema 详规 A §7.2 注 2 已做最小一致性修订（本提交内完成）。

## 6. Canonical Payload

### 6.1 单一权威规范载荷（CREATE，V1）

**一个**规范语义载荷承载 CREATE 的全部用户可见持久语义；批准哈希与
`experience_command_log.payload_sha256` 均由它计算。结构（键序即序列化序，冻结）：

```text
canonical_payload_v1 := {
  "contract":                   "ekb.experience-canonical-payload",   # 恒定字面量
  "version":                    1,                                    # 恒定（§9）
  "creation_origin":            "human" | "agent_assisted",           # 参与哈希（评审 §13）
  "root_cause_user_confirmed":  false | true,                          # JSON 布尔；参与哈希
  "blocks": [                                                          # 恰 10 项，§4.1 规范序
    { "block_key": <10 键之一>, "text": <规范化文本>, "origin": <4 值之一> }, ...
  ],
  "source_associations": [                                             # 草稿展示序，0..N 项（§10）
    { "block_key": <8 键之一>, "relation_kind": "support"|"context",
      "target_type": "page"|"knowledge_object"|"evidence",
      "target_stable_id": <128 内字符串>,
      "target_title": ≤500 字符,

    , ...
  ]
}
```

- `blocks` **恒含全部 10 键**（缺席语义统一为 `text=""`，与存储 NOT NULL DEFAULT ''

- 新鲜度三键（fingerprint / fingerprint_version / target_revision）在不适用的关联上
  **键整体缺席**（不是 null）：上下文关联的结构性"恒无"由缺席表达，与 DB 侧
  "上下文行三列恒 NULL"的跨列 CHECK 一一对应。
- **持久派生值不入载荷**：`EXISTING_SOURCE_SUPPORTED` 是派生态（读时按
  relation_kind='support' + typed FK 存活计算），永不进入载荷或哈希。
- **传输/审计元数据不入载荷**（除非有具体语义证明，逐一评估后无一成立）：
  `idempotency_key`（幂等身份，非语义）、`request_id`（尝试关联）、`actor`
  （恒 local_user）、一切时间戳（approved_at 是会话元数据；created_at 是提交时刻）、
  `agent_request_ref`（透明关联 ID，schema 详规 A §5.2 明文"参与批准哈希=否"）、
  DB 整数 id、provider/模型元数据、prompt、CoT、`kind`（恒 experience——评审 §13 明文排除）、
  `status`（恒以 active 创建）。
- **核心不变量（承评审 §13，冻结）**：不存在"批准后可变却不使批准失效的隐藏可变
  语义字段"——凡影响落库语义者皆在哈希内，凡在哈希内者皆被显示。

### 6.2 载荷的构造与规范化时序

1. 会话草稿 `ExperienceDraft`（§3.1）经**纯函数载荷工厂**
   `build_canonical_payload(draft) -> ApprovedExperiencePayload` 转换：工厂内完成
   §7 全部规范化 + §5.2 content 序列化预览 + 闭合枚举装配，产出不可变载荷。
2. UI 每次编辑后重算载荷与哈希预览（§36）。
3. 用户批准动作绑定**当前**载荷的哈希（§12）。
4. 命令携带该载荷对象；服务在执行前**再次**调用同一纯函数规格的规范化（幂等）
   并计算 canonical bytes/哈希——服务不信任 UI 侧已算的任何值。
5. 载荷工厂与服务的规范化实现共享同一模块（§49 B2），保证"所见 = 所批 = 所存"。

## 7. String Normalization

冻结规范化的**唯一目标**：消除传输/UI 引入的非确定性，**不重写用户语义**。

| 维度 | 冻结规则 | 理由 |
| --- | --- | --- |
| 换行 | CRLF→LF，孤立 CR→LF（逐字段，在 trim 之前） | Windows/浏览器文本框引入 `\r\n`；换行表示法非内容语义 |
| 首尾空白 | 每个字段 outer trim（Python `str.strip()` 语义） | 与既有 DB 写入行为逐字一致（`create_knowledge_memory_entry` 的 `.strip()`） |
| 内部空白 | **原样保留**（连续空行、行首缩进、内部多空格、Tab 全保留） | 重排内部空白=重写用户文本，违反"不过度规范化" |
| Unicode 规范化 | **不做 NFC/NFKC** | NFKC 会坍缩工程符号中语义不同的字符（如 `Ω`↔`Ω`、全角/半角单位、`№` 等）；NFC 虽保守但本仓无先例且无实际需求；不引入不可见改写 |
| 零宽字符 | **原样保留** | 同上 |
| null vs empty | 缺席可选字段 ≡ `""`；规范载荷中不存在 null 文本 | 与 NOT NULL DEFAULT '' 对齐（评审 §13） |
| title | 同一规则（trim + LF） | — |
| 时序 | 规范化只发生在载荷工厂（批准前）与服务防御性重算（幂等）；存储值 = 规范化值 | 批准所见 = 所存 |

## 8. Canonical Serialization / SHA-256

### 8.1 序列化格式（冻结）

```text
canonical_bytes(payload) =
    UTF8( json.dumps(payload_dict,
                      ensure_ascii=False,
                      separators=(",", ":"),      # 无空白
                      sort_keys=False) )          # 键序 = 构造序 = §6.1 冻结序
payload_sha256 = lower_hex( SHA256( canonical_bytes ) )   # 64 个小写十六进制字符
```

- `payload_dict` 由**专用纯函数**按 §6.1 冻结键序显式构造（专用 dataclass → dict
  转换器），**不得**依赖字典插入偶然、`repr()`、locale 或 `sort_keys`。
- `ensure_ascii=False` + UTF-8 编码：中文原样入字节流（可读 + 确定性）。
- 无盐（该哈希是身份/完整性元数据，不是口令存储——无离线爆破面）。
- 与 `src/source_fingerprint.py` 的来源指纹**彻底不同物**：来源指纹对"来源实体
  DB 行"做 v1 配方渲染哈希（识别来源内容变化）；payload_sha256 对"批准载荷"做
  canonical JSON 哈希（识别命令语义变化）。二者不互相替代、不互相推导。

### 8.2 undo / restore 载荷哈希

同一实现框架、独立契约（schema 详规 A §20 冻结形状的精确化）：

1. relation_kind 与全部快照字段参与规范批准哈希（schema 详规 A §10.3）；批准后任何
   改动（含 context→support）= `APPROVAL_MISMATCH`（§22）。
2. 提交校验按 relation_kind 分派（§32）：support=存在性+新鲜度相等；context=仅存在性。
3. relation_kind 不加入 DB 唯一键（同块同源双关系行不可表达）；歧义载荷 fail-closed
   （§11）。
4. context 永不参与 EXISTING_SOURCE_SUPPORTED 派生；永不增强持久 origin。

### 10.3 来源排序（冻结：展示序即语义序）

**裁决：`source_associations` 数组顺序 = 草稿展示顺序 = 语义的一部分；规范载荷保留
数组顺序，不做排序。** 依据：上游评审 §13 明文"顺序 = 草稿展示顺序（所见即所批）"
——来源引用在 UI 中的呈现次序是被批准语义的一部分（WYSIWYS）。推论：

- 两条来源数组顺序不同的载荷 = **语义不同** ⇒ 哈希不同（正确行为，不是缺陷）；
- 批准后**重排**来源 = 语义编辑 ⇒ 批准失效（§14）；
- "两语义相同载荷哈希相同"不变式在"语义相同（含顺序相同）"的前提下成立
  （§44 向量表 V-05/V-06 钉死两个方向）。

## 11. support / context Normalization（两阶段裁决）

### 11.1 阶段一：批准前草稿装配（用户所见=所存）

若草稿装配层（模型提案 + UI 组装）对同一 `(block_key, target_stable_id)` 同时收到
context 与 support 两条关系：**在哈希与批准之前**折叠为 **support**（强语义吸收弱
语义）。用户在屏幕上看到且批准的是折叠后的单一关系。折叠是纯确定性规则：
`{(block, target)} → 支持优先`。

### 11.2 阶段二：批准后提交（fail-closed，绝不静默归一）

若命令载荷中同一 `(block_key, target_stable_id)` 出现多条关联（无论关系组合）：
**`VALIDATION_FAILED` 拒绝，零副作用**。已批准载荷必须与所见逐字一致；服务对它做
归一化 = 替用户改写批准内容，被架构禁止（纵深防御：正常流在阶段一已折叠，
此路径只可能由 bug 或伪造命令触达）。

### 11.3 汇总

| 阶段 | 输入 | 行为 | 结果 |
| --- | --- | --- | --- |
| 装配（批准前） | 同 (block,target) 双关系 | 折叠为 support | 用户所见=单一 support |
| 提交（批准后） | 同 (block,target) ≥2 条 | **VALIDATION_FAILED** | 零写入 |
| DB 兜底 | UNIQUE(entry_id, block_key, target_stable_id) | INSERT 冲突=不可能（服务已拒） | — |

## 12. Approval Token

### 12.1 形状（冻结；N-7 更正后）

```python
@dataclass(frozen=True, slots=True)
class ApprovalToken:
    approved_draft_sha256: str        # 批准的规范化 CREATE 载荷 SHA-256（64 小写 hex）
    approved_idempotency_key: str     # 批准绑定的逻辑 CREATE 命令键（UUID4；N-7）
    approved_at: datetime             # 会话内批准动作时刻（UTC；仅 UI/审计显示语义）
```

- 命名取 `approved_idempotency_key`（与 `approved_draft_sha256` 平行；"approved" 表述
  "用户批准了它"，而 `authorized_*` 会暗示键自身是授权者——与 §21"键不是授权"矛盾）。
- **两个独立绑定，语义分工（N-7 核心）**：`approved_draft_sha256` = **语义范围**
  （批准了什么内容）；`approved_idempotency_key` = **逻辑命令身份**（批准了哪一次
  变异）。二者独立、并列，**不**把键哈希进载荷（§24/§35 of 任务——保持载荷哈希
  与命令身份正交）。
- 无独立批准 ID（三字段足以承载语义；令牌的三元组本身就是批准标识）。
- `approved_at` 是 **UI/审计上下文元数据，不是安全原语**（§12.3）；无基于时间的
  过期（会话生命周期即批准生命周期；无 TTL 常量）。

### 12.2 创建与存在性规则（逐条冻结；N-7 更正后）

1. **仅由显式用户批准动作创建**（UI"确认保存"类按钮）。**批准动作原子地**：
   (a) 生成全新 `uuid4()` 作为该次逻辑 CREATE 的幂等键；(b) 计算当前规范化载荷哈希；
   (c) 创建绑定二者的令牌。**键先于令牌存在，随令牌同生共死**（§15.1 规则 2）。
2. **服务验证三条件（新键 CREATE；§26 步骤 5）**：令牌在场 ∧
   `payload_sha256 == token.approved_draft_sha256` ∧
   `command.idempotency_key == token.approved_idempotency_key`。任一不满足 = 未获
   该逻辑命令的授权。
3. **永不**由模型文本 / Agent 输出 / 会话内容推断产生（模型没有构造该类型的任何
   代码路径；§39）。
4. **仅存于本地会话状态**（`st.session_state`）；永不落 DB、永不入日志、永不跨会话、
   永不进备份（备份里不存在"批准"这种东西——已提交经验的授权证明是命令日志行，
   其 `idempotency_key` 恰为被批准键，§22）。
5. 每会话至多一个有效令牌（每次批准动作生成全新键 + 全新令牌并覆盖旧令牌；旧
   (键,令牌) 对随之消失，旧键若无命令日志行则自然作废，无任何清理需求）。
6. 概念 API（纯函数，UI 层调用）：
   - `create_approval_token(payload) -> ApprovalToken`（内部生成键并绑定
     `canonical_hash_v1(payload)` + 键）；
   - `approval_authorizes(token, command) -> bool`（服务内等价断言 = §26 步骤 5 三条件）。

### 12.3 安全区（批准的安全原语 = 四者合取；N-7 更正后）

```text
显式用户动作  +  会话局部性  +  精确载荷哈希绑定  +  逻辑命令键绑定
```

`approved_at` 不承担任何安全职责；消费规则见 §13；失效规则见 §14。一次性语义的
服务级证明：令牌只能授权恰好 `(P, K)` 这一对；持久幂等层（UNIQUE + 事务内首查）
保证 `(P, K)` 至多提交一次 ⇒ **一次批准至多一次逻辑变异**——该证明不再依赖任何
UI 约定（N-7 更正后有效）。

## 13. Approval Consumption

### 13.1 裁决：方案 B —— 仅成功提交后消费（N-7 更正后维持，安全证明更新）

**精确规则（冻结）**：

1. **服务端从不消费、从不改写令牌**（服务无会话状态；它只做验证）。每次执行尝试中，
   新键（命令日志无同键行）必须通过三条件（§12.2 规则 2）：令牌在场（否则
   `APPROVAL_MISSING`）∧ `payload_sha256 == token.approved_draft_sha256`（否则
   `APPROVAL_MISMATCH`·payload_mismatch）∧
   `command.idempotency_key == token.approved_idempotency_key`（否则
   `APPROVAL_MISMATCH`·command_key_mismatch）。**N-7：第三条使服务层（而非 UI）
   成为"一次批准至多一次逻辑变异"的强制点。**
2. **消费 = UI 从会话状态移除令牌**（令牌内嵌键，消费即同时清除二者——无第二份
   CREATE 键状态，§36），仅当 UI 收到 `ExperienceWriteResult` 且
   `operation == 'create'` 且成功（无论 `duplicate_replay` 真假——重放成功同样意味着
   逻辑写已完成）。
3. **一切 typed 失败（含 commit-unknown 的安全失败呈现）保留令牌**：载荷与键均未变时，
   重试直接复用同一令牌 + 同一键，无需重新批准。
4. 令牌的其他清除时机见 §14 / §35（语义编辑、新建草稿、手动重置）。

### 13.2 方案比较与选择理由

（此处 A/B/C 指消费**时机**方案，与 §0 N-7 整改选项 A-E 无关。）

| 评估面 | 首试即消费 | 成功后消费（**选定**） | 验证通过即消费 |
| --- | --- | --- | --- |
| 瞬态失败（DB busy / 来源漂移后未改稿）重试 | 需重新批准（与失败矩阵 #10"是（同键）"重试语义冲突） | **直接重试**（令牌仍绑定同一载荷+键） | 需重新批准 |
| 双击竞态（第二次点击落在首次提交期间） | 第二次尝试 `APPROVAL_MISSING`（噪声错误） | 第二次尝试或重放或被批准门拦下，零重复写入 | 同首试即消费（噪声错误） |
| "批准允许多次独立写"风险 | 无（但服务无法强制消费——见下行） | **无**（N-7 后服务级证明：令牌只授权 (P,K) 一对 ∧ 幂等层保证 (P,K) 至多提交一次） | 无 |
| 失败后用幂等键顶替授权 | 不可能（键非授权） | 不可能（重试的授权是**仍有效的令牌**，键只是其范围） | 不可能 |
| commit-unknown | 重放免批准 ✓ | 重放免批准 ✓ | 重放免批准 ✓ |
| UI 心智模型 | "每次失败都要重新确认" | "批准对未变的草稿持续有效，直到成功或内容变化" | 近似首试即消费 |

**N-7 前后的安全证明差异（必须如实记录）**：原 §13.2 曾声称"哈希绑定 ⇒ 只可能
提交同一载荷一次"——该论证**无效**（哈希绑定只证明载荷恒等，不证明命令恒等；
异键同载荷可各自通过校验）。N-7 更正后，规则 B 的安全性由**服务层键绑定**（令牌
只授权 (P,K) 一对，异键 = `APPROVAL_MISMATCH`）与**持久幂等层**（同键至多一行
⇒ 至多一次提交）的**合取**保证——不再依赖"UI 每令牌只发一键"的约定，也不再
依赖消费时机。消费时机因此仅是 UX 选择，选 B 的决定性理由不变：失败矩阵
#10/#18 的重试语义要求失败不吊销授权。

任务四条核心要求逐条验证（N-7 更正后）：

- 批准不允许多次独立写 ✓（服务级证明，§13.2 表第 3 行；绕过 UI 直接构造异键命令
  亦被拒——§27 验收判据）；
- 已提交响应丢失重放不需要批准 ✓（重放路径根本不查令牌，§21）；
- 失败未提交尝试不能把幂等键当授权 ✓（键非授权；重试授权=保留的令牌，且键必须在
  令牌绑定范围内）；
- 失败后有可理解的重新批准路径 ✓（未变=直接重试；已编辑=§14 失效后重新批准，
  新批准生成新键）。

### 13.3 任务 §18 逐情形验证

| 情形 | 规则 B 行为 |
| --- | --- |
| 双击（并发两尝试） | 一者提交成功并消费；另一者要么重放（若已提交）要么被 `BEGIN IMMEDIATE` 串行化后重放；零重复经验 |
| **同一令牌 + 不同键**（并发或顺序，含绕过 UI 的直接构造） | 键范围不匹配 → `APPROVAL_MISMATCH`·command_key_mismatch；零写入（N-7 闭合；§31/§48 攻击行） |
| Streamlit 反复 rerun | 令牌/键在 `session_state` 中原样存活（§36） |
| DB 锁 | typed `STORAGE_UNAVAILABLE`；令牌保留；用户重试 |
| 校验失败 | typed `VALIDATION_FAILED`；令牌保留（载荷未变即可重试——但校验失败意味着载荷有问题，用户修正即触发 §14 失效，自然回到重新批准路径） |
| 来源漂移 | typed `SOURCE_REFERENCE_INVALID`；令牌保留；用户重审来源后：未改载荷重试仍失败（源仍漂移），改载荷 ⇒ §14 失效 ⇒ 重新批准 |
| commit-unknown | 提交已发生 ⇒ 重试=重放（免批准）；UI 收到重放成功后清令牌 |
| 响应丢失且未提交 | typed 失败；令牌+键保留；重试=首写 |
| 陈旧令牌复用（载荷已变） | §14 派生式失效已提前清令牌 ⇒ `APPROVAL_MISSING`；即使绕过（直接构造命令）⇒ `APPROVAL_MISMATCH` |

## 14. Approval Invalidation

### 14.1 语义编辑清单（任一发生 ⇒ 批准立即失效，无部分保留）

| 编辑 | 失效原因 |
| --- | --- |
| 任一区块文本（含 title/outcome/root_cause/各叙事块） | 文本参与哈希 |
| 任一区块 origin | origin 参与哈希 |
| 根因确认状态翻转（0↔1） | `root_cause_user_confirmed` 参与哈希（且是显式用户动作，非批准的副作用） |
| `creation_origin` 变化 | 参与哈希 |
| 来源成员变化（增/删任一关联） | 关联列表参与哈希 |
| 来源顺序重排 | 顺序是语义（§10.3） |
| 任一关联 `relation_kind` 变化（含 context↔support） | N-6：参与哈希 |
| 任一关联快照字段变化（fingerprint/fingerprint_version/target_revision/target_title/target_stable_id/target_type） | 全部参与哈希 |

### 14.2 失效机制（派生式，冻结）

实现不跟踪"编辑事件"，而是**每次渲染/提交前重算当前载荷哈希并与令牌比对**
（§36）：`token 存在 ∧ payload_sha256(当前载荷) ≠ token.approved_draft_sha256`
⇒ UI 清除令牌（令牌内嵌键 ⇒ 绑定的幂等键一并消失，无残留第二份 CREATE 键状态），
回到审阅态，提示"内容已变化，请重新确认"。单一真相（哈希比较）杜绝"漏记某个
编辑事件"类 bug。状态行为：
`APPROVED → 语义编辑 → 批准失效（含其键）→ 回 REVIEW/EDITING`；**无部分保留批准**。
下次批准按 §12.2 规则 1 生成**全新键** K2 + 新令牌（绝不复用旧键承载已变化的
逻辑意图，§15）。

## 15. Idempotency Key Lifecycle

### 15.1 核心规则（冻结；N-7 更正后）

1. **生成者与生成时机**：`uuid.uuid4()` 字符串（36 字符小写连字符）；格式由服务层
   校验（UUID 语法）；DB 层 `length BETWEEN 16 AND 64` + `UNIQUE`（schema 详规 A
   §18）。**非 AI 生成、非内容哈希派生、非时间戳派生。** 生成时机按操作分派
   （N-7 更正）：**CREATE 键在批准动作时生成**（§12.2 规则 1——键与授权同生，
   提交时绝无键生成点）；**undo/restore 键在该操作首次提交点击时生成**（无批准
   令牌，键稳定性由 §15.1 规则 5 的绑定对保证）。
2. **一个键 = 一个逻辑变异意图**。同语义命令的每次重试（未变载荷+未变键）**保留键**；
   语义变化 ⇒ 键随令牌一并清除，下次批准生成新键（CREATE）或下次提交生成新键
   （undo/restore）。
3. 键在**成功提交后不再复用**：同一键的逻辑命令已完成；任何新写（新草稿、undo、
   restore）= 新键。键本身随命令日志永久保留（审计 + 重放）。
4. 键不是授权（授权 = 令牌 ∧ 哈希匹配 ∧ 键在令牌范围内，§12.2）；键不是内容身份
   （同内容两次保存 = 两个键 = 两条经验——各自经独立批准，§31/§18 of 任务）。
5. 会话键稳定性机制按操作分派（N-7 更正后无重复真相）：**CREATE 的键由
   `ApprovalToken.approved_idempotency_key` 唯一承载**（令牌是唯一真相，无第二份
   CREATE 键状态；重试与 rerun 一律取令牌内键）；**undo/restore 的键**由
   `(operation, payload_sha256) → idempotency_key` 绑定对承载（§36）：重试时当前
   尝试的 `(operation, 规范载荷哈希)` 与绑定对一致 ⇒ 复用键；否则生成新键。

### 15.2 全事件生命周期表（冻结）

| # | 事件 | 键动作 | 令牌动作 |
| --- | --- | --- | --- |
| 1 | 初始草稿生成 | 无键 | 无令牌 |
| 2 | 用户编辑草稿（语义） | 无键（尚未生成） | 无令牌 |
| 3 | 用户批准 | **生成键 K**（原子地先于令牌；N-7） | **创建**令牌（绑定 P 哈希 + K） |
| 4 | 首次提交点击 | **无生成**——使用令牌内 K（N-7；CREATE 无提交期键生成点） | 保留 |
| 5 | 校验失败（未提交） | **保留**（同语义重试，键仍在令牌内） | 保留 |
| 6 | 来源陈旧失败 | **保留** | 保留 |
| 7 | DB busy/失败 | **保留** | 保留 |
| 8 | 语义编辑（在任一失败后） | **随令牌一并清除**（键内嵌于令牌，N-7） | **清除**（§14） |
| 9 | 重新批准 | 生成**新**键 K2（事件 3 规则） | 重建令牌（绑定 P2 + K2） |
| 10 | 再次提交 | 使用令牌内新键 K2 | 验证通过（§26 步骤 5 三条件） |
| 11 | 成功保存（首写） | 保留展示（命令完成，不再复用） | **消费**（清除，键随之消失） |
| 12 | commit-unknown → 重试 | **保留**（同键同载荷）→ 重放 | 保留 → 收到重放成功后消费 |
| 13 | 重复按钮点击（已提交后） | 保留 → 重放 | 已清除（无影响） |
| 14 | 幂等冲突（IDEMPOTENCY_CONFLICT） | **随令牌一并清除**（重试必须重新批准换新键；N-7 后 (P,K) 对被视为可疑） | **清除**（fail-closed） |
| 15 | 用户取消/新建草稿/重置 | 清除 | 清除 |
| 16 | undo/restore 点击 | 同规则 4 的 undo/restore 分派：首次点击生成（绑定对 (operation, payload_sha256)→键） | 不适用（无令牌） |
| 17 | undo/restore 失败重试 | 同规则 5（绑定对匹配则保留） | 不适用 |

## 16. Request ID Lifecycle

**裁决（二选一中冻结第一模型）**：

- `idempotency_key`：**逻辑用户变异意图**；UI 生成；跨重试稳定；持久化于命令日志
  （UNIQUE）。
- `request_id`：**一次执行尝试的关联身份**；**服务端**在每次执行尝试开始时生成
  `uuid4()`；每次实际尝试一个新值；**只贯穿净化应用日志**（§40）。
- 命令日志是 SUCCESS-ONLY ⇒ 行内 `request_id` 恒为**成功提交那一次尝试**的
  request_id。失败尝试的 request_id 只存在于应用日志，重放时与库内行无对应关系
  （属正常）。两个标识职责正交：键回答"这是哪次逻辑意图"，request_id 回答"这次
  尝试发生了什么"（日志贯通/排障）。request_id 不参与载荷哈希、不参与批准、
  不是幂等比较键。

## 17. Create Command Contract

### 17.1 `ExperienceWriteCommand`（冻结）

```python
@dataclass(frozen=True, slots=True)
class ExperienceWriteCommand:
    operation: ExperienceWriteOperation        # create | undo | restore（闭合 allowlist）
    idempotency_key: str                       # UI 生成 UUID4；重试稳定
    request_id: str                            # 服务端按次生成（UI 不提供）
    payload: ApprovedExperiencePayload | None  # 仅 create；非 None ⇔ operation is create
    approval: ApprovalToken | None             # 仅 create；非 None ⇔ operation is create
    agent_request_ref: str | None              # 仅 create 可非 None（§17.3）；≤128 字符
    target_stable_id: str | None               # 仅 undo/restore；非 None ⇔ operation 非 create
```

构造期一致性（工厂函数 `ExperienceWriteCommand.create(...)/.undo(...)/.restore(...)`
强制，服务层二次校验——不信任构造方）：

| operation | payload | approval | target_stable_id | agent_request_ref |
| --- | --- | --- | --- | --- |
| create | **必须**非 None | **必须**非 None | 必须为 None | 可 None / 可非 None |
| undo / restore | 必须为 None | 必须为 None | **必须**非 None | 必须为 None |

违反 ⇒ 构造期 `ValueError`（`VALIDATION_FAILED` 族；服务未进入）。

### 17.2 命令绝不包含

`raw model` 实例、provider、prompt、会话对象、DB 连接、UI widget 状态、内部 DB 整数
id、时间戳（时间由服务在事务内以 `_utc_now()` 生成）。命令是纯数据。

### 17.3 `agent_request_ref` 的位置（任务 §48 冻结）

- 属于**命令**（create 时由 UI/组装层从草稿生成上下文带入），**不属于规范载荷**
  （不参与哈希）；是持久化透明元数据（落 `knowledge_memory_entries.agent_request_ref`，
  ≤128 字符 DB CHECK）。
- **值规则**：若草稿生成链存在可信稳定请求 ID（如 AI 调用台账的持久 call uuid）则
  存它；**否则存 NULL。绝不为了填列而伪造 UUID。** 现行
  `AuditedExperienceOutput.audit_call_id` 恒为 `None`（`src/models.py:1639` 文档明示），
  故 v0.7 实现预期恒存 NULL，除非未来草稿服务暴露稳定 call uuid（届时仅改组装层）。
- 它不是批准权威、不是幂等键、不是 prompt 存储；create 后不可变（v0.7 无变更路径）。

### 17.4 create 载荷必含（§6.1）；服务从命令取载荷后

再规范化 → 哈希 → 与 approval 比对 → 域校验 → 来源校验 → 事务写入（§26）。

## 18. Undo Command Contract

- **无草稿批准哈希**（`approved_draft_sha256=NULL`；无令牌）。
- **授权 = 四条件合取**（缺一即 typed 拒绝）：
  1. 显式本地用户动作（UI 点击）；
  2. 服务仅可从批准的 Local UI 组装触达（§38；结构事实，非运行时检查项）；
  3. 目标存在受控 create 命令历史（`EXISTS(SELECT 1 FROM experience_command_log
     WHERE operation='create' AND target_stable_id=?)`，schema 详规 A §28；索引
     `idx_ecl_target` 支撑）；
  4. 当前 `status == 'active'`。
- **规范载荷（幂等键的哈希对象）**：§8.2 `target_command_payload_v1`
  `{operation:"undo", target_stable_id}`。
- **同键同载荷 → 重放**（返回首次 undo 结果，零写入，不要求任何授权凭证——日志行即
  既往授权的持久证明）；**同键 + 目标变了（=载荷哈希不同）→ `IDEMPOTENCY_CONFLICT`**
  （对 undo 而言"载荷"就是 operation+target；键复用于不同目标 = bug 信号）。
- undo 不删内容、不删来源链接、不碰 provenance、不 hard purge（schema 详规 A §25.2）。

## 19. Restore Command Contract

- 与 §18 同构：无 create 令牌；授权 = 显式动作 + Local 组装 + **受控 create 历史** +
  **当前 `status == 'deleted'`**。
- 规范载荷：`{operation:"restore", target_stable_id}`。
- 恢复目标状态恒为 `active`（v0.7 不存在 archived→deleted 路径；schema 详规 A §14）。
- 同键同载荷 → 重放；同键异载荷 → `IDEMPOTENCY_CONFLICT`。

## 21. Duplicate Replay Semantics

**重复重放是 typed 成功，不是异常**（任务红线；失败矩阵 `AlreadyCommitted → 重放成功`）。

**精确触发条件（全部满足）**：`idempotency_key` 在 `experience_command_log` 有行 ∧
行 `operation` == 命令 operation ∧ 行 `payload_sha256` == 当前尝试计算的
`payload_sha256`。

**重放行为（冻结）**：

```text
→ ExperienceWriteResult(
      operation=<行.operation>,
      target_stable_id=<行.target_stable_id>,
      duplicate_replay=True,
      first_committed_at=<行.created_at>)
  无 DB 变异（零 INSERT/UPDATE/DELETE）
  无新审计行
  无新 FTS 活动
  无新经验
  不要求 approval（令牌可缺席——日志行即既往授权的持久证明）
  不做任何当前语义校验（§29 规则：重放先于可变校验）
```

- `duplicate_replay=True` 的语义（逐字冻结）：**本次尝试未发生任何变异；结果是从
  既往成功命令日志重构的**。`False`：**本次事务提交了一笔新变异**。
- 服务以空事务 COMMIT 结束重放路径（schema 详规 A §25.1 步骤 3 的 COMMIT（空事务））。

## 22. Error Family

### 22.1 类型形状（TD-06 模式；`RagAnswerError`/`RagAnswerErrorCode` 为仓内先例）

```python
class ExperienceWriteErrorCode(StrEnum):
    VALIDATION_FAILED = "validation_failed"
    APPROVAL_MISSING = "approval_missing"
    APPROVAL_MISMATCH = "approval_mismatch"
    IDEMPOTENCY_CONFLICT = "idempotency_conflict"
    SOURCE_REFERENCE_INVALID = "source_reference_invalid"
    TARGET_NOT_FOUND = "target_not_found"
    STATUS_CONFLICT = "status_conflict"
    STORAGE_UNAVAILABLE = "storage_unavailable"
    WRITE_NOT_ALLOWED = "write_not_allowed"
    INTERNAL_FAILURE = "internal_failure"

class SourceReferenceReason(StrEnum):        # SOURCE_REFERENCE_INVALID 的闭合子码
    MISSING = "missing"                      # 目标行不存在（提交时已删）
    STALE = "stale"                          # 指纹/revision 与快照不等（漂移）
    UNVERIFIABLE = "unverifiable"            # 指纹无法计算(None)/配方版本错配——"无法校验"
    INVALID_TYPE = "invalid_type"            # 目标类型越 allowlist / stable_id 类型段不一致

class ApprovalMismatchReason(StrEnum):       # APPROVAL_MISMATCH 的闭合子码（N-7）
    PAYLOAD_MISMATCH = "payload_mismatch"            # 载荷哈希 ≠ 令牌绑定哈希
    COMMAND_KEY_MISMATCH = "command_key_mismatch"    # 命令键 ≠ 令牌绑定键（批准范围外的新键）

class ExperienceWriteError(RuntimeError):
    def __init__(self, code: ExperienceWriteErrorCode, message: str, *,
                 details: tuple[tuple[str, str], ...] = ()) -> None: ...
    # code：闭合机器语义；message：安全中文文案；details：可选安全结构化键值对
```

- 机器决策只认 `code`（+ `details` 的闭合键）；消息可独立改写而不改变分类
  （TD-06 消息独立性）。
- `details` 仅允许安全键：`("block_key", <8 值>)`、`("target_stable_id", <用户可见
  stable_id>)`、`("reason", <SourceReferenceReason 或 ApprovalMismatchReason 值>)`、
  `("field", <区块/字段名>)`。**绝不**携带来源正文、标题、路径、SQL、哈希原像、
  令牌内容。
- **未知异常 fail-closed**：任何未预期异常 → 整体回滚 → 映射 `INTERNAL_FAILURE`
  （仅安全消息 + 异常类名；§22.4）。

### 22.2 码 → 触发面映射（单点穷尽；schema 详规 A §36 全覆盖）

| code | 触发 | DB 副作用 | 可重试？ |
| --- | --- | --- | --- |
| `VALIDATION_FAILED` | 必填缺失/长度超限/区块结构非法/origin 非法/空块 origin 违规/outcome origin 违规/confirmed 一致性违规/序列化总长>20000/关联结构非法（越枚举、重复 (block,target)、歧义双关系、上下文携带新鲜度字段、支撑缺新鲜度字段、类型段不一致）/命令构造一致性违规 | 无（回滚） | 是（修正后） |
| `APPROVAL_MISSING` | 新键 create 无有效会话令牌 | 无 | 是（批准后） |
| `APPROVAL_MISMATCH` | 令牌在场但 (a) 载荷哈希 ≠ 令牌绑定哈希（批准后载荷被改，含 relation_kind 改动；reason=payload_mismatch）或 (b) 命令键 ≠ 令牌绑定键（同一令牌被另一个新键复用；reason=command_key_mismatch，N-7） | 无 | 是（重新批准后；重新批准生成全新键+令牌） |
| `IDEMPOTENCY_CONFLICT` | 同键已提交但 operation 或 payload_sha256 任一不同 | 无（回滚） | 否（必须换新键=新请求） |
| `SOURCE_REFERENCE_INVALID` | 关联目标缺失/漂移/无法校验/类型非法（details 携带 reason 子码） | 无（回滚） | 是（移除/更换/重审引用后） |
| `TARGET_NOT_FOUND` | undo/restore 目标 stable_id 不可解析为现存条目（含硬删后） | 无 | 否（静态事实） |
| `STATUS_CONFLICT` | undo 时 status≠active；restore 时 status≠deleted（含 archived） | 无 | 否（状态迁移后另当别论；重复 undo 新键属此类） |
| `STORAGE_UNAVAILABLE` | BEGIN IMMEDIATE 失败/DB 锁超时/事务内操作性错误/审计行插入失败（同事务回滚后呈现）/commit 异常无法判别时 | 无残留（全回滚） | 是（同键） |
| `WRITE_NOT_ALLOWED` | undo/restore 无 create 历史行（资格守卫）；假想的越 allowlist 操作触达服务 | 无 | 否 |
| `INTERNAL_FAILURE` | 未预期异常（含服务层理应拦截却被 DB 约束兜住的 IntegrityError——调用方 bug 信号） | 无残留（回滚） | 否（bug 信号） |

### 22.3 语义冲突 vs 存储不可用 vs 约束错误（任务 §29 冻结）

```text
DB 锁/busy/操作性失败          → STORAGE_UNAVAILABLE（机器语义：可重试的基础设施态）
非法当前目标状态               → STATUS_CONFLICT（机器语义：领域状态机拒绝）
幂等唯一冲突                   → IDEMPOTENCY_CONFLICT
服务层本应拦截的约束在 DB 层触发 → INTERNAL_FAILURE（fail-closed；绝不靠解析 SQL 文本分类）
```

分类永远基于异常**类型与捕获位置**，绝不基于消息文本（TD-06；仓内仅存的
`in str(exc)` 均为 SQLite vendor 协议串先例，本域不新增）。

### 22.4 UNKNOWN FAILURE（任务 §33 冻结）

未预期异常：回滚 → 映射 `INTERNAL_FAILURE` → 用户见安全消息；不泄漏 SQL、路径、
API 密钥、来源内容、prompt、provider 响应体、CoT。沿既有 secret-scrub 测试风格
（`tests/test_agent_final_answer.py:772` 先例）加 scrub 断言。

## 25. Public Service API

**裁决：三个显式方法，无泛型 `execute(command)` 分发。**

```python
class ExperienceWriteCommandService:
    def __init__(self, database: Database) -> None: ...
    def execute_create(self, command: ExperienceWriteCommand) -> ExperienceWriteResult: ...
    def execute_undo(self, command: ExperienceWriteCommand) -> ExperienceWriteResult: ...
    def execute_restore(self, command: ExperienceWriteCommand) -> ExperienceWriteResult: ...
```

- `operation` allowlist 已由命令构造期闭合；三方法各自直接实现，**无**动态处理器
  注册表、**无**插件命令框架、**无**反射分发。
- 与架构 "WriteCommand 概念" 的关系：概念由 `ExperienceWriteCommand` +
  `ExperienceWriteOperation` 承载；API 层显式化避免"单 execute + 内部 switch"的
  无收益间接层（仓内风格：服务方法显式、窄面，如 `KnowledgeMemoryService`）。
- 构造函数仅依赖 `Database`（Local 组合根注入 `application_database()`）；
  无 provider、无 settings、无 UI 依赖——写正确性不依赖 AI 可用性（§49 B 系列测试
  全部纯数据）。

## 26. Create Algorithm

schema 详规 A §25.1 冻结事务序在应用层的完整重述（顺序冻结；幂等解析在批准校验
**之前**）：

```text
execute_create(command):
  0. 命令一致性复验（§17.1 表；违反 → VALIDATION_FAILED，服务未进入事务）
  1. 幂等键语法校验（UUID；违反 → VALIDATION_FAILED，事务前）
  2. 载荷规范化重算（§6.2 步骤 4；纯函数）→ canonical_bytes + payload_sha256
     （此步只做"可解析 + 可规范化"，不做语义校验 —— §29）
  3. BEGIN IMMEDIATE（服务拥有唯一外层 knowledge_transaction）
  4. 幂等解析：SELECT * FROM experience_command_log WHERE idempotency_key = ?
     ├─ 有行 ∧ operation='create' ∧ payload_sha256 相同
     │    → 重放结果（§21；不查批准、不做任何后续校验）；COMMIT（空事务）；返回
     ├─ 有行 ∧ (operation 或 payload_sha256 任一不同)
     │    → ROLLBACK；IDEMPOTENCY_CONFLICT（与批准状态无关）
     └─ 无行（新键）→ 继续
  5. 批准校验（新键 CREATE 三条件；N-7）：
     a. command.approval 在场（否则 APPROVAL_MISSING）；
     b. payload_sha256 == approval.approved_draft_sha256
        （否则 APPROVAL_MISMATCH · payload_mismatch）；
     c. command.idempotency_key == approval.approved_idempotency_key
        （否则 APPROVAL_MISMATCH · command_key_mismatch——同一令牌携带任何其他
        新键都被服务层拒绝，一次批准至多授权一次逻辑变异）
  6. 域校验（§73 顺序：形状 → 区块不变量 → origin/确认 → 关联结构）；
     含 §5.4 序列化总长 ≤ 20000
  7. 来源校验（逐关联，事务内；§32：支撑=存在性+新鲜度相等；上下文=仅存在性；
     按 relation_kind 分派 —— N-6）
  8. 连接感知 INSERT 经验行（kind='experience'，status='active'，creation_origin，
     root_cause_user_confirmed，agent_request_ref，content=§5.2 规范序列化，
     四影子列同步写入）—— FTS insert 触发器同事务自动生效
  9. 连接感知 INSERT ×10 provenance 行（每 block_key 恰一行）
 10. 连接感知 INSERT ×N source 关联行（relation_kind + 快照列；插入前"恰好一目标"
     已由步骤 6 保证）
 11. build_stable_id(kb_uuid, 'knowledge_memory', 新行 id) → 连接感知 INSERT
     命令日志行（create：approved_draft_sha256=payload_sha256；creation_origin；
     target_stable_id；actor='local_user'；result='committed'；created_at=_utc_now()）
 12. COMMIT
 13. 返回 ExperienceWriteResult(create, target_stable_id, duplicate_replay=False,
     first_committed_at=日志行 created_at)
```

- 步骤 5-11 任一失败 → 整体回滚 → 经验/来源/provenance/FTS/日志**零残留** →
  用户见"保存失败，未写入任何数据"；同键重试 = 步骤 4 无行 = 正常首写
  （SUCCESS-ONLY 纪律，§41）。
- **新鲜度比较必须在事务内**（BEGIN IMMEDIATE 之后）对同一连接执行——事务外预检
  会制造 TOCTOU（任务 §37 红线）；本算法无任何事务外来源读取。
- stable_id 只能在 DB 整数 id 存在后构建（步骤 11 顺序冻结；无第二事务）。

## 27. Undo Algorithm

```text
execute_undo(command):
  0. 命令一致性复验（§17.1；target 必须在场）
  1. 幂等键语法校验
  2. canonical_bytes(§8.2 {operation:"undo", target_stable_id}) → payload_sha256
  3. BEGIN IMMEDIATE
  4. 幂等解析（同 §26 步骤 4；op='undo'）→ 重放 / IDEMPOTENCY_CONFLICT / 继续
  5. target_stable_id 解析（parse_source_id 严格文法）+ SELECT knowledge_memory_entries
     ├─ 不存在（含硬删）→ typed TARGET_NOT_FOUND；ROLLBACK
     └─ stable_id 的 kb_uuid ≠ 本库 kb_uuid 或类型段 ≠ knowledge_memory → TARGET_NOT_FOUND
  6. 资格：EXISTS(create 日志行, target_stable_id)（否则 WRITE_NOT_ALLOWED；不推断、
     不重建——历史损坏 fail-closed，schema 详规 A §28）
  7. 状态校验：status 必须 = 'active'（否则 STATUS_CONFLICT；archived 亦冲突）
  8. 连接感知 UPDATE status: active → deleted（update_knowledge_memory_status 的
     连接感知变体；FTS update 触发器自动重同步——内容不变，可见性由检索 status
     过滤承担，schema 详规 A §31 方案 A）
  9. 连接感知 INSERT 命令日志行（undo：approved NULL；creation_origin NULL）
 10. COMMIT；返回 ExperienceWriteResult(undo, target_stable_id, False, created_at)
```

不删内容、不删来源链接、不碰 provenance、不 hard purge。

## 29. Pre-transaction Validation Boundary

**原则（任务 §38/§69/§70 冻结）**：对携带幂等键的请求，**幂等查找必须发生在任何
可能随版本演化的语义校验之前**——否则新版本更严的校验会错误拒绝旧已提交命令的
合法重放（校验演化破坏重放兼容）。

### 29.1 三层边界

| 层 | 内容 | 时机 |
| --- | --- | --- |
| L0 构造期类型层 | 命令对象字段一致性（§17.1）、闭合枚举 | 工厂构造（服务未进入） |
| L1 传输级解析安全（事务前允许的全部） | 幂等键 UUID 语法；载荷结构可解析（字段存在/类型正确/枚举可解释）**足以规范化并计算哈希** | BEGIN IMMEDIATE 之前 |
| L2 语义校验（一律在幂等查找之后） | 批准、必填/长度、origin/确认、关联结构、来源存在性/新鲜度、目标状态/资格 | 事务内，新键路径 |

- L1 **故意不含**：长度上限、必填性、来源有效性——这些属于 L2，随版本演化不会
  折断重放。
- **恶意超大载荷**：v0.7 无网络传输面（进程内调用，载荷由本仓 UI 构造）；载荷
  结构上界由区块最大值 + 关联结构唯一性确定性界定（§29.2）；L2 的 §5.4 总长
  fail-closed 兜底。为假想传输面预设复杂限流 = 过度工程，拒绝；未来 Hosted 写
  （v0.7 明确不存在）若引入传输面，须在当时引入显式请求上限——本规格不做预设。
- L1 失败 ⇒ `VALIDATION_FAILED`（结构不可解析的载荷无法与任何历史行可信比较，
  fail-closed 合理且不破坏重放：不可解析载荷本就不可能曾被成功提交）。

### 29.2 载荷确定性上界（任务 §71）

| 项 | 上界 | 来源 |
| --- | --- | --- |
| 单区块文本 | 4000 码点 | §4.2（冻结） |
| content 序列化总长 | 20000（fail-closed） | §5.4 |
| 载荷正文本体 | title 200 + 6×4000 + outcome 4000 ≈ 24.2k 码点 → canonical JSON ≤ ~30 KB | 区块冻结值推论 |
| 来源关联数量 | **不新增数值上限**；自然上界 = 草稿装配仅从当前上下文包提供目标（`KnowledgeContextPackager.DEFAULT_MAX_ITEMS=100`，`src/knowledge_context_packager.py:29`）× 每项可关联 ≤8 块；DB 侧 UNIQUE(entry,block,stable_id) 收敛重复 | 任务红线"优先复用既有上限、无臆测大常数"；v0.7 无传输面 DoS 向量 |

## 30. Transaction / Commit-Unknown

### 30.1 事务所有权（承 schema 详规 A §25，重申）

- 服务拥有**唯一**外层 `knowledge_transaction`（`BEGIN IMMEDIATE` + 异常整体回滚，
  `src/database.py:1643`）；体内只允许连接感知调用（`_knowledge_scope(connection)`
  模式）；**禁止**调用自开事务的方法（嵌套 BEGIN IMMEDIATE 会直接抛
  "cannot start a transaction within a transaction"——结构性约束）。
- 无嵌套事务；无第二事务边界；审计/日志与数据写同事务（AUDIT_MUST_BE_ATOMIC，
  评审 §19）。

### 30.2 commit-unknown 精确边界（重申并接 §13/§15）

```text
BEGIN IMMEDIATE            ← 写锁取得，后续全部原子
  写经验/关联/provenance（连接感知）
  FTS 触发器同事务同步
  INSERT experience_command_log（行 = 提交标记）
COMMIT                     ← commit-unknown 窗口开启
（服务返回结果）            ← 窗口关闭
```

- **窗口内**任何崩溃/断连：事务整体回滚，日志行不存在 → 重试 = 首写（批准按 §13
  规则 B 仍在场，且令牌绑定同键同载荷，N-7）。
- **COMMIT 返回后响应丢失**：日志行已原子落库 → 同键同载荷重试 = 重放（免批准）。
  此时令牌与绑定键**仍在会话**（UI 未观察到成功，规则 B 未消费——§30.4 案 1）；
  重放后 UI 收到成功再消费。
- **重放的精确前提（承诺边界，冻结）**：重放要求**同一幂等键被再次呈现**。键是
  会话内状态——浏览器/会话消失后自动重放不可达，这是 **v0.7 明示接受的可用性
  边界，不是授权或持久性缺陷**：已提交变异本身安全落库（用户可到知识记忆页
  核实），且新会话无令牌，任何新写都必须重新批准（不可能因此产生重复或越权写）。
  日志的持久性（DB 内、随备份迁移）保证"只要键再现，重放必成"——本架构承诺的
  就是这一点，**不承诺**跨会话自动找回键；不为此持久化草稿/批准/键（无范围膨胀）。
- 无启发式恢复；**无内容哈希全局搜索**（"找一条内容一样的经验来顶替"被禁止——
  内容哈希不是命令身份）。
- 三操作（create/undo/restore）恢复语义一致（各自幂等键）。

### 30.3 提交异常的分类与 UI 保留物（任务 §67 冻结）

- 本地 SQLite 同进程可以**在同一连接上查证**：服务不猜测"是否已提交"；异常一律
  按 §22.2 分类（操作型 → `STORAGE_UNAVAILABLE`；未预期 → `INTERNAL_FAILURE`），
  以安全失败呈现。
- 失败后 UI **必须保留**（§36）：幂等键（+其载荷哈希绑定对）、同语义载荷、批准令牌
  （规则 B：未成功未消费）。
- 若该次其实已提交：同键重试 → 步骤 4 命中 → 重放。若未提交：重试 = 首写。
  **同一幂等键就是恢复机制**；无任何"人工核实后清理"流程。

### 30.4 批准 × commit-unknown 联合一致性（任务 §68 逐案冻结）

| 案 | 序列 | 结果 |
| --- | --- | --- |
| 1 | 批准 → 提交 COMMIT 成功 → 响应丢失（**令牌与绑定键仍在会话**——规则 B 的消费只发生在 UI 观察到成功结果时，服务无会话写回机制；N-7 更正措辞） | 重试同键同载荷 → 幂等命中 → **重放，不要求批准**（键绑定无关紧要：重放根本不查令牌）；UI 收到重放成功后消费令牌 |
| 2 | 批准 → 事务回滚（规则 B：令牌**未**被消费） | 重试同键同载荷 → 无行 → 批准校验三条件用**仍在场的令牌**通过（键在绑定范围内）→ 正常首写。幂等键仍未参与授权——授权是保留的有效令牌 |

## 31. Concurrency / Double-click

| 场景 | 机制 | 结果 |
| --- | --- | --- |
| 同键两尝试并发 | `BEGIN IMMEDIATE` 串行化 + `idempotency_key UNIQUE` + 事务内首查 | 一者获写锁提交；另一者随后观察到命令行 → 重放。**零重复经验** |
| 同键两尝试，第二者在第一者提交前进入查找 | BEGIN IMMEDIATE 使第二者等待；第一者提交后第二者获锁 → 命中重放 | 同上 |
| 异键 + 内容完全相同 + **各自独立批准**（各自令牌绑定各自键） | 内容哈希不是命令身份；键绑定使两次批准互不可替代 | **两条独立有效经验**——预期行为，文档化（§18 of 任务）；语义重复提示属草稿期纯 advisory（预研 §21），写入层绝不静默抑制 |
| **异键 + 内容完全相同 + 同一令牌**（N-7 攻击形态） | 服务层键范围校验（§26 步骤 5c）：第二键 ≠ token.approved_idempotency_key | 第二命令 `APPROVAL_MISMATCH`·command_key_mismatch；**恰一次变异**；零第二个键的写入 |
| 双击（UI 层） | UI disable/debounce 仅为 UX | **正确性绝不依赖 UI 防抖**；数据库幂等是唯一权威（任务 §53 冻结语句） |

## 32. Source Validation

### 32.1 逐关联命令层校验清单（事务内；新键 create 路径）

对每条 `SourceAssociationDraft`：

1. `block_key` ∈ 8 关联允许块（title/outcome 出现 ⇒ `VALIDATION_FAILED`）；
2. `relation_kind` ∈ {support, context}；
3. `target_type` ∈ {page, knowledge_object, evidence}；
4. `target_stable_id` 经 `parse_source_id` 严格解析（`src/source_metadata.py:34`）
   且类型段 == `target_type` 且 kb_uuid 段 == 本库 uuid（否则 `INVALID_TYPE`）；
5. **恰一个真实存活目标解析**：按类型 SELECT 目标行；缺失 → `MISSING`；
6. 无重复 `(block_key, target_stable_id)`（含歧义双关系；§11.2 → `VALIDATION_FAILED`）；
7. `target_title` = 批准展示快照（§32.3，不做新鲜度比较）；
8. **support**：page/evidence ⇒ 快照 fingerprint+fingerprint_version 必备，提交时
   重算 `compute_source_fingerprint(conn, type, id)` 与快照逐字节相等（不等 →
   `STALE`；重算返回 None 或 fingerprint_version ≠ 1 错配 → `UNVERIFIABLE`）；
   knowledge_object ⇒ 快照 target_revision 必备，提交时
   `SELECT current_revision` 与快照相等（不等 → `STALE`；行缺失 → `MISSING`；
   **不用指纹**——v1 配方不含 KO，不发明新配方，schema 详规 A §12）；
9. **context**：新鲜度三字段必须整体缺席（载荷层）；仅做存在性校验（存在即可，
   不比较任何内容）；
10. 支撑行提交时新鲜度证明不可用（目标未删未变但指纹无法计算/revision 缺失）→
    `UNVERIFIABLE` fail-closed（失败矩阵 #22）。

### 32.2 按关系分派（N-6，重申）

`support` = 存在性 + 新鲜度相等；`context` = 仅存在性。同一 8 块集合对两类关系
合法；差异只在快照要求与校验强度。

### 32.3 `target_title` 的角色（任务 §44 冻结：方案 A）

**target_title 是批准/展示快照，不是新鲜度判据；提交时不与当前标题比较。**
理由：标题是显示标签；对 page/evidence，内容漂移已由指纹覆盖；对 KO，内容修订
已由 `current_revision` 覆盖。把无害重命名变成"来源失效"会制造虚假漂移信号，
违背"不重写语义"纪律。`target_title` 仍参与批准哈希（用户批准的是所见展示），
改名后的重批由用户编辑触发（§14）。

### 32.4 提交后删除边界（任务 §45 冻结）

WriteCommand **只在提交时**校验来源。提交成功后目标被删（`ON DELETE SET NULL`）
不是任何写命令的失败，而是**读时状态**：support → MISSING_SUPPORT；context →
MISSING_CONTEXT（分立派生，schema 详规 A §13；永不合并、永不回写）。
读模型按 relation_kind 分立呈现（任务 §45 四态：live support / missing support /
live context / missing context）。

## 33. Root Cause Confirmation

冻结规则（承 schema 详规 A §9 与评审 §11，逐条可校验）：

```text
root_cause_user_confirmed = 1 当且仅当全部成立：
  R1  creation_origin == 'agent_assisted'
  R2  root_cause 区块 text 非空
  R3  root_cause 区块 origin == 'user_asserted'
  R4  用户在整稿批准之前执行了显式"确认根因"动作（会话事实，随载荷绑定）
```

- **整稿批准本身不升格根因**（批准只授权 mutation，不改变认识论标记——ADR-011 §2；
  上游预期确认）。
- `root_cause_user_confirmed` **参与规范哈希**：确认状态翻转 = 语义编辑 = 批准失效
  （§14）。
- 违反 R1/R2/R3 的载荷 ⇒ `VALIDATION_FAILED`；DB 跨列 CHECK
  `(root_cause_user_confirmed = 0 OR length(root_cause) > 0)` 是第二道防线（schema
  详规 A §5.2）；R1/R3 由服务层强制（DB 无法跨行表达 origin 行与列的一致性）。
- `creation_origin == 'human'` ⇒ confirmed 恒 0（人类路径无确认门概念；schema 详规
  A §9）。
- create 后 confirmed 不可变（v0.7 无变更路径；`update_knowledge_memory_entry`
  冻结不得加入该列赋值面——schema 详规 A §9）。

## 34. Draft → Approval Handoff

| 契约点 | 冻结 |

## 35. UI Session State Machine

### 35.1 状态集（最小化；与失败矩阵 §2.1 命名对齐）

```text
IDLE → DRAFTING → DRAFT_READY ⇄ EDITING → APPROVAL_READY → SAVING → SAVED
（失败迁移回 EDITING/IDLE；undo/restore 是知识记忆页独立命令流，不属于草稿状态机）
```

不引入 SAVE_FAILED/UNDONE/RESTORED 会话态：typed 失败回 EDITING（草稿保留+错误
呈现，失败矩阵 §2.3）；undone/restored 是**持久实体状态**（status），由读面呈现，
不复制进会话状态机（避免不必要状态）。

### 35.2 转换表（冻结；令牌/键动作与 §13/§15 一致）

## 36. Streamlit Rerun Safety

### 36.1 会话键与存活规则（冻结；N-7 更正后——无重复真相）

| `st.session_state` 键 | 内容 | rerun 间 | 清除时机 |
| --- | --- | --- | --- |
| `experience_draft` | `ExperienceDraft`（不可变实例） | 存活 | 新建草稿/重置（§35.2 #14） |
| `experience_approval` | `ApprovalToken \| None`（**内嵌 CREATE 键**——CREATE 键绑定的唯一真相，N-7） | 存活 | 派生失效（§14）/成功消费/冲突 fail-closed/重置 |
| `experience_pending_command` | **仅 undo/restore**：`(operation, payload_sha256) → idempotency_key` 绑定对（二者无令牌，键稳定性由此承载） | 存活 | 语义变更（目标/载荷变化）/冲突/重置/操作完成 |
| `experience_last_result` | `ExperienceWriteResult \| None` | 存活 | 新一轮命令发起 |
| 规范载荷哈希预览 | **不单独存**——每次由 draft 纯函数重算（成本微秒级；单一真相防漂移） | — | — |

**为什么 CREATE 不再占用 `experience_pending_command`（§29 选型 A）**：令牌内嵌键
后，若再保留一份 CREATE 绑定对即出现两份键真相，存在失配面（任务 §29 的风险 C）。
冻结：**CREATE 的键唯一由令牌承载**，pending 绑定对仅服务 undo/restore 重试；
两槽职责正交，不建统一工作流类（避免泛化）。

### 36.2 重跑安全不变量（冻结；N-7 更正后）

1. **rerun 绝不为同一 CREATE 命令生成第二个键**：CREATE 键只在批准动作内生成一次
   （§12.2 规则 1）；提交/重试/rerun 一律取 `token.approved_idempotency_key`，
   **提交路径不存在任何键生成点**（比键生成点更少的机制，结构性更强）。
2. **undo/restore 的 rerun 绝不生成第二个键**：键只在"提交点击分支 ∧ 绑定对与当前
   (operation, 载荷哈希) 不一致"时生成（§15.1 规则 5 的 undo/restore 分派）；同键
   重试的 rerun 命中既有绑定对。
3. **rerun 绝不清除令牌/键**（它们只按 §35.2 表的动作清除）。
4. 语义编辑的检测是**派生式**的（当前哈希 vs 令牌哈希），不依赖"捕获 onChange 事件"，
   对 rerun 模型天然稳健。
5. 提交期间的 rerun（失败矩阵 #18）：命令若已发出，后端照常完成或失败；会话重建后
   按 #12/#11 呈现；幂等层保证无重复。
6. 正确性不依赖任何 UI 防抖/禁用（§31）；**授权正确性也不依赖 UI 键管理**——服务层
   键范围校验（§26 步骤 5c）独立兜底（N-7 核心结论）。

## 42. Backup/Restore Interaction

- 命令日志/经验/关联/ provenance 随 SQLite backup API 全库复制自动入备份
  （schema 详规 A §33）。
- **数据库回卷语义（冻结）**：恢复到早于某次成功命令的备份点 ⇒ 命令行与经验俱不在
  ⇒ 应用对该命令零知识 ⇒ 同键稍后提交 = 首写（语义自洽）。**无跨备份全局幂等**；
  **不发明外部台账**；**不做命令重放进恢复**（会伪造从未发生的历史）。
- 恢复点晚于提交 ⇒ 日志随库恢复 ⇒ 同键重试 = 重放（原样）。

## 43. Historical Replay Semantics

### 43.1 幂等回答的问题（冻结）

幂等重放回答 **"这条命令提交过吗"**，**不回答** "它的目标今天还存在吗 / 是什么
状态"。历史真实性优先。

### 43.2 目标其后被硬删（任务 §77：方案 A）

同键 create 重放 → 返回历史成功结果（`duplicate_replay=True`、原 target_stable_id、
原 first_committed_at），即使当前目标已不存在。UI 如实呈现"该记录曾保存于
<stable_id>"级别的信息由读面另行呈现；**不重建内容**。

### 43.3 目标其后被 restore（任务 §79/§80：方案 A）

undo 键 U 已提交；restore 键 R 后续提交；稍后重试 U → **返回 U 的历史成功结果
（duplicate_replay=True）且绝不改变当前状态**（不重跑 undo）。幂等语义不允许
"按当前状态重新执行"——那会把幂等层变成状态同步器，破坏"一个键 = 一次逻辑意图"
的核心语义。

### 43.4 结果契约不得误述当前状态（任务 §80）

`ExperienceWriteResult` 无当前状态字段（§20）；`first_committed_at` 明确命名为
"首次提交时刻"而非"当前状态时刻"。操作提交效果（operation_committed_effect）与
目标当前状态（current_target_state）严格分离；后者永远来自读面实时查询。
