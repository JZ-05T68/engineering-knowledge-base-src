# ADR-010: v0.7 Controlled Write Boundary — Deterministic WriteCommand Outside the Agent Tool Registry

- **Status:** PROPOSED（待维护者 / DeepSeek-Pro 评审，未经批准不得实现）
- **Date:** 2026-08-29
- **Deciders:** EKB maintainer（本地单用户工程知识库）
- **Scope:** v0.7 Personal Experience 的 READ_ONLY → CONTROLLED_WRITE 边界
- **Supersedes:** 无；扩展 ADR-006 的只读 Agent 约束，不修改其单步执行决定

## Context

EKB 现行 Agent 是 ADR-006 冻结的单步、只读执行结构：Tool Registry 恰有七个
`READ_ONLY` Tool，每次 run 最多一次 Tool call，Agent 自主重试为零。现有 Tool
负责确定性本地读取；Final Answer 是回答阶段而不是 Tool。Hosted 又由 ADR-007
保持结构性只读。

v0.7 的目标不是让 Agent 自主修改知识库，而是允许本地用户把真实工程结局整理成
Personal Experience 草稿，在看清完整内容后显式批准，再由确定性应用代码写入现有
Knowledge Memory。该能力第一次跨过 READ_ONLY 边界，因此必须明确谁能发起、谁能
批准、谁能校验、谁能提交，以及失败、重试和提示注入不能越过的边界。

## Problem

若把写入表示成 Agent Tool，模型选择 Tool 的行为就会成为写工作流的触发面；导入文档
或检索结果中的提示注入也会更接近副作用路径。若把 propose→approve→commit 放入多步
Agent 循环，批准将被错误地建模为 Agent run 内的一个步骤，同时引入 ADR-006 明确延后的
循环、回滚、预算和副作用语义。

必须在不改变现行 Agent 结构的前提下回答：如何允许用户批准的窄写入，同时保证模型、
Agent、Tool 输出和导入内容都永远不能自行提交 mutation。

## Constraints

1. Local-first、单用户、默认离线；核心能力不依赖云服务。
2. 用户资料未经显式确认不得被修改；原始 PDF、页面图像和导入正文不得由该能力改写。
3. 现行七个 Agent Tool 必须保持 `READ_ONLY`，不得增加第八个 WRITE Tool。
4. 单步 Agent executor 保持不变；不得引入 autonomous propose→write loop。
5. 草稿只存在于 UI session/in-memory；v0.7 不建草稿表，不持久聊天历史。
6. v0.7 mutation 仅在 Local 组合根装配；Hosted 保持只读，不新增公共写端点。
7. 写入必须可审计、幂等、可撤销；审计失败不得留下成功 mutation。
8. 本 ADR 只冻结设计；不实施 schema、代码、测试或迁移。

## Decision

### 1. 采用方案 B：Agent 执行之外的确定性 WriteCommand

v0.7 的 mutation 表示为应用层 `WriteCommand`；创建经验时可使用概念上的
`ExperienceWriteCommand` 作为具体命令类型。命令服务不属于 Agent Tool Registry，
不由模型选择，不由 Agent executor 调度，也不向模型暴露提交能力。

唯一允许的流程为：

```text
用户显式点击“沉淀为工程经验”
  -> 只读检索 / 经审计且受预算约束的草稿生成
  -> session-only 草稿
  -> 用户审阅、编辑并显式批准完整规范载荷
  -> UI 构造同一幂等键的 WriteCommand
  -> 应用服务确定性校验
  -> 单一 BEGIN IMMEDIATE 事务提交或完整回滚
```

提案阶段可以使用现行只读 Agent 与 ExperienceModelService 风格的 AI 组织能力；提交阶段
不允许任何模型调用或 Agent 决策。Agent 的产出始终只是 proposal。

### 2. Tool Registry 与 executor 不变

- Registry 仍恰有七个 `READ_ONLY` Tool；不得注册 WRITE Tool。
- 单步 executor 的 Tool call 上限、模型调用边界和 autonomous retry=0 保持不变。
- `knowledge_search` 与 `get_knowledge_memory` 继续承担写后读取；不为 v0.7 新增读 Tool。
- WriteCommand 使用独立应用服务入口；不得把它隐藏在现有 Tool Adapter 内。

### 3. 写 allowlist

v0.7 只允许：

1. 创建一条 `knowledge_memory_entries`，且 `kind = experience`；
2. 对由该受控命令链创建的经验执行显式 undo（软删除 / tombstone）；
3. 对该墓碑执行显式 restore。

不允许编辑导入文档、修改指纹、删除源文件、批量 mutation、后台学习、自动知识维护、
Agent-assisted post-create revision 或 hard purge。普通用户手工编辑现有 Knowledge Memory
仍属于既有 UI 能力，不因此获得 Agent 自动修订语义。

## Authority model

| 参与者 | 权威 | 明确不具备的权威 |
| --- | --- | --- |
| 导入来源、文档、Tool 内容 | 信息权威（information only） | 发起、批准或提交 mutation |
| 模型 | 提案与组织权威（proposal/organization only） | 把自身输出当作事实或提交 mutation |
| Agent | 提案编排权威（proposal/orchestration only） | mutation approval / commit |
| 用户 | 唯一显式 mutation approval authority | 绕过应用校验或 DB 约束 |
| 应用服务 | policy enforcement authority | 替用户创造批准意图 |
| 数据库 | 确定性校验通过后的 commit authority | 解释提示、推断事实或放宽 allowlist |

任何导入文本、引用、ToolResult 或模型输出中出现“保存”“批准”“执行写入”等指令，都只是
普通数据，对写入的触发与批准权威为零。只有用户对本地 UI 的显式动作可以启动草稿流程；
只有用户对屏幕上完整草稿的显式批准可以进入提交。

## Approval boundary

批准是 session-scoped、one-shot 的用户意图，表示为：

```text
approved_draft_sha256 + approved_at
```

`approved_draft_sha256` 必须基于用户可见完整载荷的确定性规范序列化计算，覆盖所有内容
区块、origin/provenance 标记和来源引用；不得有未显示却参与提交的可变隐藏字段。

提交前应用服务必须重新规范化载荷并计算哈希：

- 无批准令牌：`ApprovalMissing`；
- 哈希不同：`ApprovalMismatch`，拒绝写入并要求重新批准；
- 哈希相同：才可继续域校验和事务。

批准后任何内容或引用变化都使批准失效。这一哈希绑定关闭 TOCTOU 窗口，保证落库载荷
就是用户所见、所批的载荷。批准本身不持久化、不跨 session、不充当可重放授权凭据；
提交成功后立即消费并清除。批准 mutation 不等于把所有 AI 推断自动升级为用户确认事实，
认识论标记规则由 ADR-011 冻结。

## Transaction, idempotency and audit boundary

一个成功命令必须在同一个 `BEGIN IMMEDIATE` 事务中形成完整状态：经验行、来源/
provenance 链接、FTS 可见状态、write audit、持久化幂等结果。任何一步失败均整笔回滚；
不存在“写成功但审计失败”的可接受状态。

UI 首次构造命令时生成 UUID-style `idempotency_key`，重试保持不变。持久化
`experience_command_log` 至少绑定 key、payload hash、批准 hash、operation、目标结果和
时间：

- 同 key + 同 payload：重放首次成功结果，不创建第二条经验；
- 同 key + 不同 payload：`IdempotencyConflict`，fail-closed；
- COMMIT 成功但响应丢失：同 key 重试从持久日志恢复原结果，即 commit-unknown 闭环。

write audit 与幂等结果可由同一 append-only 命令日志行承担，但其原子性和最小数据原则
不可弱化：只存标识、类别、hash、长度、目标与时间，不存草稿正文、完整 prompt、
chain-of-thought、provider reasoning、密钥或私有路径。

## Security invariants

以下不变量为实现与测试的 fail-closed 门禁：

1. 模型、Agent、七个 Tool、导入来源和 prompt 文本均没有 write authority。
2. 只有显式本地 UI 动作能启动写工作流；只有精确载荷的显式批准能提交。
3. 写入载荷必须等于批准载荷；变化后必须重新批准。
4. 同一幂等键永不创建第二条经验。
5. 无 write audit 的成功 mutation 不可达。
6. 事务失败不留下经验、链接、FTS、审计或幂等部分状态。
7. undo/restore 是用户显式、可审计的墓碑状态迁移；v0.7 不 hard purge。
8. Hosted 不 import、不构造、不暴露 WriteCommand 服务；Hosted 始终 READ_ONLY。
9. v0.7 不持久聊天历史、不持久草稿、不引入多步 Agent mutation。

## Consequences

### Positive

- 模型选择空间与 mutation 提交面结构性分离，提示注入不能直接抵达写入口。
- 复用七个只读 Tool、单步 executor、Knowledge Memory 读链路和 FTS，不复制系统。
- 哈希批准、持久幂等和原子审计共同覆盖 TOCTOU、双击和 commit-unknown。
- Local 与 Hosted 的能力边界清晰；Hosted 无需新增认证、写 API 或多用户语义。

### Costs and limitations

- UI 与应用服务需要独立状态机和命令契约，不能复用 Tool 调用协议。
- 草稿随 session 消失，不提供崩溃恢复；这是 v0.7 的主动隐私/复杂度取舍。
- v0.7 仅 create + undo/restore；Agent-assisted post-create revision 延后。
- schema v13 与 TD-04/05/06 整改仍须在实现前/发布前按计划完成。

## Rejected alternatives

### A. WRITE Agent Tool

**Rejected for v0.7.** 即使 Tool 外包一层批准参数，模型仍获得选择副作用入口的能力，
prompt injection 面直通写路径；Registry 的七个只读 Tool 不变量被打破；executor 还需理解
副作用、commit-unknown、回滚和重放。它没有给用户批准流程带来 WriteCommand 之外的收益。

### B. Deterministic WriteCommand outside Agent execution

**Selected.** 用户 UI 动作是唯一触发，应用服务执行 allowlist、批准哈希、引用、幂等和
事务校验，数据库只提交确定性结果。Agent/model 无提交能力，现行执行器不变。

### C. Multi-step/autonomous propose→write Agent workflow

**Rejected for v0.7.** 批准是两个 run 之间的人类动作，不是 Agent 循环中的机器步骤。
多步自主工作流会引入 loop detection、跨步骤授权、付费重试、部分失败和回滚语义，既超出
本里程碑，也与 ADR-006 的单步边界冲突。v0.7 只吸收“提案→人批→提交”的两阶段语义，
不吸收 autonomous loop。
