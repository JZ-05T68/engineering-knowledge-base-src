## 2. ADR 逐项实现审计

### 2.1 V53-ADR-01 — ContextItem 统一投影契约

#### 已有能力

| 能力 | 现状 | 证据 |
|---|---|---|
| 页面投影 | `SearchResult` 字段齐全（page_id/document_id/title/filename/page_number/content/snippet/status/tags/projects/extracted/ocr/markdown/updated_at） | `src/models.py:451-475` |
| KO 投影 | `KnowledgeObjectView`（本体+来源+双向关系）+ `KnowledgeSearchResult(knowledge_object)`（含 stable_id/kind/status/source_anchors） | `src/models.py:1379-1389`、`:1325-1348` |
| Memory 投影 | `KnowledgeMemoryEntry` + `KnowledgeSearchResult(knowledge_memory)` | `src/models.py:1290-1302` |
| Evidence 投影 | `EvidenceItem` 字段齐全（evidence_text/选区/来源页面/确认状态/区域信息） | `src/models.py:509-544` |

#### 缺口

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **无统一知识消费模型** | 页面用 `SearchResult`，知识用 `KnowledgeSearchResult`，Evidence 无检索投影——三套形状，无 `ContextItem` |
| 2 | page/evidence 无 `stable_id` | `build_stable_id` 仅 5 类知识类型，页面/证据无法被统一引用 |
| 3 | 无统一 `SourceAnchor` / `RelationRef` 结构 | `KnowledgeSearchResult.source_anchors` 是 `tuple[(str,int),...]`，不含指纹状态；KO view 的来源含指纹但形状不同 |
| 4 | 无集中投影服务 | 投影逻辑散在 `database.py`/`search_service.py`/`knowledge_search_service.py`/`knowledge_object_service.py` |
| 5 | 页面文本优先级（extracted→ocr→markdown）未固化为独立投影规则 | 现有页面搜索水合分散在检索层，未作为 ContextItem 投影契约 |

#### 涉及文件

`src/models.py`、`src/database.py`、`src/search_service.py`、`src/knowledge_search_service.py`、
`src/knowledge_object_service.py`、`src/evidence_basket_service.py`、`src/evidence_service.py`。

#### 风险

- 若在现有两套结果模型上打补丁而非引入独立 ContextItem，会加剧模型分裂。
- 投影读路径必须只读（不得重算并回写指纹），否则违反 v0.5.2 ADR-03。
- stable_id 扩展 page/evidence 会改动 `build_stable_id` 契约，需同步导出与引用测试。

- Packager 的 Markdown 结构若与三个构建器重叠，会拉大测试面；建议 Packager 作为"统一消费层"，

| 新增关联表 | `knowledge_project_links`（project_id + target_type + target_id + UNIQUE） |

| 新增 UI | 知识记忆页：outcome/context_conditions 表单；知识对象/记忆页：project 选择器；项目管理页：知识资产挂接列表 |

#### 涉及文件

`src/migrations.py`、`src/models.py`、`src/database.py`、`src/knowledge_memory_service.py`、
`pages/14_知识对象.py`、`pages/15_知识记忆.py`、`pages/10_项目管理.py`、相关 `knowledge_*_ui.py`。

#### 风险

- `content_revision` 递增逻辑必须与 KO 的 `current_revision` 语义区分（Memory 只有版本号，无 before/after）。
- project link 是多态引用：SQLite 无多态 FK，服务层必须写前校验目标存在（沿用 source link 模式）。
- outcome/context_conditions 暂不进 FTS（ADR R1 已记录）：用户对"结果/适用条件"的检索预期需管理。

### 2.6 V53-ADR-07 — stable ID 扩展审计

#### 当前 `build_stable_id` 支持

| 类型常量 | 值 |
|---|---|
| `KNOWLEDGE_OBJECT_STABLE_TYPE` | `knowledge_object` |
| `KNOWLEDGE_MEMORY_STABLE_TYPE` | `knowledge_memory` |
| `KNOWLEDGE_RELATION_STABLE_TYPE` | `knowledge_relation` |
| `KNOWLEDGE_SOURCE_STABLE_TYPE` | `knowledge_source` |
| `KNOWLEDGE_REVISION_STABLE_TYPE` | `knowledge_revision` |

证据：`src/models.py:1393-1405`（`_KNOWN_STABLE_TYPES` 冻结集合）。

#### 确认结论

- **需要增加**：`page`、`evidence` 两个类型常量并加入 `_KNOWN_STABLE_TYPES`。
- 影响面（无 schema 变更，仅纯函数层）：
  - `src/models.py`：新增两个常量 + 集合扩展；
  - `src/database.py`：可新增 `page_stable_id`/`evidence_stable_id` 便捷方法（与
    `knowledge_object_stable_id` 同构）；
  - ContextItem 投影与结构化导出使用扩展命名空间。
- 既有 5 类 id 的生成不得变化（回归测试保护既有快照）。

#### 风险

- 与 v0.5.2 ADR-07 的导出命名空间存在修订关系，Phase 5 导出实现必须同步本扩展（ADR R4）。
- 扩展命名空间后，任何拼接逻辑都必须走 `build_stable_id`，禁止散落手写字符串。

### 5.1 Migration 测试

### 5.2 ContextItem 测试

- 四类投影字段完整性与类型；缺失字段为 None/空字符串、不伪造 importance。
- 页面文本优先级（extracted→ocr→markdown）；目标不存在 fail-closed（不返回半成品）。

- stable_id 对四类投影非空（page/evidence 使用扩展命名空间）。

### 5.3 ContextPackage fail-closed 测试

- 空 items 拒绝；全部排除拒绝；allow_partial 时失败项进 excluded。
- archived/superseded 默认排除且写入 excluded；显式包含带历史徽标。
- CHANGED/MISSING/UNKNOWN 来源保留+标注；字符截断与总上限拒绝。
- JSON+Markdown 双输出；manifest/citations/excluded 结构；五项必含信息（来源/版本/状态/关系/stable_id）。
- 无 AI 调用、无自动排序、保持输入顺序。

### 5.4 AI 调用台账测试

- success/error/rejected 三态；prompt_sha256 有值且原文不落库（负向）。
- retry_count/latency_ms/tokens/finish_reason/error_class 记录正确。
- 预算预检超限 → rejected 且零网络调用（transport 未触发）。
- 台账写失败不阻断业务返回；wrapper 不改变 provider 返回值/异常类型。
- API Key 不出现在任何表/日志/异常（负向断言）。

### 5.5 Experience Model 测试

- Memory outcome/context_conditions ≤4000 校验；content_revision 编辑递增、创建为 1。
- project link 建立/UNIQUE 去重/目标不存在拒绝/项目删除级联只删链接/KO 或 Memory 删除级联。
- 六类资产落点映射（错误/方法/判断/项目记录/决策/结果）服务层构造断言。

### 5.6 备份恢复测试

- 完整备份/恢复覆盖 ai_calls/ai_outputs/project links；恢复后行数与哈希一致。
- v8 备份隔离升级八步状态机成功与每步失败注入（原备份字节不变）。
- 结构化导出格式 1.0：manifest/kb_uuid/stable_id 交叉引用/排除 API Key 与 embedding 负向。

## 6. 风险清单

| # | 风险 | 分析 | 缓解 |
|---|---|---|---|
| R1 | 污染用户知识 | ai_outputs 只登记不写 KO；project link 只关联；Memory 新列默认空、不覆盖；迁移回填不虚构；服务层保持拒绝 `authorship='ai'` | 服务层负向测试 + 审计 |
| R2 | 泄露 API Key | 台账字段不含 key；wrapper 不打印；key 仅在运行时解包一次 | 负向断言：表/日志/异常/备份不含 key |
| R3 | AI 自动写入知识 | v0.5.3 不新增任何 AI→KO/Memory/笔记自动写路径；ai_outputs ≠ 知识本体 | 代码审计 + 负向测试 |
| R4 | 引入 Agent 逻辑 | Packager 只组装显式输入；无循环、无自动选择、无自动重试付费 | fail-closed 测试 + 审计 |
| R5 | 破坏离线能力 | 台账仅在有 provider 且真实调用时写；离线路径不经 wrapper；无 Key 时 provider=None，全部离线功能不变 | 全量回归 + 无 Key 启动验收 |

- R6：台账写库与 AI 调用事务边界（避免阻塞与死锁）。
- R7：`build_stable_id` 扩展 page/evidence 对既有 5 类 id 与测试快照的回归。
