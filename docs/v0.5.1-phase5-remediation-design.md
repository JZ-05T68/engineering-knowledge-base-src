## Track A — D-01 Indexing Coverage

### 生命周期与 file:line 证据

| 阶段 | 证据 | 行为 |
|---|---|---|
| 页面/内容创建或导入 | `src/pdf_service.py` / `document_service.py`（不在本审计深入） | 建 Page，`searchable_content` = reviewed Markdown→OCR→extracted |
| 文本可用性 | `page_indexer.prepare_page_text` (page_indexer.py:94-111) | 空/空白页返回 `None` 跳过；否则截断 8000 字符 + 算 sha256 |
| missing/stale 检测 | `_classify_pages` (page_indexer.py:340-362) | 用 `get_fresh_page_embedding` 判定 fresh→REUSED，否则 INDEXED(missing/stale) |
| 索引编排 | `PageEmbeddingIndexer.index_pages` (page_indexer.py:234-319) | 只 embed missing/stale，分批 ≤20，retry=0，成本精确计数 |
| 持久化 | `upsert_page_embedding` (database.py:1434) | 写 schema v8 `page_embeddings` |
| 向量召回资格 | `recall_scored` (vector_recall.py:207-209) | 无 fresh row 的页被 `continue` 跳过，**永不进向量候选** |

### 七个问题的答案

1. **哪些非空页当前可被索引？** 任何 `prepare_page_text(searchable_content) != None` 的页
   （即 `searchable_content` 非空）。无其它准入门槛。

2. **missing vs stale 如何检测？** `_classify_pages` 用 `get_fresh_page_embedding(page_id,
   sha256, model, dimensions, config_version)`：无匹配 row = missing；有 row 但
   `source_text_sha256` 不匹配 = stale（文本已变）。二者都归为 `PageIndexStatus.INDEXED`
   （需重新生成）。

3. **什么用户/动作触发索引？** **没有 UI 触发入口**。`PageEmbeddingIndexer` 只被独立的
   命令行脚本 `scripts/ai_real_page_index.py`（手动、需 `--confirm-paid-call`）与测试调用。
   生产 Streamlit 页面（`pages/*`）与 `runtime.py` 均无索引入口。

4. **页能永久无嵌入而无可视警告吗？** **能。** 无 UI 覆盖率展示、无"未嵌入"标记、
   无提示。partial-coverage 页在 hybrid 下静默缺失向量贡献，用户无感知。

5. **页面文本变更后发生什么？** 无自动机制。旧 row 在下次 recall 时因 `source_text_sha256`
   不匹配被判定 stale（跳过），但仍需手动重跑索引脚本才会重新生成。文本变更期间该页
   向量召回静默失效。

6. **已有可复用覆盖率 summary API？** **没有独立的 coverage 统计服务。** 只有底层
   `list_page_embeddings(model, dimensions, config_version)`（database.py:1568），返回
   stored 行（不判 freshness）；无 `indexed / missing / stale` 三态汇总。

7. **覆盖状态应在何处暴露（不引入隐式付费）？** 只读、dry-run 的 `PageEmbeddingIndexer.
   plan_indexing()`（page_indexer.py:210-232）已经能零成本算出 total/reused/missing/stale/
   skipped_empty 五态，是**现成的、零付费的 coverage 汇总入口**——只需一个只读 service
   把它包装给 UI，**绝不**在搜索路径上触发 `index_pages()`。

### 最小 remediation 设计（D-01）

**目标**：让用户可见地了解 embedding 覆盖率（**visibility remediation only**）。索引完成
仍保持显式/手动，v0.5.1 **不新增付费路径、不从搜索触发索引**。

设计组件（全部只读，零付费、零 DB 写）：

1. **新增公开只读 coverage API**（`src/ai/coverage_service.py`）：
   - 提供稳定公开方法（如 `coverage_summary() -> CoverageSummary`），**内部**复用既有
     missing/stale/fresh 分类逻辑（`prepare_page_text` + `get_fresh_page_embedding`），
     **但不暴露私有 `_classify_pages` 给 UI**、不复制散落 SQL。
   - 统计：`total`（非空可索引）/ `indexed`（fresh）/ `missing` / `stale` / `skipped_empty`。
   - **零网络、零付费、零 DB 写**：只读，不构造 provider、不 embed。

2. **UI 只读展示**（新页面或检索页侧栏）：显示"向量索引覆盖率 X/Y（missing M, stale S）"，
   与"AI 模式"并列的可视状态。**无任何按钮触发 embed、无付费路径。**

3. **索引完成保持显式/手动**：沿用既有 `scripts/ai_real_page_index.py` 的
   `--confirm-paid-call` + cost guard + staging 隔离；**不在 UI / 搜索路径引入索引触发**。

4. **召回资格不变**：不引入融合/eligibility hack 补偿缺失 embedding。

**保留的既有 guard**：付费确认、cost guard（batch ≤20、retry=0、provider_calls 精确计数）、
freshness 语义（sha256）、production/staging 隔离（`data/` vs `staging-data/`）。

**D-01 预期 disposition（实现后）**：
`Production OPEN / PARTIALLY MITIGATED — coverage state is observable; indexing completion
remains explicit/manual.`（**不因覆盖可见而标 FIXED**。）

### 不改的东西

- 不改 `recall_scored` 的 freshness gate（缺失即跳过，是正确的零成本契约）。
- 不新增 search-time 隐式索引。
- 不动 `rrf_fuse`。

## Track B — D-02 Weak-Evidence Product Boundary

### Phase 4 结论

**NO-GO for reliable production eligibility rule**（绝对阈值不可分、margin 需 label）。
因此**不引入 cosine 阈值或 benchmark 派生 margin**。

### 现有运行时可观证据元数据（file:line）

| 信号 | 来源 | 是否已暴露给 UI |
|---|---|---|
| `lexical_rank` / `vector_rank` | `HybridHit` (retrieval.py:52-76) → `HybridSearchResult` (hybrid_search.py:86-93) | 是：`search_hybrid_source_meta`（provenance → `result_source` 标签"语义召回/关键词匹配/混合匹配"） |
| `source_count`（1 或 2） | `HybridHit.source_count` (retrieval.py:72-76) | 间接（经 `result_source`） |
| `vector_status`（DISABLED/OK/EMPTY/UNAVAILABLE/FAILED） | `HybridSearchOutcome.vector_status` | 是：`hybrid_status_note`（Phase 2/3 已落地降级提示） |
| 结果数（loaded_count / effective_total） | 检索页 line 821-834 | 是（keyword 侧） |
| embedding 覆盖状态 | 无（Track A 缺失） | **否**（待 Track A） |
| 向量证据缺失（某结果纯词面） | `vector_rank is None`（每结果） | 部分：`result_source` 标"关键词匹配" |

### 最小诚实产品边界设计（D-02）

基于**生产可观测事实**（非阈值、非 label），用保守的确定性布尔规则分层展示：

- **normal evidence**：结果集存在 `vector_rank is not None`（至少一条有向量佐证）→
  现有展示，无额外弱证据警告。
- **WEAK_LEXICAL_ONLY（保守确定性规则）** 仅在**同时满足**以下全部条件时成立：
  1. vector 路径健康/可用（`vector_status in (OK, EMPTY)`）；
  2. 结果集非空；
  3. **每一条**结果都满足 `lexical_rank is not None` **且** `vector_rank is None`。
  → 即向量路径在运行，但返回证据**全部**为词面。此时在结果区顶部显示诚实提示：
  「当前结果主要来自关键词匹配，建议结合原文判断相关性。」
  （**不使用任意比例阈值**如"全/绝大多数"；**不把 `source_count==1` 等同于纯词面
  证据**——`source_count` 是双来源计数，不代表语义无关，仅用显式 `lexical_rank`/
  `vector_rank` 字段判定。）
- **insufficient / unavailable vector evidence**：`vector_status in (DISABLED/UNAVAILABLE/
  FAILED)` → **复用既有** `hybrid_status_note` 降级/回退状态（Phase 2 已落地），
  **不新建**平行状态机、**不叠加**冲突的弱证据提示。

**约束**：
- 只用 `vector_status`、`lexical_rank`/`vector_rank`、结果数、coverage 状态这些
  **生产可观测事实**。
- **绝不**把 benchmark 的 `relevant_pages` / `distractor_pages`（label）作为运行时输入。
- **不引入**任何 cosine 阈值或 margin、任何比例阈值。
- **不新建**与现有降级状态平行的状态机。

## Track C — D-03 Final Result Bound

### `state.limit` 的语义审计

| 事实 | file:line |
|---|---|
| `state.limit` 默认 50，范围 [10,100]，10 取整 | search_state.py:110-111 |
| `result_page` 独立（默认 1） | search_state.py:112-114 |
| keyword：`search_service.search(query, limit=state.limit)` | pages line 190 → search_service.py:105 `safe_limit=min(limit, max_results=100)` |
| hybrid：`outcome.results` **不做截断**，全量进 session | pages line 216-221 |
| 渲染分页用 `RESULTS_PER_PAGE=10`（非 limit） | pages line 70, 868 |
| hybrid `loaded_count = len(results)` = 并集全量 | pages line 821-832 |

**结论**：`state.limit` 的语义是**检索侧加载上限**（lexical `safe_limit`、以及 hybrid 里
传给 lexical/vector recall 的 `limit`），**不是最终返回结果数的上限**。

- keyword：结果 ≤ `state.limit`（lexical 被截断 + `safe_limit`）。
- hybrid：结果 = `lexical(≤limit) ∪ vector(≤limit)`，**可能 > `state.limit`**（理论上 ≤ 2×limit，
  实际上 ≤ 语料页数）。

因此 **`final returned results ≤ state.limit` 这个 product contract 当前不成立**（尤其 hybrid）。

### 最小设计评估：`fused_results[:state.limit]`

**是否匹配现有产品语义？** 部分匹配：keyword 已隐式 ≤ limit；hybrid 缺口。

**显式评估**：

1. **顺序正确性**：`fused_results` 已是 RRF 最终排序（`retrieval.py` 排序键），`[:limit]`
   保留排序，正确。
2. **分页/load-more**：当前 UI 用 `RESULTS_PER_PAGE=10` 分页（line 868），`state.limit`
   不是分页粒度；`[:limit]` 只限制"已载入"总量，不影响 10/页的分页逻辑。需确认
   `effective_total` 与"另有 N 页未加载"提示仍一致（见风险）。
3. **空/回退行为**：空查询返回空列表；`[:limit]` 对空列表无副作用。降级（vector 退化）
   时结果 = lexical 全量 ≤ limit，`[:limit]` 仍安全。
4. **测试影响**：`tests/test_search_hybrid_ui.py` 的 `_ConfigurableHybridService` 返回
   单条结果，不受影响；需新增"hybrid 结果数 > limit 时被截断到 limit"的回归测试。
5. **是否有调用方故意期待 > limit？** 仅检索页消费 `knowledge_results`，当前"已载入 N 条"
   标题在 hybrid 下其实**反映了 > limit 的并集**。截断后标题口径更一致（≤ limit）。

### 设计结论

**D-03 disposition: `Production OPEN — final-result product boundary undefined`。**

审计已确立 `state.limit` 当前语义是**检索侧加载/候选上限**，而非既定的最终结果
product contract。因此对 `outcome.results[:state.limit]` 做切片会**重定义产品语义**，
而不是修复一个已证实的 contract violation。

**v0.5.1 不实施 `outcome.results[:state.limit]` 切片，不改 hybrid 最终结果行为。**

**显式 defer** 在以下两者之间做抉择（留待后续版本）：
- retrieval candidate budget（检索侧候选预算）；
- final presentation / result limit（最终展示/结果上限）。

此二者是**不同语义**，当前混用 `state.limit`，需在后续版本明确拆分。**不引入独立
vector top_k**（与最终结果边界分离，独立问题）。

## migration / schema 影响

## 向后兼容风险

  仅新增可见性。

  非退化。

## 付费/成本影响

- Track C：无（defer）。

## 显式非目标（Non-goals）

- 不引入 `vector_weight`、独立 vector `top_k`、新 RRF 加权。
- 不引入 cosine 阈值 / benchmark 派生 margin。
