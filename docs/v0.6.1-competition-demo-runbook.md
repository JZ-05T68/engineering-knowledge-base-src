# v0.6.1 Competition Demo — Presenter Runbook（演示操作手册）

面向比赛主讲与操作员。目标时长 **3.5–4.5 分钟**；默认 Mode 2 预置离线演示。
配套：`docs/v0.6.1-competition-demo-freeze.md`（场景冻结值）、
`docs/v0.6.1-frontend-teammate-handoff.md`（交接）。

## Before Demo（提前 60 分钟）

1. 启动服务：
   `python -m streamlit run app.py --server.port 8501 --server.address 127.0.0.1 --server.headless true`
2. 确认 `http://127.0.0.1:8501/_stcore/health` 返回 200。
3. 打开「知识Agent」页，确认右上角徽章为「● 预置离线演示」。
4. 依次点一遍 A → B → C 三张场景卡，核对冻结清单中的期望画面
   （徽章、引用数、来源状态），无需逐字检查，画面一致即可。
5. 点底部「演示操作 → 重置演示」回到初始态。
6. 投影设置 1920×1080（或 1366×768，均可用）；浏览器全屏（F11）。

## 5 Minutes Before

- 关闭无关窗口/通知；确认无系统更新弹窗。
- 刷新页面一次，确认初始态（「向你的工程知识库提问」+ 右栏信任提示）。
- 深呼吸。全程只需要点 3 张卡片 + 3 个来源按钮，无需键盘输入。

## Opening（0:00–0:20）

> 各位评委好。工程项目里真正容易流失的，不只是文件，更是工程师解决问题的经验。
> 我们做的 EKB——工程知识库——就是把资料、历史经验和来源依据组织起来，
> 让 AI 的回答能够重新回到来源。下面用三个真实场景演示。

（同时手指向屏幕：品牌区 → 三张演示场景卡。）

## Scenario A — 快速成功（0:20–1:15）

动作：点击「A · 参数影响」→ 等待约 1 秒出答案 → 停顿让观众读徽章 →
点击右栏「#1 · PID 控制器调试手册」。

口播：

> 我先问一个普通的工程问题：PID 调整时，比例项和积分项分别影响什么。
> 注意看，它不是只给一段 AI 文字——回答上方有「有依据回答」的标记，
> 并注明引用了两条来源。每条结论后面都有蓝色编号。
> 我点开第一条来源：可以看到它来自《PID 控制器调试手册》第 12 页，
> 以及它为什么支撑这条回答。

停顿点：徽章出现后 2 秒；来源详情展开后 3 秒。

期望画面：✓ 有依据回答 · 引用来源 2 条；viewer 显示来源详情 · 已验证。

## Scenario B — 历史经验（1:15–2:25）

动作：点击「B · 历史经验」→ 读回答 → 点击右栏来源。

口播：

> 第二个场景是我们最有价值的部分。编码器接线错误曾经导致 PID 震荡，
> 当时是怎么定位、怎么解决的？系统直接找回了那次问题解决的完整记录：
> 根因、定位过程、处理方式、复用条件，全部来自知识记忆里沉淀的工程经验。
> 也就是说，老工程师解决问题的经验，新人可以随时找回来、直接复用。
> 同时大家注意顶部这条提示：这条记录的来源存在限制，系统如实标注出来，
> 提醒核对——这就是它的诚实。

停顿点：「来源存在限制」横幅出现后指给观众看。

期望画面：✓ + ⚠ 双徽章、警示横幅、知识记忆来源。

## Scenario C — 信任边界（2:25–3:35）

动作：点击「C · 来源可信度」→ 点击右栏「#1 · 伺服驱动调试指南」→
停在琥珀色「来源状态 · 来源发生变化」块。

口播：

> 最后一个场景，也是我们最大的差异点。我问它：这个知识对象的来源现在还可信吗？
> 系统检查后明确告诉我：登记的两个来源中有一个，内容与建档时的快照已经不一致，
> 也就是「来源发生变化」。注意它的表述——变化不代表造假或被篡改，
> 但系统不会悄悄把过期资料继续当作可靠事实，而是提醒我们重新核对后再采信。
> 普通聊天机器人做不到这一点；EKB 把信任边界保留在了产品里。

停顿点：琥珀块展开后停 4–5 秒，这是全场记忆点。

## Closing（3:35–4:05）

> 总结一下：EKB 不只是让 AI 多回答一个问题，而是让个人积累的工程资料和
> 解决问题的经验，变成可检索、可复用、可回源、可核验的知识资产。
> 它运行在本地，今天的演示不需要联网，资料也不会上传。谢谢大家。

（4:05–4:30 为缓冲 / 评委过渡，如被提问直接进入 Q&A。）

## If Agent Page Fails（页面异常/白屏）

1. 浏览器刷新（F5）——会话重建即恢复初始态。
2. 仍异常：重启服务（上方命令），约 5 秒内恢复；刷新页面。
3. 全程不解释技术细节，只说“我们重启一下演示环境，几秒钟”。

## If Mode 1 Fails（误切本机 Agent / 服务未启动）

画面会显示「本机 Agent 服务当前不可用」——这不是故障画面，是设计行为。

1. 点击「切换到预置离线演示」，页面自动以预置数据重跑当前问题。
2. 继续演示；不要现场启动 Hosted 服务。

## If Browser Refreshes Mid-Demo

刷新后回到初始态，直接重新点击当前场景卡即可；预置数据确定性一致，
观众看到的答案与刷新前完全相同。

## If Source Viewer Fails（来源详情获取失败）

来源按钮下方会标注「该来源暂时不可检查」，答案不受影响。
口播：“这一条来源的详情暂时没有取到，但答案本身和它的引用关系都在。”
然后继续下一场景。

## If Screen Resolution Is Wrong

1280×800 及以上均可运行；优先 1920×1080，其次 1366×768（内容完整，
回答区略靠下）。避免小于 1280 宽度的投影模式。

## Q&A — 非技术评委

**这跟 ChatGPT 有什么区别？**
通用助手面向所有人回答所有问题；EKB 面向一个人自己的工程资料。最大区别是
“依据”：每条回答都有来源编号，可以点开回到原文，无依据时明确说没有资料。

**这些回答从哪里来？**
来自使用者自己导入并整理的工程资料——手册页面、问题解决记录、知识对象。
当前演示用的是预置演示语料（页面右上角有标识）。

**如果资料错了怎么办？**
系统不判断“对错”，但它保留了两层防线：回答永远带来源，可以人工核对；
资料建档后如果发生变化，会标注「来源发生变化」，提醒重新核对，而不是
继续默默当作可靠事实。

**能不能导入自己的资料？**
可以，本地版支持导入 PDF 并逐页整理，这是产品已经在用的核心流程；
比赛演示为保持确定性使用了预置语料。

**没有网络还能不能用？**
可以。核心的资料管理、检索和今天的演示模式全部本地运行，本次演示就
不需要任何网络与 API Key。

**这个系统现在有人在用吗？**
它是我个人在用的工程知识管理工具，现在把它整理成产品形态参加比赛；
多用户与云端版本在规划中（如实说，不编造数据）。

## Q&A — 技术附录（备查，不主动讲）

**Agent 做了什么？** 单步受控 Agent：理解问题 → 调用只读知识工具（检索页面/
笔记/对象/记忆等七类）→ 汇总证据 → 生成带引用校验的最终回答；无自主循环。

**为什么限制单步？** 可预算、可复现、可审计：固定工具上限避免不可控的多轮
自主行为，演示与生产语义一致。

**怎么防止它乱写？** 回答阶段的引用会逐条校验——引用的 stable_id 必须真实
存在且类型合法，校验失败整个回答降级为失败，不会输出无依据文本。

**来源变化怎么判断？** 本地内容指纹：资料登记时记录快照指纹，读取时与
当前内容比较；changed 表示快照不一致（可能是正常更新），不联网、不做
真伪判断，所以措辞是“发生变化”而非“被篡改”。

**为什么是本地优先？** 工程资料是个人资产，隐私与离线可用是硬需求；
核心功能零网络依赖，AI 能力是可选增强。

**公网为什么暂缓？** 发布前完成本地优先与安全边界的验证优先级更高，
公网部署在路线图中按独立门禁推进。

**为什么演示用预置数据？** 比赛环境需要确定性、可重复、零隐私风险；
预置语料与生产数据物理隔离（不同数据根，零生产库依赖）。
