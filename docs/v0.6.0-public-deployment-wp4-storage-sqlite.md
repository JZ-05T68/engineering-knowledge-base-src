## Hosted Storage Topology

```text
Explicit server settings / manually approved artifact
  -> path + SHA + schema + UUID + structural checks
  -> same-directory temporary DB / validated atomic no-overwrite publication
  -> DATA_ROOT/database/knowledge.db
  -> exact-v12 gate -> existing Database.initialize/migrate_database
  -> independent WAL verification -> HostedStorage
       database: existing short-connection read services / audit append
       observer: bootstrap-owned read-only connection for readiness
```

`src.hosted.storage` is transport-neutral. Database import/construction happens
only in explicit bootstrap, not on app/readiness import. Full dependency and
provider composition is WP5; this package does not mount any write workflow.

## DATA_ROOT Runtime Directories

The configured root must already exist, outside the source tree. Bootstrap reuses
WP1 containment/type policy and explicit startup write probes, then creates only:

- `DATA_ROOT/database/`
- `DATA_ROOT/logs/`

Derived DB/log paths remain centralized in HostedSettings. Link/junction components,
file aliases and escaping paths fail before initialization. Existing target and
sidecar files must be regular, with one hard link. No raw/pages/markdown/backups/
exports/quarantine/runtime directories are created. The `backups` namespace is
rejected before migration if it already exists; it is never reset or deleted.
Python 3.11 lacks `Path.is_junction`; the validator also rejects Windows reparse
attributes from `lstat`. A native NTFS junction smoke confirmed ancestor rejection.

## Demo Artifact Contract

| Setting | Contract |
| --- | --- |
| `EKB_DEMO_DB_ARTIFACT` | Explicit server-side `.db` regular-file path; no symlinks/junctions/hardlink aliases |
| `EKB_DEMO_DB_SHA256` | Exactly 64 hexadecimal characters, normalized to lowercase |
| `EKB_DEMO_KB_UUID` | Canonical UUID string, fixed corpus identity |

All three are optional in HostedSettings so transport-only injection needs no real
artifact. Missing-target bootstrap requires all three. Existing-target bootstrap
requires the expected UUID; it does not open or require the original artifact/hash.
Configuration is init/env only, never HTTP/frontend or repository dotenv. Artifact
path normalization preserves link spelling so validation can reject it.

## Seed Artifact Validation

`validate_seed_artifact` rejects known Local private roots before hashing/opening.
It requires a complete matching SHA, self-contained regular `.db`, no WAL/SHM or
rollback-journal sidecar, exact v12 identity/shape, integrity and foreign-key success,
and structural sanitation. The copied temporary DB is validated independently.
The original artifact is revalidated after copying to catch source changes.

Artifact inspection uses SQLite `mode=ro&immutable=1` only for a sidecar-free input.
No migration, checkpoint, journal-mode change, CREATE/INSERT/UPDATE or repair is
performed on an artifact. Tests compare its bytes/hash and ensure no sidecars appear.

## Structural Sanitization

The complete migration/model/API inventory identifies these stored filesystem columns:

| Table / column | Hosted policy |
| --- | --- |
| `documents.source_path` | Non-filesystem `demo://...` placeholder; existing NOT NULL/nonempty constraints remain |
| `pages.image_path` | Non-filesystem `demo://...` placeholder; existing NOT NULL/nonempty constraints remain |
| `pages.markdown_path` | NULL, empty, or permitted `demo://...` placeholder |
| `ai_outputs.recheck_path` | NULL, empty, or permitted `demo://...` placeholder |

The placeholder grammar permits alphanumeric/underscore/hyphen authority and safe
path segments; it rejects traversal, percent escapes, query/fragment and filesystem
schemes. Windows/POSIX absolute paths, UNC, file:// and relative filesystem paths
are not admitted. Document/evidence filename metadata must be basenames, without
path separators, colon or controls.

`import_records` must be empty. Persisted document import errors/page processing
errors must be empty. Seed `ai_calls` and `ai_outputs` must be empty.

There are **no deletion/quarantine/backup/export/restore state tables in actual v12**.
Deletion recovery and backup/restore use Local filesystem manifests; their model
Path fields are transient records, not extra SQLite columns. These manifests/assets
are never seeded. Unknown tables/columns/views/triggers fail the known-layout gate.

Evidence `source_locator` is a logical document/page/hash locator generated by the
existing service; revision `source_ref` is a typed local ID, not a filesystem path.
Search-result document/image paths are projections of the inventoried stored fields.
Ordinary knowledge prose, notes, revision text and source excerpts are not scanned
for path-looking strings. Engineering text may legitimately discuss C:\\ or /usr/.

## Manual Public-Corpus Approval Boundary

**Structural sanitation is not legal/public-content approval.** It checks declared
filesystem metadata, operational state, schema, identity and integrity. It cannot
prove that prose, titles, notes or a corpus are authorized for public use. The
maintainer must explicitly approve the actual corpus and its SHA/UUID before WP5/6.
No production-derived or competition corpus binary is included in this work package.

## Artifact Hash / KB UUID

SHA-256 authenticates the exact seed input and copied bytes. Runtime identity is
the expected `knowledge_base_meta.kb_uuid`, not permanent file-hash equality.
AI audit append and SQLite WAL/checkpoint legitimately change runtime DB bytes.
The expected UUID must continue matching on restart and readiness observations.

## Seed Algorithm

1. Require explicit Hosted profile and declared one-process/one-worker policy.
2. Check root/layout, then create only database/logs and verify startup writability.
3. If target exists, take the validation-only reuse branch; do not read the artifact.
4. Otherwise validate complete artifact configuration and the immutable input.
5. Copy in bounded 1 MiB chunks to an exclusively created `.ekb-seed-*.db` in the
   target database directory, flush and fsync.
6. Validate copied temp and original artifact again.
7. Publish with `os.link(temp, target)`: an existing target causes atomic failure.
   Remove the temporary name immediately; no unconditional `os.replace` fallback.
8. Recheck bytes/identity, initialize existing runtime and independently verify WAL.

This uses same-filesystem hardlink publication supported by the tested NTFS
environment and by normal POSIX filesystems. A filesystem without that primitive
fails closed; no non-atomic fallback is used. There is no distributed lock.

On ordinary failure, owned temporary/new-seed files are removed; pre-existing or
replacement targets are preserved. Cleanup verifies owned file identity and layout.
An actual cleanup I/O/permission failure remains a sanitized bootstrap failure,
not success; operator inspection may be required. This is not a filesystem sandbox
against an administrator concurrently replacing directories, nor a crash-recovery
daemon. WP5 must exclude overlapping writers and preserve DATA_ROOT ownership.

## Existing DB Behavior

No overwrite/reseed/delete/reset fallback. Before any Database constructor, the
existing file must pass exact schema/UUID/integrity/structural validation. Wrong
schema/UUID failures preserve the file bytes and never invoke migration. Orphan
sidecars without a target, partial WAL/SHM pairs and journal files fail closed.

Valid runtime reuse preserves file identity and corpus/audit rows. WAL checkpointing
may change main-file bytes. No seed SHA equality is required on restart. No reset
endpoint, force-reset setting or operator CLI is added.

## Exact Schema v12 Policy

Both `SCHEMA_VERSION == 12` and complete migration history 1..12 are required, plus
the existing v12 table/column inventory (including FTS5 shadow tables), nine FTS
trigger names and no views/unknown tables. This is validation, not a second DDL or
migration engine. It intentionally rejects unknown schema additions.

`PRAGMA integrity_check` must return exactly `ok`; `PRAGMA foreign_key_check` must
return no violations. These are SQLite's integrity guarantees, not semantic or
public-content verification. No migration/schema object is created by validation.

## Hosted Migration Semantics

The maintainer's WP4 clarification interprets ADR-007 startup migration as:
**validate exact v12 first, then existing idempotent schema/WAL initialization**.
Old/future/empty/unknown databases are rejected. Hosted version-changing migration
is not permitted; Local migration and automatic pre-upgrade backup semantics are
unchanged in the existing Database/migrations modules.

`Database.last_backup_path` must be None. An unexpected newly generated backup
causes failure and cleanup of only the newly created migration backup namespace.
No pre-existing backup is deleted. Legacy migration exception logs are suppressed
only on the bootstrap thread during that call; the Hosted boundary emits a closed
failure code. Filters are restored, preserving Local logging behavior.

## WAL Initialization

Only after the seed/existing gate does the existing Database constructor invoke
`migrate_database`, which sets WAL. Bootstrap then opens a read-only runtime observer
and independently queries `PRAGMA journal_mode`; anything except `wal` fails.
No-op migration and migration-error injections prove setting/returning is insufficient.
No alternate migration engine or checkpoint policy is added.

## Runtime Database Validation

Runtime validation repeats identity, known schema, SQLite integrity/foreign keys and
filesystem/operational metadata checks. It permits runtime audit rows. The application
Database remains writable for existing audit append; READ_ONLY refers to the business
surface, not an OS read-only runtime DB.

All SQLite paths are absolute and derived from DATA_ROOT/database. WAL/SHM are checked
as same-directory regular nonlinked files. The observer lifetime keeps initialized
sidecars available to short-lived runtime connections; it is closed at shutdown.

## Single-process / Single-worker Policy

`HOSTED_PROCESS_COUNT = HOSTED_WORKER_COUNT = 1` and
`validate_hosted_sqlite_runtime_policy` reject any other declared values, including
zero, negative, bool, float or string aliases. Validation precedes mutations.
No OS-process scan, environment heuristic or distributed coordination is claimed.
Actual server command/worker count and no overlapping shared-volume writers are WP5.

## Readiness Integration

WP5 should explicitly compose `HostedReadiness(settings, storage.readiness_reason)`
after `bootstrap_hosted_storage(settings)`. Formal demo identity settings without
that injected observer return `storage_invalid`, not a silent fallback.

Readiness reuses the existing connection, verifies file identity/layout, current UUID,
migration history and actual WAL mode under a short lock. It sees committed live WAL.
It does not seed, migrate, create directories, open a new SQLite connection, issue
write SQL, call AI or run startup write probes. Writability observation uses the
shared WP1 path policy with access checks; actual write probes remain startup-only.

The old quiescent probe uses immutable read-only input only when **no** sidecars
exist. It fails rather than ignoring a live WAL; formal runtime uses the observer.
The existing WP2 test was strengthened from allowing sidecar creation to requiring
an unchanged file set. New HTTP tests also compare file bytes across repeated ready
requests and mutate UUID through WAL to prove the observer does not read stale main DB.

## Private Local Data Exclusion

Known `PROJECT_ROOT/data`, `backups`, `logs` and `runtime` roots are rejected as input.
This explicitly includes the Local production DB. Symlink/junction components and
hardlink aliases are rejected before input open. A synthetic `deploy/demo` packaging
area is accepted; the entire read-only source tree is not categorically forbidden.
Source-tree writes and production DB/dotenv reads are blocked by test guards.

## Failure Semantics

`HostedStorageError` carries closed codes and a fixed safe message; no SQL, input
path, digest, private corpus text or raw exception is exposed. Readiness adds only
`storage_invalid` to its closed reason catalog. Existing public HTTP envelopes and
WP3 middleware are untouched. No failure falls back to Local, creates an empty KB,
retries Agent/provider calls, resets an existing DB or declares readiness falsely.
