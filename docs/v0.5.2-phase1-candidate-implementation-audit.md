## 4. schema v9 数据模型审计

### 4.1 总体结论

- v9 是**纯增量**迁移（`migrations.py:862-1014`）：不重建任何 v1-v8 表，迁移前后
  `_core_data_fingerprint` 一致才提交（`:880,1008`）；迁移前自动备份（`:35-41`）；
  迁移幂等（版本 9 时全部 `_apply_version_*` 跳过）。
- 迁移链版本记录 1..9；生产库 v8→v9 自动备份证据在位（见第 8 节）。
- 长期基础判定：**可作为 Personal Knowledge System 基础，但需按第 6 节裁决做语义修订**；
  四张表的“骨架”（对象/来源/关系/记忆）方向正确，缺陷集中在状态语义、来源真实性、
  事件与记忆混表三个维度。

### 4.2 `knowledge_objects`（`migrations.py:885-918`）

- 列：`id, kind, title(1..200), content(1..20000), importance(primary/secondary/normal),
  status(draft/reviewed/archived), created_at, updated_at, reviewed_at`；
  索引：kind/importance/status 各带 `updated_at DESC`。
- 约束与数据访问：`database.py:1608-1837`（CRUD、LIKE、白名单排序、分页上限 500）。
- 5.1 逐问：
  - **是否真正独立于 Document/Page**：是。表无 document/page 外键；服务与 UI 均不强制
    锚点（`knowledge_object_service.py:134-176`）。这是相对 notes/evidence 的本质进步。
  - **kind/status/importance 语义**：importance 复用 `NoteImportance` 三档（业务语义，
    与展示颜色解耦，OK）。`kind` 六类承担“内容形态”+“认知来源”双重语义（见下）。
    `status` 三态实际承担“复核状态”与“生命周期”双重语义（draft/reviewed 是复核轴，
    archived 是生命周期轴）——**两个维度被压缩进一个字段**。
  - **kind 是否混淆“内容类型/知识可信度/来源类型”**：部分混淆。`concept/fact/principle`
    接近内容类型；`experience/decision/problem` 更接近认知来源/知识形态，且与
    `knowledge_memory_entries.kind`（problem_solving/experience/decision）语义重叠。
    可信度与来源类型并未混入 kind（可信度在 status，来源在 sources），但“内容类型”与
    “认知类型”确实混在同一枚举。
  - **draft/reviewed/archived 是否足以支撑长期生命周期**：不足以完整支撑。archived
    可表达“已过时但保留历史”（墓碑态）；但无 `obsolete/superseded`，无法表达“被新
    知识替代”这一长期知识库最常见的演进。
  - **是否需要 obsolete/superseded**：v0.5.2 不强制（可在 v0.6.x 引入），但必须明确
    承认 archived 承担“过时保留”职责，并在变更日志中留下可回看痕迹（当前缺失）。
  - **现有 relation 能否表达替代关系**：不能。六类关系（`:948-956`）无 supersedes；
    `contradicts` 表达矛盾而非时间上的替代；`derived_from` 表达派生而非替代。
  - **更新知识时是否保存足够历史**：否。update 直接覆盖 title/content
    （`database.py:1669-1739`）；`_log_change` 只写“动作+标题”
    （`knowledge_object_service.py:221-224`），无 before/after。
  - **是否存在静默覆盖用户知识的可能**：**是**。UI 编辑即覆盖（`knowledge_object_ui.py`
    的详情/编辑区为只读展示 + 状态按钮，当前 UI 未暴露 content 编辑表单——但服务层
    update 是覆盖式，且变更日志不含旧内容；一旦 UI 补上编辑框，覆盖即静默发生）。
    判定为需修订（见 6.3）。

### 4.3 `knowledge_object_sources`（`migrations.py:921-939`）

- 列：`id, knowledge_object_id(FK CASCADE), source_type(document/page/note/evidence),
  source_id, source_note(≤500), created_at`；`UNIQUE(knowledge_object_id, source_type,
  source_id)`；索引 `(source_type, source_id)`。
- 5.2 逐问：
  - **四类来源**：document/page/note/evidence（`models.py:929-945`）；服务层映射到
    documents/pages/notes/evidence_items 四张表（`knowledge_object_service.py:386-399`）。
  - **来源链接是否只校验“对象仍存在”**：是。`_source_target_exists` 只做
    `SELECT 1 FROM {table} WHERE id = ?`（`:395-399`）。且写路径校验不统一：
    `link_source` 总是校验（`:267-270`）；`create` 仅 reviewed 状态校验，**draft 可
    携带不存在的来源被成功创建**（`:155-176`）。
  - **来源内容变化后知识对象是否仍被错误视为有效**：**是**。页面文本被修改/OCR 更新
    后，只要 page 行存在，来源仍 VALID，reviewed 状态不受影响。这弱于笔记锚点
    （`NoteSourceStatus.CHANGED`，`models.py:249-268`）与证据（`source_text_sha256`）。
  - **是否复用 SHA-256/freshness/Evidence 校验**：否。未复用任何指纹机制。
  - **多态来源是否可能形成悬空引用**：SQLite 无多态 FK；服务层写前校验（不完整），

  - **删除文档/页面/笔记/证据后的语义**：文档删除前清理四类链接（含其页面/笔记/
    证据，`:370-408`）；单独删除页面/笔记/证据（非经文档删除服务）时**无级联清理**，
    但读时实时重算为 MISSING（`source_views:238-253`）。知识对象本身保留。
  - **reviewed 状态与来源有效性的关系**：create/update 时点强制≥1 有效来源；但
    `unlink_source` 与文档删除清理不维持该不变量（见 BLOCKER-2）。
  - **来源事实和用户解释是否明确分离**：部分分离。`source_note`（≤500）可承载用户
    解释，但与来源事实同存一行；提示词包中来源与知识对象内容并列但知识对象内容本身
    可能含个人判断（提示词规则 6 已警告，`knowledge_prompt_builder.py:29-31`）。
    结论：**事实/解释分离不彻底但方向正确**。

### 4.4 `knowledge_relations`（`migrations.py:941-967`）

- 列：`id, source_ko_id(FK CASCADE), target_ko_id(FK CASCADE), relation_type(六类),
  description(≤1000), created_at`；`UNIQUE(source_ko_id, target_ko_id, relation_type)`；
  `CHECK(source_ko_id <> target_ko_id)`；两个方向索引。
- 5.3 逐问：
  - **是否拒绝自环**：是，DB CHECK（`:956`）+ 服务层 ValueError（`database.py:1931-1932`）。
  - **是否拒绝重复关系**：是，UNIQUE 三元组（`:955`）。
  - **是否允许反向冲突**：**允许**。`A supports B` 与 `B contradicts A` 可同时存在
    （UNIQUE 只挡同向同类型）。这是“允许”而非“拒绝”——合理（知识可互斥），但 UI
    无冲突提示。
  - **六类关系真实语义**：relates_to（相关）、derived_from（派生自）、supports（支持）、
    contradicts（相矛盾）、example_of（是…的实例）、requires（依赖）（`models.py:948-968`）。
    语义清晰，方向明确。
  - **能否表达“替代、修正、依赖、支持、反驳”**：依赖=requires ✓，支持=supports ✓，
    反驳=contradicts ✓，替代=**无**，修正=**无**（只能用 contradicts + description 近似）。
  - **删除对象后的级联行为**：`ON DELETE CASCADE` 双向删除关系（测试覆盖
    `test_schema9_knowledge_foundation.py:283-317`）。
  - **当前是否只是 UI 装饰**：基本是。关系仅在对象详情展示（`knowledge_object_ui.py:

  - **是否存在无边界知识图谱倾向**：否。六类直接关系、无图查询引擎、无传递闭包，
    符合 Phase 0 非目标（6.7 节）。

## 6. 七个核心问题裁决

### 6.1 无来源个人知识与 reviewed 冲突 —— **BLOCKER**

- 现状确认：
  - 无外部来源的个人经验/判断/失败教训可创建（draft 无源，`knowledge_object_service.py:
    54-65` 测试覆盖；记忆条目可无源，`knowledge_memory_service.py:78-114`）。
  - `reviewed` 要求至少一个有效来源（`knowledge_object_service.py:155-162,199-207`）。
  - 因此：**无来源个人经验会永久停留在 draft**，除非用户伪造一个来源链接。
- 裁决：
  - “外部证据充分”与“用户本人已经确认”被错误合并为同一状态 `reviewed`——确认。
  - 应当把 **lifecycle status / epistemic type / source status** 拆成不同维度——方向
    正确，但 v0.5.2 不应为此重建 schema。
  - fact/experience/decision/judgment 需要不同确认规则——确认。fact/concept/principle
    必须有外部来源；experience/decision/problem 属于用户自身认知，用户本人就是合法
    认知来源。
  - **最小方案（符合 v0.5.2 边界，无 schema 变更）**：服务层按 kind 区分确认规则——
    `fact/concept/principle` 设 reviewed 仍需 ≥1 有效来源；`experience/decision/problem`
    允许用户无来源复核（用户本人确认即 reviewed，`reviewed_at` 记录确认时间）。
    同时提示词包对无来源 reviewed 对象保留“个人判断”标注（已具备规则 6，
    `knowledge_prompt_builder.py:29-31`）。
  - 伴随修复（同一规则实现）：`unlink_source` 与文档删除清理后必须重算受影响 KO 的
    reviewed 资格——不满足规则时自动降为 draft 或要求用户显式处理；不得静默保持
    reviewed 零来源。
- 结论：**必须先裁决/实现该规则才能继续开发**；这是本阶段的 BLOCKER-1。

### 6.2 来源真实性与 freshness —— **v0.5.2 release gate**

- 现状确认：来源链接只校验行存在（`knowledge_object_service.py:386-399`）；弱于
  v0.4.x/v0.5.x 已建立的证据可信边界（笔记锚点 `NoteSourceStatus.CHANGED`、
  证据 `source_text_sha256`、embedding `source_text_sha256` freshness）。
- 裁决：
  - 当前实现确实弱于既有证据可信边界——确认。
  - 来源内容变化后系统无法识别——确认（页面文本更新后来源仍 VALID）。
  - 最小可信方案可复用现有哈希与 evidence validation——确认：
    - `document` 来源：复用 `documents.sha256`（文件级指纹，已存在）；
    - `page` 来源：链接时计算 `searchable_content` 的 SHA-256（复用页面检索内容），
      读时重算比对；
    - `note` 来源：复用 note 行 `source_page_text_sha256`/`personal_note` 内容指纹；
    - `evidence` 来源：复用 `evidence_items.selection_sha256`/`source_text_sha256`。
    - 实现形态：`knowledge_object_sources` 增一列 `source_fingerprint`（v10 纯增量），
      服务层写时计算、读时比对，状态机增加 `CHANGED`；`reviewed` 有效性要求
      `VALID` 且指纹一致。
  - 哪些来源必须绑定 fingerprint：**page、note、evidence 必须**；document 建议绑定
    文件 sha256（可选，因为文档文件在 EKB 内只读保存，变化概率低，但绑定成本低）。
  - 哪些只需存在性校验：无。v0.5.2 至少要“存在 + 指纹一致”才可称有效；纯存在性
    只能作为 draft 对象的可追溯线索。
  - **属于 v0.5.2 release gate**：是。否则“已复核”可能建立在已被修改的原文之上。

### 6.3 知识过时、替代和演进

- `archived` 能否表达“已过时但保留历史”：**可以**（作为生命周期墓碑态，且归档不清
  来源与关系）。可接受为 v0.5.2 的过时表达。
- relation 能否表达 supersedes：**不能**（六类无 supersedes，CHECK 枚举加值需重建表，
  延后 v0.6.x）。
- 用户更新是否覆盖旧内容：**是**（`database.py:1669-1739` 覆盖式 UPDATE）。
- 当前 change log 是否足以重建演进：**否**（只有动作+标题，无前后内容）。
- v0.5.2 至少需要的生命周期能力：draft/reviewed/archived 三态 + **变更日志保存前后
  内容**（可重建内容演进）+ 明确 archived 承载“过时保留”语义。`supersedes` 关系与
  自动过时判断属于 v0.6.x。
- 裁决：**v0.5.2 release gate = 变更日志内容快照**；替代语义整体延后 v0.6.x。

### 6.4 统一检索闭环 —— **v0.5.2 release gate（闭环失败确认）**

- 现状确认：
  - Knowledge Object 未进全局搜索：`SearchService.search` 只检索页面
    （`search_service.py:99` “Search local pages”）；`pages/4_检索资料.py` 中的
    `knowledge_*` 键是检索会话命名（`:174-196`），与知识对象无关。
  - KO 检索仅为页内 `title/content LIKE`（`database.py:1824-1828`）。
  - Memory 无任何关键词检索（`knowledge_memory_service.py:48-64`）。
- 裁决：**“记录后找不到”判定为 Knowledge Foundation 闭环失败**——确认。
- 最小离线方案（不引入 embedding）：为 `knowledge_objects` 与
  `knowledge_memory_entries` 建立 FTS5 外部内容表（复用 `page_search` 同款
  `unicode61 remove_diacritics 2` 分词，中文可再经 jieba 查询归一，与现检索一致），
  在 `SearchService`/`pages/4_检索资料.py` 增加结果类型（页面/笔记/证据/知识对象/
  记忆），结果卡片区分类型并支持回源（对象详情→来源页面）。
- 裁决：v0.5.2 验收必须包含该闭环（AC-06）；无 embedding 的 FTS 方案足够。

### 6.5 Memory 与系统事件的边界

三种方案比较：

| 维度 | 共表保留（现状） | 拆表（Memory / Event·Revision） | 共表 + 严格类型隔离 |
|---|---|---|---|
| migration | 无 | 新增表 + 数据搬迁（v10） | 无（或仅补索引） |
| 查询 | 简单但每查须 kind 过滤 | 各自清晰 | 需纪律性 kind 过滤 |
| UI | 混展（已有徽标区分） | 天然分离 | 分 tab/过滤器即可 |
| 导出 | 需过滤，易混 | 天然分离 | 导出时显式排除 knowledge_change |
| 删除 | 服务层无守卫（当前缺陷） | 权限天然分离 | 服务层强制系统行不可改删 |
| 未来 Agent | 需过滤 | 直接读 Memory | 需过滤但成本低 |
| 审计可信度 | 中（可被改删） | 高 | 高（若强制不可变） |

裁决：**v0.5.2 采用“共表 + 严格类型隔离”**（零迁移成本）：服务层强制
`knowledge_change` 不可手动创建/更新/删除（补上 update/delete 守卫）；UI 分 tab 或
默认过滤；导出与未来 Agent 一律按 kind 隔离。拆表方案延后 v0.6.x 与 Revision 需求
一并评估。

### 6.6 数据可迁移性

- 区分五类场景：
  - 灾备恢复：现有完整备份/恢复（`backup_service.py`）覆盖，**保留**。
  - 更换电脑：完整备份恢复 + 路径重定位（既有能力），**保留**。
  - EKB 版本升级：迁移链 + 迁移前备份（v8→v9 已实证），**保留**；v8 备份恢复缺口见 6.7。
  - 模型供应商替换：知识数据纯本地结构化，与 Qwen/embedding 无关（`runtime.py:108-133`
    证明无 AI 启动依赖），**已满足**。
  - 导出到其它工具：**当前缺失**（仅按对象生成提示词文本，无批量导出）。
- 裁决：v0.5.2 至少需要 **结构化 JSON 导出（无损、非模型依赖）+ 每对象 Markdown +
  manifest（含来源与关系的可重建标识，如稳定本地 ID 与跨引用）**。JSON 为主（可重建
  关系），Markdown 为人类可读副本；`knowledge_change` 默认不含或独立文件。本阶段只
  决策，不实施。

### 6.7 v8 备份与 v9 恢复

五种路径比较：

| 路径 | 数据安全 | 回滚 | manifest 版本 | schema 校验 | 路径重定位 | 失败恢复 | 用户复杂度 | 测试成本 |
|---|---|---|---|---|---|---|---|---|
| 1. v0.5.1 恢复旧备份后启动 v0.5.2 自动迁移 | 高 | 好 | 一致 | 强 | 有 | 好 | 高（需旧版） | 中 |
| 2. v0.5.2 在隔离临时目录恢复 v8 后迁移 | 高 | 好 | 需两段 | 强 | 有 | 好 | 中 | 中 |
| 3. 修改正式恢复器直接接受 v8 | 中 | 差（顺序易错） | 复杂 | 需放宽 | 有 | 中 | 低 | 高 |
| 4. 独立升级/导入工具 | 高 | 好 | 清晰 | 强 | 有 | 好 | 中 | 中 |
| 5. 保持现状 + 文档化路径 | 低（资产不可用） | — | 一致 | 强 | — | — | 高 | 低 |

裁决：**推荐路径 2/4 的合并形态**——在正式恢复流程外提供“v8 备份升级恢复”入口：
先恢复到隔离 staging 目录 → 按 v8 严格校验 → 在隔离库上执行迁移到 v9 → 复检 →
再按正式恢复流程落位（含 pre-restore 备份）。正式 `validate_backup`/`restore_backup`
的 schema 精确匹配不变量**保持不变**（`backup_service.py:651-654,776-784`）。这样
数据安全、回滚、校验强度都不被削弱。实施放 Phase 2；**本阶段未修改
`backup_service.py` 或 `scripts/restore_backup.py`**。
